# 监督者

## 职责

监督者负责检查 worker 心跳、队列积压、处理中卡住任务和失败窗口，并发送 Telegram 告警。Telegram 现在只承接错误、异常和需要人工介入的问题，不再承接正常新信源、标题提醒、此前消息或巨鲸业务消息。

## SQLite 争用诊断日志

共享 `connect_sqlite` / `connect_sqlite_readonly` 连接向服务标准错误输出 `[sqlite-observe]` JSON：锁错误 `locked`、耗时至少 1 秒的语句 `slow_statement`，以及持续至少 2 秒的事务 `long_transaction`。记录数据库文件名、进程号、调用代码位置、操作类型、耗时和错误码，不记录 SQL 内容、参数或业务数据。通过 systemd journal 按服务、时间、进程和数据库对照；慢语句不一定在等待锁，长事务也不必然持有写锁，结束时才报告，异常中止的进程可能没有结束日志。未使用共享连接、自定义 cursor、部分游标迭代和底层隐式操作不在覆盖范围内。此日志不改变超时或重试策略，也不自动告警。

## 当前必需心跳

- `x_capture`
- `non_mainstream_media`
- `competitor_monitor`
- `jin10_monitor`
- `local_pipeline`
- `whale_watch`
- `whale_watch_hyperliquid`
- `fact_auditor`（发布后事实审查者；内容问题只在快讯总览展示，worker 心跳异常走系统告警）

旧的 `x_process_*` 分阶段 worker、`external_media_alert_*` 分阶段 worker 和 `external_media_alert_fetcher` 都不再属于生产必需心跳。

`whale_watch_hyperliquid` 对 Hyperliquid 官方 `info` 接口的 `500 / 502 / 503 / 504` 上游故障使用 `status=degraded`、`success=true` 心跳，失败地址保留在 metadata 和地址状态表中。监督者按 `last_success_at` 判断近期成功心跳时，不应把这种上游故障误报为 worker 进程无成功心跳；非上游故障仍会写失败心跳并触发健康告警。

`non_mainstream_media` 是多站点统一收集器。单批至少一个站点成功时使用 `status=degraded`、`success=true`，失败站点和 item 明细保留在 metadata；只有整批已尝试站点全部失败或 worker 外围异常才写失败心跳。监督者因此不会再把 Hankyung、TheElec、Tether、FT 等单站故障放大为整个 worker 无近期成功心跳。

## 任务监控范围

监督者仍覆盖：

- `x`
- `blockbeats`
- `panews`
- `jinse`
- `jin10`
- `non_mainstream_media`
- `ai_source`
- `mainstream_media`
- `external_media_alert`
- `ai_source_alert`

其中 `mainstream_media` 仅用于发现历史任务残留或堵塞。

本地流水线切换后，监督者不再把 `judged / searched / deduped / written / publisher_pending` 等阶段状态理解为“应该被某个远端 worker 领取的队列积压”。这些状态仍会作为观察状态保留在 `tasks` 中，真正的推进由 `local_pipeline` 本地 SQLite 队列负责。

当前仍需要重点告警：

- 旧入口或收集器遗留的长期 `pending`
- 本地流水线心跳丢失
- 本地队列已经停止自动重试的 `exhausted` job；告警样例包含 `job_id`、`task_id`、来源、尝试次数和最后错误
- 近期失败状态：`judge_failed / domain_failed / search_failed / write_failed / format_failed / publish_failed / publisher_failed / notify_failed`

`exhausted` 是 `local_pipeline_jobs` 的队列状态，不是业务任务状态。它表示同一个本地 job 已经失败 3 次，系统为防止无限重试而停止继续尝试；对应的 `tasks` 行和 pipeline 失败原因仍然保留，不会被监督者自动删除或改成成功。

SQLite 中任务时间可能同时存在 `YYYY-MM-DD HH:MM:SS` 和带时区的 ISO 8601 格式。监督者判断 `pending` 积压、`running` 超时和锁过期时统一通过 SQLite 时间函数比较，并在聚合最老时间前规范化；禁止直接按原始时间字符串比较，避免把刚入库任务误报为超过阈值。

`competitor_monitor` 的 BlockBeats 单来源失败不作为 Telegram worker 健康告警条件。BlockBeats key 缺失、额度不足、429 或普通请求失败会写入本地 `data/config/blockbeats_key.json` 并由控制台展示；只要 PANews、金色财经、Odaily 等其他来源和竞品 worker 主循环仍正常，监督者不应因为 `failed_sources.blockbeats` 单独发送“worker 无近期成功心跳”。

失败任务告警必须包含：

- `环节`：按任务状态映射到判断者、搜索/查重、编写者、发布者、标题提醒等。
- `分类`：例如 `database_connection`、`external_ai_billing`、`external_rate_limit`、`external_auth`、`telegram_delivery`、`publisher_push`、`program_output_parse`、`external_network`、`program_or_unknown`。
- `样例`：对应 pipeline 的 `last_error` 截断样例。
- `动作`：给值班人员的第一步排查建议。

错误分类、环节映射和排查建议由 `packages.common.failure_diagnostics` 统一提供，监督者 Telegram 告警与控制台任务详情使用相同分类口径；控制台还会在单条任务详情中补充本地队列 job 和 worker 心跳证据。

如果近期 `search_failed` 的 `last_error` 明确命中 DashScope embedding `Arrearage`，监督者除了保留常规“失败任务异常”外，还会额外发送一条专门的 Telegram 告警：

- 类型：`DashScope 欠费需充值`
- 对象：对应 `source/search_failed`
- 动作：明确提示值班人员立即充值或恢复 DashScope embedding 账号

这条告警是对常规失败窗口告警的补充，不替代 `search_failed` 本身。

## X 抓取健康判定

监督者判定 X 抓取是否健康时，优先检查 `pipeline_worker_heartbeats` 中 `x_capture` 的近期成功心跳。

只有近期没有成功心跳时，才回退检查 `x_capture_attempts` 是否存在近期 `success` 记录。该 fallback 使用存在性检查，不做 `count(*)` 全量计数；如果 attempts 查询本身超时或失败，监督者按 X 抓取不健康继续告警，但不让自身进程崩溃。

## 初始化边界

`pipeline-supervisor` 是常驻监控命令，读取主 SQLite 中的任务、心跳与告警去重表。监控表由相关 `*-init-db` 命令初始化；生产排障时不要通过反复重启监督者触发 schema 变更。

监督者常驻循环会捕获单轮检查异常并继续下一轮，避免一次数据库连接、网络或 Telegram 波动导致监督者自身退出。

## 系统巡检

控制台 API 在自身进程内启动独立的系统巡检 worker，不替代 `pipeline-supervisor`，也不增加第二个常驻 systemd 服务。它每 5 分钟复用配置和 `pipeline_worker_heartbeats` 检查启用渠道及缺失心跳；只检查当前启用组件，并按组件选最新 worker 实例，避免 PID 历史心跳形成大量重复告警。成功空结果、停用源和数据库中明确关闭的计划不报成渠道中断。worker 重启时，遗留的 `running` 巡检 run 会结为失败并记录重启中断。健康状态读取失败会保留读取错误，不伪装为“无问题”。竞品服务和事件数据使用活动主 SQLite，系统巡检不再读取旧的独立竞品数据库路径。

巡检 worker 每日 06:00 后幂等运行漏闻候选、审核复盘、活动规则冲突、失败恢复和证据留存任务。质量问题保存在独立巡检表，控制台人工决定与运行恢复分开。新增模型复核异步排队，最多每日 100 次及 100 万输入 tokens；达到任一上限暂停并顺延，不视作通过。模型超时或解析失败保留结构化错误、可用请求 ID、原始响应证据与实际用量，自动尝试最多 3 次。

来源 SQLite 为已登记的可变业务表创建 `odaily_observability_outbox` 触发器，在业务状态事务内写入身份、状态、阶段、错误/理由、投递返回摘要及时间字段；不复制正文、模型原始响应、凭据或配置。投影器以水位和稳定事件 ID 恢复，成功投影 24 小时后的源 outbox 行可清理。已结束主任务的普通状态事件超过七天后分批清理；阶段尝试的清理须校验来源任务和审核状态，保留事件身份。运行健康页显示事务记录表覆盖数、缺失数和水位。每日维护不自动删除孤立证据，因为仅查观测库不能证明来源库没有引用。数据库与证据可写入独立持久卷 `ODAILY_SYSTEM_OBSERVABILITY_DIR`；生产目标为 `/data/OdAIly/system-observability`。运行状态、剩余空间和 30 天增长估算在运行健康页展示，空间不足不自动删证据。

巡检字段、证据来源和当前独立业务适配范围见 `控制台-系统巡检.md` 与 `控制台-全量信息流.md`。
