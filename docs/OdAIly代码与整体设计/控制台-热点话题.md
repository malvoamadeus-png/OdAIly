# 控制台-热点话题

## 边界

`热点话题` 是 X Agent 内的只读话题组件。它使用现有本地 Bearer session 和 `/console` 鉴权，数据不进入主 `odaily.sqlite`，也不读取或修改 `x_capture_accounts`。

- 独立数据库：`data/runtime/hottopic.sqlite`。
- 独立 worker：`odaily-hottopic.service`，成功账号按 10 分钟节奏轮询；FXTwitter 请求在同一 worker 内默认错开 2 秒，429 会触发共享冷却和账号退避；每次 SQLite 聚合最多处理 100 条 inbox 内容。
- API：既有热点读取接口为 `editor-plugin-api-server` 的 `/console/hottopic/dashboard`、`/topic`；统一账号目录和订阅开关通过 `/console/x-agent/*` 接口维护，均要求控制台管理员 session。
- 控制台在 X Agent 内只读展示当前热点、参与账号和抓取错误。账号新增及三个订阅开关统一在 X Agent 账号目录操作。

## 话题归并

归并先使用同一 `$` 资产、明确的裸 ticker（如 `QNT`）或合约地址等强身份。对没有资产锚点的发布、产品、公司或协议事件，则在 24 小时窗口内要求同时满足：至少两个非泛化命名实体相同、事件动作类别相同、合并后至少有三个独立账号。宽松的词汇召回、普通中文切分词和单一平台名不构成归并身份；两个不同的主要资产也不会走此兜底路径；已有明确资产锚点的话题也不能仅凭 Binance、钱包等共同实体并入无资产话题。热点资格评估也使用同一身份：共同出现的一对命名实体可作为参与者锚点，精确相同的合约地址同样可作为强参与者锚点；不能由单一平台名凑足人数，名称相同但合约不同的内容也不会相互计数。这个规则统一处理非资产事件，不维护按项目或产品名称列出的特例。每小时维护会重归并最近 24 小时仍开放的话题，因此规则升级不依赖下一条新内容才生效。

确定性召回形成候选后，系统再按 claim 逐条进行语义复核。复核输入包含待归并材料、当前话题标题/主题/事件类型和少量已接受代表材料，不按账号整体判断。模型返回三类：`support` 计入参与账号、热度、检索和正文；`context` 保留为可选背景但不计入参与账号或热度；`unrelated` 只保留审计，不进入正文、参与人数、热度或后续检索。模型不可用、超时或返回非法分类时沿用确定性结果并记录 fallback，避免模型故障造成整批数据丢失。复核结果按 claim、topic 和输入指纹缓存；每小时维护会以有界批次补审历史上尚未复核的关系。

## 首次部署

首次启动 worker 时会创建 `hottopic_meta.deployment_started_at`。它是不可回退的 UTC 水位线：早于该时间的帖子不会进入 inbox、SQLite 或热点归并。禁止复制旧 HotTopic 的 `state.sqlite`、`service.sqlite`、帖子或话题到生产。

`backend/packages/hottopic/initial_accounts.csv` 是一次性最小种子，只包含旧服务最后 48 小时活跃账号的用户名和显示名。种子账号默认打开热点话题；完整账号目录和市场情绪、项目推介的初始化建议由本地 X Agent 初筛报告显式导入。

生产同步代码后安装单元并启动：

```bash
sudo cp deploy/odaily-hottopic.service /etc/systemd/system/
sudo systemctl daemon-reload
sudo systemctl enable --now odaily-hottopic.service
sudo systemctl status odaily-hottopic.service
```

首次启动前确认根分区保有至少 5 GB 可用空间；运行中观察 `data/runtime/hottopic.sqlite`、`systemctl status odaily-hottopic.service` 和控制台的抓取异常计数。

正文模型默认 `gpt-5.6-luna`、`reasoning_effort=none`；Luna 请求或结构化输出失败时，使用 `gpt-5.6-terra`、`reasoning_effort=none` 重试同一材料。`HOTTOPIC_MODEL` 和 `HOTTOPIC_FALLBACK_MODEL` 可覆盖这两个路由。`HOTTOPIC_OPENAI_BASE_URL`、`HOTTOPIC_OPENAI_API_KEY` 可单独覆盖模块兼容 API；未指定时依次使用通用 `ODAILY_LLM_BASE_URL` 和兼容旧部署的 `X_PROCESS_OPENAI_BASE_URL`。本机 LiteLLM 使用 `LITELLM_MASTER_KEY`，不将外部上游凭据发送给本机代理。

语义复核默认使用 `gpt-5.6-luna`、`reasoning_effort=high`，失败时回退 `gpt-5.6-terra`、仍使用 `high`。相关配置为 `HOTTOPIC_CLAIM_REVIEW_ENABLED`、`HOTTOPIC_CLAIM_REVIEW_MODEL`、`HOTTOPIC_CLAIM_REVIEW_FALLBACK_MODEL`、`HOTTOPIC_CLAIM_REVIEW_REASONING_EFFORT`、`HOTTOPIC_CLAIM_REVIEW_OPENAI_BASE_URL`、`HOTTOPIC_CLAIM_REVIEW_OPENAI_API_KEY`、`HOTTOPIC_CLAIM_REVIEW_TIMEOUT_SECONDS`、`HOTTOPIC_CLAIM_REVIEW_BATCH_SIZE` 和 `HOTTOPIC_CLAIM_REVIEW_BACKFILL_LIMIT`。复核请求默认按最多 40 个 claim-topic case 批量发送，每轮维护默认补审最多 120 条历史关系；未配置凭据时只使用机械候选结果，生产数据不会因此停止采集。

正文证据会过滤与当前资产锚点冲突的其他 ticker；同一资产邻近话题只能补充不带竞争资产的行情背景。写作 Prompt 要求只保留材料中的事实和已归因的观点，不加入编辑者自己的免责声明或结论性提醒，并要求同一行情事实只写一次；当材料包含事件背景、数据变化、社区观点或争议等明显不同的叙事层次时，要求正文分成 2 至 4 个自然段。模型返回后还会去除固定的编辑元话术（包括“并非已兑现”“不构成确定性结论”“这一说法来自市场参与者的解读”等）和完全重复句，但保留“有人猜测”以及明确主体的正常来源归因。

热点读模型同时返回 `firstGeneratedAt` 和 `lastUpdatedAt`：前者取话题首次进入聚合状态的 `first_seen_at`，后者取最近一次被接受的证据时间 `last_evidence_at`；若历史数据缺少后者，则回退到首次生成时间。它们描述话题生命周期，不等同于最近一次正文 AI 调用时间。

## 订阅与保留

账号目录只维护热点话题、市场情绪和项目推介三个订阅开关。任一开关开启时账号进入共享采集调度；全部关闭时停止调度，但既有热点和运行结果按保留策略继续存在。临时内容、未成热点话题、inbox 和短期审计保留 48 小时；运行事件保留 5 天；成为热点的永久档案不清理。

热点话题是否消费某条共享 inbox 由 `hot_topic_enabled` 控制。关闭该开关不会影响同一账号已经打开的市场情绪或项目推介消费；只要三个订阅开关仍有一个打开，账号仍可由共享 worker 采集。具体账号目录契约见 `控制台-X Agent.md`。

## 已接入、待部署的事件自动追踪

热点自动快讯从已形成的 HotTopic 开始，但不把 `topic_id` 当作事件唯一键。同一真实事件的多个阶段性 topic 应归入一个 `tracking_event`，并用独立 `tracking_cycle` 保存短线追踪生命周期。任务 1 的二元 `track` / `do_not_track` 判断和 GPT Web Search 官方账号发现均不改变当前热点归并规则。

事件追踪使用独立的 `event_tracking_*` 表和 inbox。它只读取已自动核验的官方账号；事件账号不加入 `hottopic_accounts`，事件原帖不回灌 `hottopic_inbox`。同一 worker 复用 FXTwitter 2 秒 pacer、429 冷却和退避，事件账号优先，最多 15 个全局账号、每个事件最多 3 个账号，目标轮询间隔为 1 分钟。

每条新官方帖必须先判断为 `material_progress`、`relevant_no_progress` 或 `irrelevant`。只有实质进展能通过 durable outbox 创建 `tasks.source = 'event_tracking'`，再走主写作链路的全站查重、写作、格式化和幂等自动发布；其他内容绝不生成快讯候选。完整契约与上线验收见 `docs/讨论与修改日志/热点话题长期追踪升级计划书.md`。

## 写入与性能边界

启用语义复核时，确定性候选关系先提交，AI 复核在事务外执行，复核结果提交后才重建参与人数、话题归并、热度和可见性；正文生成也在此之后执行。

SQLite 只有一个写者。话题归并的确定性状态先提交，再在写事务外完成 claim 语义复核并重建参与人数、热度和可见性，之后才发起可能重试的 AI 正文生成；每篇正文完成后立即提交。账号订阅开关在短事务中保存，不等待 AI 请求或执行无上限内容删除。X Agent 的市场情绪和项目推介模型调用也在短事务外执行，并用各自的任务消费位与热点处理隔离。历史清理队列仅用于兼容旧库，worker 按小批次恢复执行，异常会保留在队列记录中供下一轮重试。

聚合批次失败时，事务回滚，inbox 内容保持未处理状态，并记录 `aggregate_error` 运行事件；下一次重试前会从 SQLite 重建话题检索缓存，避免缓存引用已回滚的话题而重复触发外键错误。确定性 seed 写入使用幂等插入，以兼容话题已提交但 inbox 标记尚未完成的重试。批次成功提交后才标记 inbox 内容为已处理。
