# 控制台-热点话题

## 边界

`热点话题` 是 X Agent 内的只读话题组件。它使用现有本地 Bearer session 和 `/console` 鉴权，数据不进入主 `odaily.sqlite`，也不读取或修改 `x_capture_accounts`。

- 独立数据库：`data/runtime/hottopic.sqlite`。
- 独立 worker：`odaily-hottopic.service`，成功账号按 10 分钟节奏轮询；FXTwitter 请求在同一 worker 内默认错开 2 秒，429 会触发共享冷却和账号退避；每次 SQLite 聚合最多处理 100 条 inbox 内容。
- API：既有热点读取接口为 `editor-plugin-api-server` 的 `/console/hottopic/dashboard`、`/topic`；统一账号目录和订阅开关通过 `/console/x-agent/*` 接口维护，均要求控制台管理员 session。
- 控制台在 X Agent 内只读展示当前热点、参与账号和抓取错误；dashboard 和话题详情都只读取 `matching_status='active' AND visibility='visible'` 的话题。账号新增及三个订阅开关统一在 X Agent 账号目录操作。

## 话题归并

主题级归并以“读者会当作同一个热点，且能写成一篇准确的综合报道”为准。一次向模型输入全部 `active + visible + ready` 话题的页面标题和最多 700 字摘要，粗筛只提出候选组及共同主线；重叠候选合成一组后，再用每条完整正文及原始 support claim 深审共同事实、应保留的差异和证据。仅明确通过且每个成员都有原始证据时合并；模型失败或结论模糊时保留原话题。隐藏 seed 与归档话题不参与。合并保留最早形成的活动话题及其身份，复用 memberships、threads、参与人数和自动快讯关联；首次综合正文只使用两侧原正文引用及深审确认的 claim，写出草稿后再按深审列出的共同事实、应保留差异和失真风险修订一次，避免旧的混杂 membership 改写主线或漏掉一侧的独有信息。按全量输入指纹、候选组、深审结论、证据 claim ID、合并记录和失败原因审计。旧的词语召回及 40 对截取不再用于生产主题归并；claim 内部的 `support/context/unrelated` 复核继续运行。

claim 级参与内容复核改为每小时一次。新内容先按确定性结果展示；维护时逐条判为 `support`、`context` 或 `unrelated`，随后重建参与人数、热度、检索与正文。`context` 不计入参与，`unrelated` 不进入正文。模型不可用时暂沿用确定性结果并保留失败审计，下一轮重试。每轮最多补审 120 条未审/失败关系，健康状态公开待审数。

## 首次部署

首次启动 worker 时会创建 `hottopic_meta.deployment_started_at`。它是不可回退的 UTC 水位线：早于该时间的帖子不会进入 inbox、SQLite 或热点归并。禁止复制旧 HotTopic 的 `state.sqlite`、`service.sqlite`、帖子或话题到生产。

`backend/packages/hottopic/initial_accounts.csv` 是一次性最小种子，只包含旧服务最后 48 小时活跃账号的用户名和显示名。种子账号默认打开热点话题；完整账号目录和市场情绪、项目推介的初始化建议由本地 X Agent 初筛报告显式导入。

生产同步代码后安装单元并启动：

```bash
sudo cp deploy/odaily-hottopic.service /etc/systemd/system/
sudo systemctl daemon-reload
sudo systemctl enable --now odaily-hottopic.service
sudo systemctl status odaily-hottopic.service
```

首次启动前确认根分区保有至少 5 GB 可用空间；运行中观察 `data/runtime/hottopic.sqlite`、`systemctl status odaily-hottopic.service` 和控制台的抓取异常计数。

正文模型统一为 `gpt-5.6-luna`、`reasoning_effort=none`；请求或结构化输出失败时按相同配置重试同一材料。`HOTTOPIC_MODEL` 和 `HOTTOPIC_FALLBACK_MODEL` 可覆盖模型与重试配置。`HOTTOPIC_OPENAI_BASE_URL`、`HOTTOPIC_OPENAI_API_KEY` 可单独覆盖模块兼容 API；未指定时依次使用通用 `ODAILY_LLM_BASE_URL` 和兼容旧部署的 `X_PROCESS_OPENAI_BASE_URL`。本机 LiteLLM 使用 `LITELLM_MASTER_KEY`，不将外部上游凭据发送给本机代理。

语义复核默认使用 `gpt-5.6-luna`、`reasoning_effort=high`，失败时按 `high` 重试。相关配置为 `HOTTOPIC_CLAIM_REVIEW_ENABLED`、`HOTTOPIC_CLAIM_REVIEW_MODEL`、`HOTTOPIC_CLAIM_REVIEW_FALLBACK_MODEL`、`HOTTOPIC_CLAIM_REVIEW_REASONING_EFFORT`、`HOTTOPIC_CLAIM_REVIEW_OPENAI_BASE_URL`、`HOTTOPIC_CLAIM_REVIEW_OPENAI_API_KEY`、`HOTTOPIC_CLAIM_REVIEW_TIMEOUT_SECONDS`、`HOTTOPIC_CLAIM_REVIEW_BATCH_SIZE` 和 `HOTTOPIC_CLAIM_REVIEW_BACKFILL_LIMIT`。复核请求默认按最多 40 个 claim-topic case 批量发送，每轮维护默认补审最多 120 条历史关系；未配置凭据时只使用机械候选结果，生产数据不会因此停止采集。

主题级粗筛和深审固定使用 `gpt-5.6-luna`、`reasoning_effort=high`；`HOTTOPIC_TOPIC_MERGE_REVIEW_ENABLED` 可禁用，`HOTTOPIC_TOPIC_MERGE_TIMEOUT_SECONDS` 控制单次请求超时（默认 300 秒）。新话题首次完成正文并可见时持久化扫描请求，同批新话题只触发一次全量扫描；另每 4 小时按独立成功时间戳全量扫描，即时扫描不推迟周期。失败保留待办并在 15 分钟后重试。缺少模型配置时记录失败，不自动跨主题合并。

正文证据会过滤与当前资产锚点冲突的其他 ticker；同一资产邻近话题只能补充不带竞争资产的行情背景。写作 Prompt 要求只保留材料中的事实和已归因的观点，不加入编辑者自己的免责声明或结论性提醒，并要求同一行情事实只写一次；当材料包含事件背景、数据变化、社区观点或争议等明显不同的叙事层次时，要求正文分成 2 至 4 个自然段。模型返回后还会去除固定的编辑元话术（包括“并非已兑现”“不构成确定性结论”“这一说法来自市场参与者的解读”等）和完全重复句，但保留“有人猜测”以及明确主体的正常来源归因。

热点读模型同时返回 `firstGeneratedAt` 和 `lastUpdatedAt`：前者取话题首次进入聚合状态的 `first_seen_at`，后者取最近一次被接受的证据时间 `last_evidence_at`；若历史数据缺少后者，则回退到首次生成时间。它们描述话题生命周期，不等同于最近一次正文 AI 调用时间。

## 订阅与保留

账号目录只维护热点话题、市场情绪和项目推介三个订阅开关。任一开关开启时账号进入共享采集调度；全部关闭时停止调度，但既有热点和运行结果按保留策略继续存在。临时内容、未成热点话题、inbox 和短期审计保留 48 小时；运行事件保留 5 天；成为热点的永久档案不清理。

热点话题是否消费某条共享 inbox 由 `hot_topic_enabled` 控制。关闭该开关不会影响同一账号已经打开的市场情绪或项目推介消费；只要三个订阅开关仍有一个打开，账号仍可由共享 worker 采集。具体账号目录契约见 `控制台-X Agent.md`。

## 已接入、待部署的事件自动追踪

热点自动快讯只消费归并后的可见 HotTopic。每个 topic 至多拥有一个 `tracking_event`；追踪层不再按身份词归并其他话题。若两个已有热点后来合并，保留一个追踪事件并终止另一事件的 cycle、账号绑定及未发布任务；历史发布与审计保留。任务 1 的 `track` / `do_not_track` 判断和 GPT Web Search 官方账号发现不改变热点归并规则。

针对明确指定的可见热点，运维可通过 `EventTracker.start_tracking_topic()` 记录带操作者、理由、已确认事实、未确认说法和官方回应预期的人工启动决定。它覆盖该 topic 的自动追踪资格判断，并在主题快照更新后持续有效；重复调用不新建事件。此入口不接受账号 handle，也不绕过后续 GPT Web Search 官方账号核验、容量限制、cycle 生命周期或官方进展的实质性判断。普通热点仍只走自动判断；该入口目前不暴露控制台按钮。

事件追踪使用独立的 `event_tracking_*` 表和 inbox。Web Search 只负责一次性发现官方账号并保存身份引用，后续内容由事件专用账号轮询获取；它只读取已自动核验的官方账号，事件账号不加入 `hottopic_accounts`，事件原帖不回灌 `hottopic_inbox`。发现响应允许模型在 JSON 前后附带说明文字，但必须最终解析为对象；发现失败时保留返回文本、搜索工具调用、引用和错误，便于区分搜索失败、格式失败与无可核验账号。`discovery_failed` 或 `capacity_exhausted` 不会因普通热点刷新自动重新开启 cycle，只有显式重新启动才重试。控制台同时展示事件关联的原始热点，事件标题使用追踪判断返回的事件身份，不直接复用可能包含多个子话题的热点标题。同一 worker 复用 FXTwitter 2 秒 pacer、429 冷却和退避，事件账号优先，最多 15 个全局账号、每个事件最多 3 个账号，目标轮询间隔为 1 分钟。

每条新官方帖必须先判断为 `material_progress`、`relevant_no_progress` 或 `irrelevant`。只有实质进展能通过 durable outbox 创建 `tasks.source = 'event_tracking'`，再走主写作链路的全站查重、写作、格式化和幂等自动发布；其他内容绝不生成快讯候选。完整契约与上线验收见 `docs/讨论与修改日志/热点话题长期追踪升级计划书.md`。

## 写入与性能边界

新 claim 的确定性关系先展示；claim AI 复核每小时在写事务外执行，完成后刷新参与人数和可见性。新热点首次生成正文并可见时请求一次全量主题归并扫描，另每 4 小时独立扫描全部可见热点；两个计时互不干扰。主题模型调用在 SQLite 写事务外进行，应用前重查话题可见性、正文和证据指纹。

SQLite 只有一个写者。主题级和 claim 级模型调用不持有 SQLite 写事务；归并后刷新热度与正文，正文生成亦在写事务外进行。账号订阅开关在短事务中保存，不等待 AI 请求或执行无上限内容删除。X Agent 的市场情绪和项目推介模型调用也在短事务外执行，并用各自的任务消费位与热点处理隔离。历史清理队列仅用于兼容旧库，worker 按小批次恢复执行，异常会保留在队列记录中供下一轮重试。

聚合批次失败时，事务回滚，inbox 内容保持未处理状态，并记录 `aggregate_error` 运行事件；下一次重试前会从 SQLite 重建话题检索缓存，避免缓存引用已回滚的话题而重复触发外键错误。确定性 seed 写入使用幂等插入，以兼容话题已提交但 inbox 标记尚未完成的重试。批次成功提交后才标记 inbox 内容为已处理。
