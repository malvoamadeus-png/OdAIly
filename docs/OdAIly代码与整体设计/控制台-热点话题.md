# 控制台-热点话题

## 边界

`热点话题` 是 OdAIly 控制台的管理员页面。它使用现有本地 Bearer session 和 `/console` 鉴权，数据不进入主 `odaily.sqlite`，也不读取或修改 `x_capture_accounts`。

- 独立数据库：`data/runtime/hottopic.sqlite`。
- 独立 worker：`odaily-hottopic.service`，每 10 分钟轮询处于 `followed` 状态的账号；每次 SQLite 聚合最多处理 100 条 inbox 内容。
- API：`editor-plugin-api-server` 的 `/console/hottopic/dashboard`、`/accounts`、`/topic` 和 `/account`，均要求控制台管理员 session。
- 控制台展示当前热点、参与账号、账号累计内容数、累计参与永久热点数和抓取错误。累计数从本次部署开始，原始内容清理不会让指标归零。

## 话题归并

归并先使用同一 `$` 资产或合约地址等强身份。对没有资产锚点的发布、产品、公司或协议事件，则在 24 小时窗口内要求同时满足：至少两个非泛化命名实体相同、事件动作类别相同、合并后至少有三个独立账号。宽松的词汇召回、普通中文切分词和单一平台名不构成归并身份；两个不同的主要资产也不会走此兜底路径。热点资格评估也使用同一身份：共同出现的一对命名实体可作为参与者锚点，精确相同的合约地址同样可作为强参与者锚点；不能由单一平台名凑足人数，名称相同但合约不同的内容也不会相互计数。这个规则统一处理非资产事件，不维护按项目或产品名称列出的特例。每小时维护会重归并最近 24 小时仍开放的话题，因此规则升级不依赖下一条新内容才生效。

## 首次部署

首次启动 worker 时会创建 `hottopic_meta.deployment_started_at`。它是不可回退的 UTC 水位线：早于该时间的帖子不会进入 inbox、SQLite 或热点归并。禁止复制旧 HotTopic 的 `state.sqlite`、`service.sqlite`、帖子或话题到生产。

`backend/packages/hottopic/initial_accounts.csv` 是一次性最小种子，只包含旧服务最后 48 小时活跃账号的用户名和显示名。`nikkei`、`PolymarketMoney`、`cb_doge`、`TeamTrump`、`skaas777`、`PR0H0S`、`fxtrader`、`Big_Pharmai`、`AcboxLiu`、`notthreadguy` 初始为 `blacklisted`；`hellojintao` 保持 `followed`。

生产同步代码后安装单元并启动：

```bash
sudo cp deploy/odaily-hottopic.service /etc/systemd/system/
sudo systemctl daemon-reload
sudo systemctl enable --now odaily-hottopic.service
sudo systemctl status odaily-hottopic.service
```

首次启动前确认根分区保有至少 5 GB 可用空间；运行中观察 `data/runtime/hottopic.sqlite`、`systemctl status odaily-hottopic.service` 和控制台的抓取异常计数。

正文模型由 worker 的 `HOTTOPIC_MODEL` 指定，生产使用 LiteLLM 业务别名 `odaily-gpt-writer`，不直接使用其底层模型名。`HOTTOPIC_OPENAI_API_KEY` 可单独覆盖模块凭据；当 `X_PROCESS_OPENAI_BASE_URL` 指向本机 LiteLLM 时，模块使用既有 `LITELLM_MASTER_KEY`，不将外部上游凭据发送给本机代理。

## 账号状态与保留

- `followed`：进入调度；控制台新增账号即为此状态。
- `unfollowed`：停止调度但保留累计指标；解除黑名单后落入此状态，必须人工恢复关注。
- `blacklisted`：立即停止调度、清空该账号 inbox，并写入持久化清理队列；worker 每次最多删除 100 条未属于永久热点的临时内容。该操作不在控制台请求内扫描或删除话题图，永久热点 membership 和 `topic_evidence` 继续保留。
- 临时内容、未成热点话题、inbox 和短期审计保留 48 小时；运行事件保留 5 天；成为热点的永久档案不清理。

## 写入与性能边界

SQLite 只有一个写者。话题归并的确定性状态先提交，再发起可能重试的 AI 正文生成；每篇正文完成后立即提交。管理员拉黑、关注和状态更新不得等待 AI 请求，也不得执行无上限的账号内容删除。清理队列在 worker 循环中按小批次恢复执行，异常会保留在队列记录中供下一轮重试。

聚合批次失败时，事务回滚，inbox 内容保持未处理状态，并记录 `aggregate_error` 运行事件；下一次重试前会从 SQLite 重建话题检索缓存，避免缓存引用已回滚的话题而重复触发外键错误。批次成功提交后才标记 inbox 内容为已处理。
