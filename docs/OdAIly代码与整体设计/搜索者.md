# 搜索者

## 搜索阶段

搜索者现在由本地流水线 `local_pipeline` 串联调用，不再作为独立常驻数据库 worker 领取 `tasks`。

### 自动快讯搜索

处理：

- `x`
- `blockbeats` / `panews` / `jinse`
- `non_mainstream_media`
- `ai_source`

统一 Crypto信源全文和 AI信源全文现在也走这条搜索链路，因此 CoinDesk、Cointelegraph、Decrypt、TheElec CHINA、ETNews 会与 X/竞品一起做：

- Odaily 历史查重
- 运行中 candidate 去重

### 标题提醒搜索

处理：

- `external_media_alert`
- `ai_source_alert`
- 历史兼容 `mainstream_media`

它只服务标题提醒链路，不负责新的 Crypto信源或 AI信源全文写作任务。

## 运行交接

- 收集器先写入 `tasks` 作为档案，再提交本地 SQLite job。
- `local_pipeline` 直接按来源调用搜索阶段，搜索结果仍写回 `x_task_pipeline.search_result` 或 `external_media_alert_pipeline.search_result`。
- `tasks.status` 继续保留 `deduped / searched / duplicate / search_failed` 等观察状态，但不再用于多个常驻 worker 之间抢任务。
- 主写作链路中，搜索阶段成功结束时必须写入 `x_task_pipeline.search_completed_at`，供耗时分析拆分“入库到搜索完成”耗时。
- 主写作链路查重运行时以本地 `SearchCache` 热 cache 为准，不在每条任务查重时实时读取主库的 `odaily_reference_items` 或 `search_event_candidates`。
- `local_pipeline` 启动后会后台预热并定时刷新 Odaily 已发布镜像到本地 search cache；刷新失败只记录日志和 heartbeat，不阻塞查重。
- 主写作链路的新 candidate 会先进入本地 search cache，供后续任务查运行中重复；主 SQLite 的 `search_event_candidates / search_event_sources` 保留归档和复盘用途，但不再参与实时查重判定。

## 历史集合

- `odaily_reference_items`
- 本地 search cache
- `external_media_alert_history`

`external_media_alert_history` 现在主要承载 Crypto信源标题提醒和 AI信源标题提醒历史；历史 `mainstream_media` 仍可共用这份窗口。

主写作链路中，`odaily_reference_items` 是主 SQLite 中的 Odaily 已发布镜像，继续供控制台、审核者、编写者3、插件等模块使用。搜索者不在每条查重时直接读取它，而是由本地热 cache 预热线程按 `SEARCH_WINDOW_HOURS` 窗口同步到 `data/processed/searcher/searcher.sqlite`。

Odaily 历史集合以 Odaily 官方快讯 API 为真实来源。`local_pipeline` 的后台预热线程会按窗口调用 Odaily API 拉取最新已发布快讯，并同步刷新本地 search cache；只有 Odaily API 拉取失败时，才回退读取主 SQLite 的 `odaily_reference_items`。主写作链路每条任务查重只读取本地热 cache，不在任务内实时调用 Odaily API 或主 SQLite。

运行中 candidate 由搜索阶段写入本地 search cache，供同一 `local_pipeline` 进程后续任务查重。任务最终失败、过期、丢弃后，本地 candidate 会被释放；任务已直发或挂后台后，candidate 会转为 `recent_processed`，默认保留 24 小时供后续任务查重，再自动过期。主 SQLite candidate 表作为归档和其他模块可见的辅助数据。

## 本地搜索缓存生命周期

`data/processed/searcher/searcher.sqlite` 是可重建的热缓存，不是长期档案库。它同时缓存当前任务查询向量、竞品快讯事件聚合向量、Odaily 已发布参考、标题提醒历史和运行中 candidate；业务档案仍由对应业务表保存。

- 缓存中的 `published_at / created_at / updated_at / expires_at` 新写入统一使用 UTC；窗口筛选、排序和清理使用 SQLite 时间函数，兼容历史 `+08:00` 及 `CURRENT_TIMESTAMP` 空格格式。
- embedding 新写入时以 `1024` 维 float32 BLOB 保存，不再用 JSON 数字数组作为主存储格式；旧 JSON 向量由显式维护命令转换。
- `task / newsflash_item / editor_plugin_query / external_media_alert` 文档默认保留 `2` 天；`recent_processed` 通过自身过期时间默认参与 24 小时查重。
- inactive candidate 默认保留 `2` 天；active candidate 不因定期清理被删除。
- `odaily_reference / external_media_alert_history` 文档和所有 embedding 默认保留 `8` 天，覆盖最长 `168` 小时标题提醒查重窗口并保留一天缓冲。
- `local_pipeline` 每 `6` 小时自动删除过期行，但不自动执行 `VACUUM`，避免长驻服务在运行期获取数据库压缩锁。

相关环境变量：

```text
SEARCH_CACHE_CLEANUP_INTERVAL_SECONDS=21600
SEARCH_CACHE_SHORT_RETENTION_DAYS=2
SEARCH_CACHE_REFERENCE_RETENTION_DAYS=8
SEARCH_RECENT_PROCESSED_SECONDS=86400
```

显式维护命令默认 dry-run：

```powershell
python backend/src/main.py search-cache-maintenance
python backend/src/main.py search-cache-maintenance --execute
python backend/src/main.py search-cache-maintenance --execute --compact
```

`--execute` 删除过期行并把仍需保留的旧 JSON embedding 转成 float32 BLOB。`--compact` 额外执行 WAL checkpoint 和 `VACUUM`，需要至少接近当前数据库体积的临时空闲磁盘；生产执行前应先停止会写 search cache 的服务并确认新数据盘空间。

## 查重流程

`x_processing` 搜索阶段当前只保留三段式查重：

1. 精确重复：
   - 来源链接规范化后完全相同。
   - 标题规范化后完全相同。
   - 运行中 candidate 可按必要场景比较内部 `doc_id`。
2. 向量相似度：
   - 对当前任务、Odaily 历史和运行中 candidate 计算 embedding 相似度。
   - Odaily 历史保留相似度 Top N，运行中及近期 candidate 单独保留相似度 Top N；不使用分词、共享词或关键词召回。
   - 任意候选相似度达到 `SEARCH_DUPLICATE_THRESHOLD` 时直接判为疑似重复。
3. AI 复核：
   - 没有候选达到直接判重阈值，但全部候选中的最高相似度达到 `SEARCH_BATCH_AI_REVIEW_THRESHOLD` 时，把两组 Top N 候选放进同一次搜索者 AI 请求。
   - AI 必须逐一审查全部候选；只要任意候选与新材料属于同一公告、披露或行动，就判为重复。相对某一候选属于新进展，不能覆盖它与另一候选的重复关系。
   - 同一次披露中分别强调购买数量、金额、均价、总持仓、浮盈等补充指标，仍按同一事件处理；同一主体后来发生的新动作、新交易、正式修正或事件后的实质进展才可按新内容放行。
   - AI 返回的重复目标必须存在于本轮 Top N 候选中；系统使用实际候选记录确定目标类型和 candidate ID，避免模型返回错误类型或不存在的目标。

当前默认参数为：

- `SEARCH_BATCH_AI_REVIEW_THRESHOLD = 0.60`：只负责触发主写作链路的整组 AI 复核，不直接判重。
- `SEARCH_ODAILY_REVIEW_LIMIT = 3`：Odaily 历史候选取相似度 Top 3。
- `SEARCH_CANDIDATE_REVIEW_LIMIT = 5`：运行中及 `recent_processed` 候选合并后取相似度 Top 5。

Top N 排序复用已经计算的 embedding，优先由 NumPy 一次完成。AI 复核始终是一组候选共用一次请求，不按候选逐条调用模型。
原有 `SEARCH_AI_REVIEW_THRESHOLD` 继续供插件单候选查重及兼容链路使用，默认 `0.65`；主写作链路的批量复核阈值与它分离，避免调整批量召回时改变竞品事件归并或标题提醒行为。

搜索者 AI 复核使用独立模型配置，不复用判断者模型配置：

- `SEARCH_AI_REVIEW_MODEL`：当前生产使用 `gpt-5.6-luna`，通过新的 GPT 兼容中转接口调用。
- `SEARCH_AI_REVIEW_REASONING_EFFORT`：保留为兼容配置标签，当前生产搜索 AI 复核为不思考模式，实际不发送该参数。
- `SEARCH_AI_REVIEW_OPENAI_BASE_URL` / `SEARCH_AI_REVIEW_OPENAI_API_STYLE` / `SEARCH_AI_REVIEW_OPENAI_API_KEY`：搜索 AI 复核可独立覆盖兼容接口配置；为空时继承主处理配置。key 只保存在本机或服务器 `.env`，不写入仓库。
- `SEARCH_AI_REVIEW_OMIT_REASONING_EFFORT`：当前生产为 `true`，搜索 AI 复核不发送 reasoning 参数。
- `X_PROCESS_REQUEST_TIMEOUT_SECONDS`：搜索 AI 复核客户端默认超时为 `90` 秒；该值也供主处理链路的通用外部请求使用。
- `SEARCH_AI_REVIEW_OMIT_RESPONSE_FORMAT`：当前生产新 GPT 接口为 `true`，省略 Chat Completions 的 `response_format` 参数，依靠 Prompt 中追加的 JSON Schema 约束输出；支持该参数的接口可保持为 `false`。
- `SEARCH_AI_REVIEW_CHAT_RESPONSE_FORMAT_MODE`：`chat_completions` 下的 JSON 输出模式；当前使用 `json_object`。
- `SEARCH_AI_REVIEW_APPEND_JSON_SCHEMA_TO_PROMPT`：当前保持开启，把 JSON Schema 约束追加到 prompt。

生产中搜索 AI 复核固定走 `gpt-5.6-luna` + 不思考模式；Chrome 插件 `AI查重` 复用这一配置。写作、发布和插件生成继续走原有 GPT 模型配置。

搜索或 AI 复核失败时，任务的 `last_error` 会保留模型、端点、客户端超时和上游 HTTP 状态（若有）；控制台任务详情会将其区分为额度不足、上游 5xx、AI 请求超时、embedding 超时、鉴权失败或输出解析失败等故障代码。

`x_task_pipeline.search_result` 会保留本轮全部 Top N 候选的目标类型、目标 ID、标题和相似度，以及 AI 复核的原始输出（如果本轮做过 AI 复核），便于复盘模型实际审查了哪些对象。重复命中运行中或 `recent_processed` candidate 时，任务作为 supporting source 链接到对应 `search_event_candidates` 事件候选，不再因为 candidate 已发布而丢失归并关系。

当前不再使用“共享词 / 词面规则”直接判重。也就是说，除精确重复外，所有非精确候选都必须先经过向量相似度筛选；只有进入阈值区间的候选才可能交给 AI 复核。

向量相似度计算仍保持现有语义：对当前任务向量与候选文档向量计算 cosine similarity，并按相似度选取各集合 Top N。实现上优先使用 NumPy 批量计算和排序，以减少 Python 循环开销；如果运行环境没有安装 NumPy，会自动回退到逐条计算和排序逻辑，不改变查重结果和失败边界。

主写作链路的 `search_result` 会记录 `cache_source = local_hot_cache`、本地 Odaily 参考数、active candidate 数和搜索耗时，方便复盘确认查重是否命中本地热 cache。

`快讯生成` 插件的 `AI查重` 轻接口复用同一套查重边界：

- 精确重复
- 向量相似度
- 必要时 AI 复核

插件不会额外启用独立的共享词规则或前端判断。
