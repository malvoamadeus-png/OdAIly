# 完整程序架构

## 发布后事实与文本审查契约

- 文本审查者是原中文质量审核者的对外名称，保留 `auditor` 包、表、命令、服务与插件 feed 技术标识；只检查文本质量。细节见 `审核者.md`。
- 事实审查者与文本审查者平级，从 Odaily 已发布镜像异步扫描，围绕交易决策与名誉风险筛选比对价值，先执行轻量原文对照，再仅对仍成立的具体编辑疑点联网取证；忠实转述不重新审计来源，原文不可用或材料不对应不扩散搜索；不插入或更改发布主链路，不修改、撤回或重发快讯。补充建议与事实问题分离，不改变判定状态或触发外部搜索。独立结果以稿件版本留痕，当前模型固定 `gpt-6-luna`。细节见 `事实审查者.md`。
- 快讯及数据总览是事实审查的完整查看入口，展示不查理由、豁免、各阶段结论、证据、失败与历史版本；最终状态为 `flagged` 的结果同时写入插件高频区，摘要从分段审查结果中提取精简疑点。系统级展示契约见 `控制台-快讯及数据总览.md` 与 `事实审查者.md`。
- OdAIly 的 `快讯及数据总览 / 快讯总览` 只读展示产出来源、出口品类、事件重要性优先级、当前版本文本审查、事实审查、已有查重结果及阅读状态。来源、出口品类、优先级和查重快照写入主 SQLite，并以 Push API 返回的 Odaily 快讯 ID 精确关联；出口品类独立于 `origin_key`。文本审查按当前标题和正文版本读取。插件在 Alt 阅读层成功显示正文或点击标题展开正文后，将按用户和正文版本记录本地阅读状态；该状态通过受令牌保护的只读 `GET /integration/newsflashes` 输出，尚不接收官方后台回传。OdAIly 控制台暂不读取插件阅读状态，仍显示“未同步”。字段展示和状态细节见 `控制台-快讯及数据总览.md`、`信息流插件.md` 与 `官方后台快讯补充数据拉取接口.md`。
- Odaily 官方后台审核工作台与公开首页 Meme 速递版面是独立的后续项目。本仓库不主动连接或操作 Odaily 官方后台；目前仅提供官方后台可拉取的只读接口，官方后台工作台与公开首页版面仍待后续实施。设计说明见 `docs/讨论与修改日志/新后台与新版面计划.md`。

## OdAIly 与 Odaily 官方后台同步契约

- Odaily 官方快讯 ID 是跨系统唯一键；官方后台持有标题、正文、操作人和浏览量的权威数据。当前 OdAIly 只提供补充审核元数据的出站拉取接口；从官方接口读取操作人与浏览量尚未实现。
- OdAIly 出口品类为 `人工`、`AI常规`、`商务`、`行情`、`Meme速递`、`热点自动快讯`、`定时简报`。当前演示把 AI常规与商务合并展示和统计，但这不约束官方后台如何组织页面；接口字段必须保持独立品类值，来源/工作流字段不能替代品类。
- OdAIly 只向官方后台传审阅优先级等级，不传理由；文本审查者传插件可见的完整反馈；事实审查者传插件使用的审查短文本和 OdAIly 详情 URL；查重字段先预留为空或短文本/URL，不外发覆盖不完整的现有结果。
- 审核事件计划包括 Alt 展开放大正文、文本审查接受/拒绝、点击事实审查链接跳转。插件正文阅读目前先写入 OdAIly 本地；事件同步到官方后台、官方后台事件回传 OdAIly、按事件唯一号幂等存储与失败重试均未实现。
- 本地出口字段和只读拉取接口已实现；配置 `NEWSFLASH_EXPORT_API_TOKEN` 后可按 `limit/offset` 拉取已按官方 ID 关联的快讯与 OdAIly 审查补充数据。接口不接收官方后台请求、不修改官方后台，也不包含官方操作人或浏览量回传。字段与请求细节见 `官方后台快讯补充数据拉取接口.md`；品类映射及演示工作台设计见 `docs/讨论与修改日志/新后台与新版面计划.md`。

## 主存储切换契约

- 新版本唯一允许 `ODAILY_STORAGE_BACKEND=sqlite`；主库路径由 `ODAILY_SQLITE_PATH` 指定，默认 `data/database/odaily.sqlite`。
- `ODAILY_STORAGE_EPOCH` 是一次切换的存储世代。队列只领取当前世代任务，跨世代的 `(source, source_item_id)` 唯一记录继续充当去重账本。
- 回切依赖切换前的旧 commit、旧环境文件和冻结 Supabase 数据；SQLite 时期新增数据允许放弃，因此不做持续双写。新版本本身不能通过环境变量切回 Postgres。
- SQLite 文件、`-wal` 与 `-shm` 必须位于同一台 Linux 主机的本地磁盘。在线备份使用 SQLite backup API 或停服后的完整文件副本，不能只复制主文件而遗漏未 checkpoint 的 WAL。
- 全部业务仓储、网页和插件已经切为本地 SQLite；一次性导入与生产切换步骤见迁移文档。
- 可比较的业务时刻统一以 UTC 写入 SQLite；外部来源携带的 `+08:00` 等偏移必须在仓储边界转换为 `+00:00`。历史混合格式参与窗口筛选或排序时必须使用 SQLite 时间函数解析，不能直接按 TEXT 字典序比较。面向编辑、Prompt 和控制台展示时再转换为北京时间。
- 迁移状态、磁盘门槛、清理和回切步骤见 `SQLite主存储迁移.md`。

## 生产服务器边界

- HideOnBush 的 FOMO 浏览器采集可通过受限 SSH 单次入口在官方节点执行，复用 Meme scanner 的浏览器锁和登录 profile；只回传 Trending/Thesis JSON，不参与 OdAIly 产品数据库或发布流程。契约见 `FOMO单次远程采集.md`。

- `Odaily 官方服务器` 是 OdAIly 唯一活动生产节点，承载 `/opt/OdAIly`、本地 SQLite、所有生产 worker、监督者、LiteLLM 和 `api.odaily.uk` HTTPS 入口。
- `原共享服务器` 只保留其他项目；迁移完成后不得运行 OdAIly 的 API、worker、定时任务、Telegram session 或 SQLite 写入。
- 两台服务器之间不做持续双写。迁移窗口内先冻结两边写入，再以旧生产节点的最终一致快照为主源，把官方服务器恢复为单写入节点。
- Vercel 前端和 Chrome 插件只通过 `https://api.odaily.uk` 访问官方服务器；浏览器不连接数据库，旧公网 API 地址不再作为生产兜底。
- 当前 X Agent 是控制台上的上层业务框架，包含平级的热点话题、热点自动快讯、市场情绪、项目推介和投资线索。五项业务复用 `data/runtime/hottopic.sqlite` 与 `odaily-hottopic.service` 的单次 X 采集，但保留独立消费数据；投资线索另由 `odaily-investment-leads.service` 批量扫描和推导。热点自动快讯仅通过其 durable outbox 写入主 `odaily.sqlite` 的 `event_tracking` 任务；其他 X Agent 业务不读取或修改主 `odaily.sqlite`、`x_capture_accounts`、`tasks`、`write_flow` 或发布队列。每个目录账号维护热点话题、市场情绪、项目推介、投资线索四个订阅开关；升级时一次性启用既有目录账号，新账号默认开启热点话题和投资线索，人工开关不会被模型改写。
- 热点话题先由本地索引按 `$` 资产、明确裸 ticker、合约和文本特征召回候选。确定性强匹配保持快速路径；只有弱硬关联、临界分数或相近候选才按新帖打包，最多带 5 个本地候选话题交给 `gpt-6-luna`、`reasoning_effort=none` 在 attach 前选择已有话题或新话题组，每批最多 8 条待判新帖，不遍历全部话题对。候选请求在 SQLite 写事务外执行，应用前复核候选快照；状态变化时沿用确定性结果。模型不可用时沿用确定性结果。attach 后的 claim 语义复核仍按小时有界运行，使用 `gpt-6-luna` 高思考等级复核为 `support/context/unrelated`；只有 `support` 进入参与人数和热度，`context` 只可作为背景，`unrelated` 不进入正文。有明确资产身份的话题不能仅凭 Binance、钱包等泛化共同实体并入无资产事件。正文生成会排除证据中的竞争资产，并禁止编辑者免责声明和重复行情句；细节见 `控制台-热点话题.md`。
- 同一 X 帖子在 X Agent inbox 中只保存一次。热点话题使用自己的 `processed_at` 消费位；市场情绪和项目推介各自使用幂等分析任务；投资线索把原帖、引用、转发及回复上下文保存到独立材料表，再由独立队列处理，不等待模型调用完成后才继续共享采集。扫描和推导只消费仍有启用账号观察的材料，账号关闭时取消未开始任务，运行中在落库前复核资格。新热点首次完成正文并可见时请求一次全量可见热点归并扫描，另每 4 小时独立全量扫描；隐藏 seed 和已归档话题不进入主题归并。粗筛和证据深审均使用 `gpt-6-luna`、`reasoning_effort=high`，仅明确可合为一篇准确综合报道时归并。自动快讯追踪只消费归并后的热点。正文、情绪和推介均使用 `gpt-6-luna`、`reasoning_effort=none`，失败时按原思考等级重试。投资线索使用两阶段批处理、独立重试和每日用量限制，可对核心材料不完整的候选做有界外链补充读取，并对缺少代码的具体资产执行独立限额的身份浅搜索；所有来源和推导仅供人工调研，不核查真假、不生成买卖建议，也不进入快讯或交易流程。失败、预算暂停、待补充材料和无候选分开统计。市场情绪以独立账号的原帖均分生成当前 `-100` 至 `+100` 汇总分数，并由 `odaily-hottopic.service` 每 12 小时持久化一份滚动 12 小时快照供控制台曲线读取；市场情绪和项目推介绝不发快讯。细节见 `控制台-X Agent.md`、`控制台-X Agent-投资线索.md`、`控制台-热点话题.md` 与 `docs/讨论与修改日志/X Agent升级总计划书.md`。
- X Agent“昨夜热议”由同一 HotTopic worker 每天北京时间 08:30 后从当天首次出现的可见热点中按参与热度选择事件型候选，经编写者2格式整理后用 `isPublish=false`、`isPush=false` 挂后台；按本地日期和 topic ID 幂等，不经过统一发布流水线。细节见 `控制台-X Agent.md`。
- 自动快讯追踪允许对明确指定的热点记录一次带审计的人工启动决定，只覆盖该 topic 的追踪资格判断；后续 X 账号先由 Web Search 找候选，再基于 FXTwitter 简介和最多 4 条最新原创帖由 AI 判断是否为事件主体或直接涉事者。接口与生命周期细节见 `控制台-热点话题.md`。

## 热点自动快讯契约

- 热点自动快讯是上述“X Agent 不进入主发布链路”规则的唯一受控例外，已在官方服务器运行。它不把事件账号加入人工 X 信源，也不复用 `hottopic_accounts`、`hottopic_inbox` 或普通 X 帖子的发布资格。
- 自动追踪事件首次创建时可通过插件本地 feed 生成一次 `热点自动快讯新增：{事件标题}` 提醒；提醒以事件 ID 幂等，并链接到控制台处理入口，不改变事件自动追踪和发布契约。
- 事件运行数据仍留在 `data/runtime/hottopic.sqlite` 的独立 `event_tracking_*` 表。GPT Web Search 只负责返回符合 X handle 格式的候选，不要求搜索引用或官网链接。程序通过 FXTwitter 读取账号简介和最多 4 条原创帖，再由 AI 判断账号是否代表事件主体/处置主体或直接涉事者；媒体、研究员、KOL、社区、行情/链上观察和其他转述账号不追踪。身份判断以账号简介和近期原创帖的整体内容为依据，不要求 AI 提供可逐字匹配的身份引用或外部身份证明。FXTwitter 或身份模型暂时失败时保留候选并重试，不重复搜索；只有身份判断通过的绑定才允许轮询、帖子分析和投递。工具调用、引用、账号资料、身份结论和失败仍保留作审计。
- 身份判断通过的事件主体/直接涉事者账号新帖先写事件专用 inbox，只有 GPT 判定为该事件的 `material_progress` 才通过 durable outbox 创建主库 `tasks.source = 'event_tracking'`。该任务直接从全站搜索者开始，复用查重、写作和格式化；无关、重复或无实质进展的帖子不跨库。事件详情关联主库任务和 `x_task_pipeline`，展示身份判断、FXTwitter 资料、pending/submitted/cancelled/duplicate/published/failed、生成阶段、草稿或终稿标题正文、发布决定、时间和原帖链接。
- 事件到主写作链路的契约包含账号作者信息、AI 的账号身份判断和本次进展上下文；写作按事件主体/涉事者账号归属，但不把 AI 判断说成外部认证，帖子主张仍须归属并由人工审核；编写者2只做确定性格式化。具体输入、Prompt 覆盖及失败重试规则见 `编写者1.md`。
- `event_tracking` 发布分支在全站查重通过后使用通用人工审核路径，以 `isPublish=false` 挂入编辑后台，任务状态为 `ready_review`；人工审核后再决定发布。任务 1 的 `track` / `do_not_track`、账号候选发现和静默结束不设置人工确认状态。实现细节见 `docs/讨论与修改日志/热点话题长期追踪升级计划书.md`。
- 发布者输出的审阅优先级只按已定稿标题和正文表达的事件重要性评定，与直发/挂后台决定独立；规则跳过发布者模型时，在推送成功后单独评估。优先级失败不改变发布结果。热点自动快讯复用现有写稿调用输出优先级；行情、Meme、定时简报和人工发布不适用。模块约束见 `发布者.md` 与 `控制台-热点话题.md`。
- 控制台可通过 `/console/auto-newsflash/dismiss` 人工忽略事件。忽略记录按 `event_id` 和事件身份持久化，结束 cycle、释放绑定、取消尚未发布的 outbox，并把未完成的主库任务标记为 `event_tracking_cancelled`；搜索、写作、格式化和发布阶段均在完成写入前检查，最终推送前再次检查。事件从默认 dashboard 隐藏，但候选账号帖子、审计和已进入后台或已发布的快讯保留。

## 当前有效主链路

所有收集入口在创建 `tasks` 前统一应用 `source_exclusion_rule_groups`。收集路径为 `x / competitor / crypto_source / ai_source / mixed_source / jin10`，事实审核者另用独立的 `fact_auditor` 路径；所有路径采用 Unicode NFKC、大小写不敏感、任一词子串匹配，并通过 `match_target` 选择 `title`（仅标题类文本）或 `all`（标题、摘要与正文）范围，URL 不参与匹配。事实审核者初次初始化时从竞品路径复制当前规则，之后独立维护。混合信源先检查 `mixed_source`，分类后再检查目标路径；收集路径命中后只把来源项目标记为已处理，不创建任务、不保留标题、审计、历史或计数。

`MAGNE.AI` 同时作为竞品源头默认排除词和发布者硬拦截词：竞品标题或正文命中时不创建任务；已进入发布阶段的任意任务若原始标题、原始正文、最终标题或最终正文命中，则以 `hard_blocked_term` 挂后台，推送接口调用保持 `isPublish = false`。

- `X`：`x_capture` 入库后提交本地流水线 `write_flow` job；收集者-X 会在写入任务正文前把 FXTwitter 可能返回的 Solana/EVM CA 代币别名通过 GMGN 解析为 symbol（Solana 直查，EVM 按 Robinhood、BSC、Base、ETH 主网顺序兜底），解析失败时保留原文；当前帖的 X Article 与外层帖子合并进入 `tasks.content`，引用或回复形成的前序链逐层追溯并单独存入 `tasks.metadata.context_chain`，供编写者1补全主体和背景，当前帖仍决定判断、查重及核心播报，前序抓取失败继续现有发布流程；`content_format` 为 `x_post_with_article / x_article` 时，编写者1按同一条来源的专项规则输出 2–4 句、1–2 段快讯，完整 Article 只作为事实和审计材料；标记为 `AI信源` 的 X 账号走 `judge_ai -> search -> write -> format_publish -> publish`，其他 X 走 `judge_crypto -> search -> write -> format_publish -> publish`
- `币安广场`：实验性 collector 只在数据库总开关和独立 systemd 服务同时启用时轮询配置账号；首次只建立最新 20 条基线，后续写入 `tasks.source = 'binance_square'` 并执行 `judge_crypto -> search -> write -> format_publish -> publish`，发布阶段固定挂后台
- `竞品快讯`：`competitor_monitor` 入库后提交本地流水线 `write_flow` job，执行 `search -> judge_crypto -> write -> format_publish -> publish`
- 未命中竞品事件排除规则的竞品与 Odaily 快讯由后端写入 `newsflash_events` / `newsflash_event_sources` 做事件聚合和来源归属；`快讯及数据总览` 通过二级页提供事件与首发复盘，不恢复已废弃的收藏和备注契约。
- 竞品来源的首发比较统一使用系统归一后的发布时间；PANews 在原始发布时间基础上固定顺延 1 分钟，以抵消其可能回改发布时间造成的首发偏差。原始值仅保留在 `raw_payload`。
- 事件归属的业务口径是“同一报道”而非宽泛主题：同一规范化原始 URL 可直接归并，标题+正文 embedding 达到 `0.88` 直接归并，中间区间才进入只返回布尔值的 AI 复核；现有事件以代表来源为稳定锚点，禁止组内链式扩张。实现和 Prompt 细节见 `收集者-竞品.md`。

- SQLite 主库保存原始记录、阶段结果、最终结果和失败原因；生产主链路通过本地 job 推进，`tasks` 与阶段表作为持久化事实和恢复依据。
- 搜索者查重使用的 Odaily 已发布快讯历史以 Odaily 官方快讯 API 为真实来源；`odaily_reference_items` 保存于主 SQLite，作为本地历史与 API 不可用时的兜底读取源。
- 本地 job 唯一键统一为 `source + source_item_id`，重复来源内容不会重复进入本地队列。
- `local_pipeline` 执行每个处理阶段前，必须按 `task_id + stage` 通过 `tasks` 行锁原子领取任务；即使旧分阶段 worker 被误启动，同一任务同一阶段也只能由一个执行器进入，未领取到的本地 job 退避重试。
- `local_pipeline_jobs` 的一次执行也计入尝试次数；`LOCAL_PIPELINE_MAX_ATTEMPTS` 默认是 `3`。第 3 次仍失败时，队列 job 进入 `exhausted`，不再自动重试；该状态只属于本地队列，不会删除或改写业务 `tasks` 状态。
- 控制台任务详情通过认证的 `/console/failure-diagnostics/get` 按 `task_id` 懒加载失败诊断；后端把业务任务状态、来源对应的阶段错误、本地 job 重试状态和 `local_pipeline` 心跳聚合为值班人员可转交的诊断摘要。失败分类与监督者告警共用同一套代码，`exhausted` 只表示队列重试耗尽，不代表根因。
- 主写作链路查重以服务器本地 `SearchCache` 热 cache 为实时判定来源；查重范围包括 Odaily 历史、运行中 candidate 和默认保留 24 小时的 `recent_processed`。向量召回分别取 Odaily 历史 Top 3 与 candidate Top 5；任意候选相似度达到 `0.88` 时直接判重，否则最高相似度达到 `0.60` 时把整组候选交给一次 AI 裁决，仅在候选已覆盖新材料核心事实时拦截。同一事件的新重大事实允许发布；`odaily_reference_items` 与 `search_event_candidates / search_event_sources` 写入主 SQLite 供归档、控制台、插件和复盘使用。
- 判定重复的 `x_task_pipeline.search_result` 同时保存 `duplicate_target` 对象快照，供信息周期监控说明命中的具体已发布快讯或候选；快照缺失只对历史任务兼容显示，不改变查重状态。
- `SearchCache` 是有界、可重建的运行缓存，不是永久档案：业务文档按 `2 / 8` 天窗口清理，embedding 使用 float32 BLOB；长驻服务只删除过期行，物理压缩由显式维护命令执行。具体生命周期见 `搜索者.md`。
- 所有生产链路写入 `tasks.content`、`odaily_reference_items.content`、`newsflash_items.content`、插件 `post_text` 以及编写阶段正文时，统一保留有效段落内容，但会移除空白段落；多段正文只使用单个 `\n` 作为段间分隔，不保留空行。通用 `PushClient` 调用 Odaily 发布接口时才把每个非空行转换为一个 `<p>` 段落，内部存储仍保持纯文本。
- `tasks.source_url` 表示可透出的原文链接，而不是采集站内详情页。竞品链路中 `blockbeats` 和 `jinse` 只有拿到外部原文链接时才写入；发布者调用 Odaily 发布 API 时才将其作为 `sourceUrl` 传递。律动、金色财经等竞品站内页不作为 `sourceUrl` 对外发布。
- 为满足阶段耗时分析需求，主写作链路需要把各阶段完成时间持久化到 `x_task_pipeline`。当前系统级阶段时间戳包括：`judge_completed_at`、`search_completed_at`、`write_completed_at`、`format_completed_at`、`publisher_decided_at`、`publish_completed_at`。分析时应优先使用这些显式时间戳，而不是仅靠 `tasks.updated_at` 或结果表创建时间反推。
- `耗时看板` 复用这些阶段时间戳做聚合分析，不引入新的任务状态或 worker 交接边界；V1 只覆盖主写作链路，不纳入标题提醒链路 `external_media_alert_pipeline`。

## SQLite 本地主存储架构

- 采集、处理、审核、巨鲸、Writer3、监督和维护全部读写 Linux 主 SQLite。
- 插件信息流由本地 feed store 提供；普通控制台业务表由认证后的 `/console/data` 接口访问主 SQLite，快讯运营跨表查询与写入使用专用 `/console/newsflash-operations`。
- 常驻服务没有 Supabase/Postgres 回退、异步归档或双写路径。
- 详细边界见 `SQLite本地主存储架构.md`。

  - `write_flow` -> `tasks.source = 'ai_source'`

## 运行面

- 本地流水线：
  - `local_pipeline`
  - HTTP 入口默认 `127.0.0.1:8776`
  - 本地 SQLite 队列位于 `data/runtime/local_pipeline.sqlite`
  - 同一主机只允许一个 `local_pipeline` 进程持有 `data/runtime/local_pipeline.lock` 文件锁；旧实例未完全退出时，新实例拒绝启动，避免两个 worker 并发领取同一任务。锁文件是运行资产，进程退出后文件残留不代表仍有锁。
  - 服务启动时先由 `LocalPipelineProcessor.init_remote_schema()` 幂等初始化主 SQLite schema，并 seed 代码内置的 Prompt 模板（包括 `msx_notice_writer`），成功后才启动搜索缓存预热和队列 worker；已有 active Prompt 内容不会被启动 seed 覆盖。
  - 服务启动时会把锁定超过 `30` 分钟的本地 `running` job 回收到可重试状态；已达到最大尝试次数的 job 直接进入 `exhausted`，避免历史僵尸 job 永久卡住队列表现
  - job 执行中如果某个业务阶段失败，SQLite job 进入退避重试；下一次领取会从 `judge_failed / domain_failed / search_failed / write_failed / format_failed / publisher_failed / notify_failed` 对应的失败阶段继续，而不是把业务失败状态当成已完成。失败阶段只能回到对应阶段领取，真正被其他 worker 锁住时才报告占用冲突。
  - `local-pipeline-exhaust` 默认只列出当前 storage epoch 中已超过尝试上限的 `failed/running` job；传入 `--execute` 才会将它们标为 `exhausted`。该命令不删除或修改业务任务。
- 常驻 worker 的单轮外围异常应被捕获并进入下一轮，避免一次配置读取、任务领取、外部 API 或数据库短暂波动导致进程永久退出；真正的异常由 heartbeat、失败状态和监督者 Telegram 告警暴露

  - 只读控制台由 `/console/stock-market/get` 提供，不接入主快讯任务状态机或插件信息流
- 独立 Meme 速递：
  - `meme_scanner` 承载发现、价格适配、任务状态机、Telegram CA 监听和叙事发布
  - 叙事管线在 OdAIly 本地以链加精确 CA 并行收集 FxTwitter、Telegram 与 FOMO Thesis，并保留版本化规范化材料和诊断；FOMO 只在任务触发时短暂打开独立 profile 的浏览器，和 OKX 发现串行运行
  - OdAIly 使用 `gpt-6-luna` 完成分类、写作和确定性校验，通过Grok Bot Routine补充调研，不调用Grok X Search或GMGN叙事
  - 独立 SQLite 位于 `data/processed/meme_scanner.sqlite3`
  - systemd 服务为 `odaily-meme-scanner.service` 与 `odaily-meme-tg-watcher.service`
  - 稿件固定以 `isPublish=false,isPush=false` 进入后台，不进入 `tasks` 主状态机
  - 挂后台成功后直接写入插件本地 feed store，类型为 `meme_digest`
  - `jobs` 持久化首次领取、发布开始和终态完成时间；叙事 JSON 持久化各调用耗时，控制台据此还原排队、叙事、发布和总耗时
- `non_mainstream_media_telegram` 只负责 Telegram-first 发现入口，不替代原 `non_mainstream_media` 站点直抓 worker；两者并行运行。
- 商务快讯追踪由独立 Telegram Bot API 长轮询 worker 接收多个已启用客户群的消息，首版生产只启用 Soso；其他发现群默认停用。worker 仅收件 `text` 或媒体 `caption`，媒体本身不下载、保存或分析，无文字的媒体更新不写收件箱；之后由有界处理 worker 执行 15 字硬筛、Writer4 AI 分类与脱水、编写者2格式整理、Push API 挂后台及插件单行提醒。分类明确区分快讯、活动、长内容、其他和不确定，并有用户案例判定表。活动只保留为待接 API，失败丢弃，不进入旧 `write_flow` 队列。多群共用一个 token 级接收器，不按群轮询。控制台以 `商务快讯` 一级标签展示处理结果并维护群映射。细节见 `商务快讯追踪文档.md` 与 `控制台-商务快讯.md`。
- 旧分阶段 worker 命令不属于生产 systemd；灾难回滚通过恢复完整旧 commit 完成。
- 收集器提交本地流水线失败时，不把来源 item 标记为已看，下一轮继续重试。
- 切换前未完成旧任务由 `local-pipeline-skip-legacy --execute` 标记为 `legacy_skipped`，不导入本地队列，也不继续补跑。
- 新版本不使用数据库 `LISTEN` 做阶段交接。

## 控制台访问契约

- 控制台是 Vite 前端，全部请求通过 HTTPS 后端访问本地 SQLite 或本地配置文件，不直连数据库。
- 控制台与插件共用本地单操作者邮箱密码和不透明 Bearer session。
- `/console/data` 只暴露固定表白名单、固定过滤操作和安全标识符。
- `/console/newsflash-operations` 只暴露快讯分页、人工字段、花名册、排班、自然周归属、统计、优质快讯、贡献周评分、贡献月度聚合和事件查询动作；浏览器不提交 SQL。优质快讯通过单一 `quality` action 集中完成周门槛、班次归属、首发、信源和排除词组判定，贡献快讯周评分通过 `contributions` action、月度聚合通过 `contributions_month` action 集中完成 A、区间、封顶、奖励及常规信源 / 竞品首发归零判定，前端不复制业务判定；首发单位人工覆盖写入运营事实并审计，事件来源链接由后端返回媒体详情 URL 与外部原文 URL 的分离字段。
- 发布者规则配置由 `editor-plugin-api-server` 暴露 `/console/publisher-rules/get` 与 `/console/publisher-rules/save`，但权限使用 `console_admins` 白名单，不使用插件白名单。
- 发布者规则运行时读取服务器本地 `data/config/publisher_rules.json`，主 SQLite 保存配置快照。
- 发布者控制台通过服务器接口读写规则；接口失败时明确报错，不回退远程数据库。
- `耗时看板` 通过 `/console/pipeline-timing/get` 读取 `data/runtime/pipeline_timing.sqlite` 聚合快照。
- `Gate行情播报` 通过 `/console/gate-market/get` 只读 `data/runtime/gate_market.sqlite`。
- `Meme速递` 通过 `/console/meme/get` 只读 OdAIly 自己的 `data/processed/meme_scanner.sqlite3`；路径可由 `MEME_SCANNER_DB_PATH` 覆盖。接口返回任务实际链值，前端据此生成对应 Dexscreener 链接；写入方是 `odaily-meme-scanner.service` 与 `odaily-meme-tg-watcher.service`，控制台本身不推进任务。
- `AI查重` 复用插件已有的 `POST /plugin/news-gen/search`，控制台只提交编辑粘贴的正文并展示搜索者结论和候选，不创建正式任务、不改变主流水线状态。
- Meme 叙事审计复用 `jobs.narrative_json`，叙事流程必须区分成功、空材料和阶段异常；阶段异常进入叙事重试，不得被归类为 `no_usable_narrative`。`/console/meme/get` 只返回摘要，`/console/meme/detail?id=<job_id>` 返回单条完整审计材料，旧任务缺少审计 JSON 时保持兼容并返回不可用标记。
- `Prompt及规则管理` 页面承载 `可编辑 Prompt / 内置规则 / 知名人物` 三类配置视图。代码内置 Prompt、Schema、标题策略、当前知名人物名单、确定性替换和发布者默认规则由认证接口 `GET /console/runtime-rules/get` 返回；知名人物名单由 `/console/known-title-subjects/get` 与 `/console/known-title-subjects/save` 维护，保存到 Linux 本地 `data/config/known_title_subjects.json`，不轮询数据库，不保存逐人标题情景或复杂 JSON。已有 active Prompt 的规则变更通过显式版本迁移命令发布；`x-process-publish-prompt-version --template-key x_regular_writer` 保留当前内容、创建新版本并切换 active，重复执行幂等。
- `信息周期监控` 将全部受支持来源作为一个查询范围，按可解析的 `tasks.created_at` 倒序分页，并以 `tasks.id` 作为稳定次序；从 `x_task_pipeline.writer_output.trace` 读取任务级标题策略溯源，并显示 writer Prompt、模型、特色模式配置与实际采用状态；历史任务不回填，统一显示“旧任务无标题溯源”。
- `信源管理 / 律动key` 子页通过 `/console/blockbeats-key/get` 与 `/console/blockbeats-key/save` 维护服务器本地 `data/config/blockbeats_key.json`；收集者-竞品 worker 默认在无 key 或额度不足时自动申请、替换并只重试一次，人工保存仍可覆盖当前 key。
- 发布者自动发布是否开启，仅由规则文件中的 `regular.enabled` / `ai_source.enabled` 决定；`tasks.source = 'ai_source'` 和 `tasks.source = 'x'` 且 `tasks.metadata.x_account_is_ai_source = true` 都使用 `ai_source` 发布者规则块。旧 `publisher_settings.enabled`、`publisher_channels.enabled` 和北京时间窗不再参与运行时判定。
- 后端 worker 通过 `ODAILY_SQLITE_PATH` 访问本地主库，不依赖控制台登录态。
- 快讯运营事实以 Odaily `source_item_id` 为稳定键；来源字段同步不得覆盖已锁定的人工发布人，贡献、优质快讯人工覆盖、排班和周归属修改写审计。优质快讯规则以自然周为键冻结监控账号、媒体域名、排除词组和计分参数；新上线的固定系统排除词组会按稳定键补入既有快照，不覆盖原有组，浏览量及运营事实实时重算；排班人员颜色由前端稳定键生成，不进入存储契约。模块细节见 `控制台-快讯及数据总览.md`。

## X 发言人命名契约

- `x_capture_accounts` 除抓取账号本身的配置外，还承载账号级 `写作名` 配置和插件展示用 `AI信源` 标记。
- `写作名` 的作用仅限于 X 发稿口径标准化，不改动原始抓取到的 `author_display_name`、`author_username` 和正文。
- `is_ai_source` 不改变 `tasks.source = 'x'`，但会让自动化主链路进入 `judge_ai`；保留后仍作为 X 常规快讯写作，发布阶段按 `AI信源` 发布者规则块处理。当前 `AI信源` 发布者关闭，因此这类任务不会调用发布者模型，会直接挂后台。
- 标记账号的新快讯在 Chrome 插件信息流中进入 AI区。
- 自动化 X 主链路与插件 `快讯生成` 共用同一套 X 发言人命名规则，不各自维护映射。
- 进入 `编写者1` 前，X 来源作者名按以下顺序计算 `effective_author_name`：
  - 优先使用账号配置里的 `写作名`
  - 没有 `写作名` 时回退到原始 `author_display_name`
  - 仍为空时回退到 `author_username`
- 常规模板里“{发言人}在X平台发文表示”中的 `{发言人}`，以及其他依赖 X 发言人名称的写作场景，统一使用 `effective_author_name`。

## 插件契约

- 插件是独立 Chrome 插件，不属于控制台；代码位于仓库根目录 `extension/`，当前以 unpacked extension 方式加载。
- 插件当前规划两个一级模块：`信息流` 与 `快讯生成`。
- `信息流` 消费现有业务上游结果，不新增新的抓取或审核来源；正常业务消息以插件展示为主，Telegram 只保留系统级错误、宕机、积压和程序异常告警。
- `信息流` 当前聚合内容包括：`新快讯`、`Crypto信源标题提醒`、`文本审查者`、`事实审查者`、`此前消息`、`巨鲸`，当前侧边栏只渲染 `高频区 / AI区` 两个展示分区；`此前消息` 链路默认关闭，历史兼容数据不再单独占用低频区。
- 高频区展示普通 `新快讯 / Crypto信源标题提醒 / 文本审查者 / 事实审查者 / 巨鲸`；AI区展示 `tasks.source = 'ai_source'` 和标记为 `AI信源` 的 X 账号新快讯。
- `此前消息` 由编写者3产出，但编写者3当前默认停用。`WRITER3_ENABLED=false` 时，`writer3-worker` 与 `writer3-confirm-worker` 不领取任务、不调用 AI、不写新“此前消息”；CLI、表结构和历史数据保留兼容，恢复时显式设置 `WRITER3_ENABLED=true`。
- 信息流接口返回字段不变，`lane` 当前兼容 `high / ai / low`；新巨鲸消息写入 `high`，旧 `low` 巨鲸读取时归一为 `high`。
- 信息流读模型不再按类型预留可见席位；高频区和 AI区各自只按 `occurred_at DESC` 展示。
- 信息流当前只展示最近 `2 小时` 内的内容，旧消息不再占用侧边栏空间；窗口内多条消息通过各自分区内部滚动承载，不改变两个区的展示高度。
- `新快讯` 在插件里区分 `已直发` 和 `挂后台`；这里的 `挂后台` 仅指发布状态，不等于文本审查者提醒。
- `文本审查者` 与 `此前消息` 两类卡片当前提供 `接受 / 拒绝` 反馈，并把反馈人和反馈时间写入数据库，用于值班时效统计与误报复盘。
- `文本审查者` 与 `此前消息` 的详情链接优先指向 Odaily 对应快讯页；反馈成功后卡片不再展示操作按钮。
- 生产文本 LLM 主链路统一经过本机 `odaily-litellm.service`，后端服务访问 `ODAILY_LLM_BASE_URL`。业务代码使用 `odaily-gpt-writer`、`odaily-gpt-auditor`、`odaily-deepseek-fast`、`odaily-deepseek-review` 和 `odaily-deepseek-auditor` 等业务别名；判断者、竞品事件复核和混合信源分流现使用 `odaily-gpt-writer`（底层为 `gpt-6-luna`）且不发送 reasoning 参数。X Agent 的市场情绪和项目推介也统一使用 `gpt-6-luna`，不思考且不进入快讯链路。搜索者 AI 复核按 `SEARCH_AI_REVIEW_*` 直接访问当前 GPT 中转，并固定为不思考模式。真实 OpenAI 中转配置分别维护在 LiteLLM 配置、搜索者私有配置和服务器 `.env` 中。主处理、文本审查者、编写者3和编辑插件的 AI 客户端默认超时统一为 `90` 秒；LiteLLM 自身请求窗口继续由代理配置独立控制。DashScope embedding 不经过 LiteLLM。
- `快讯生成` 由 X 页面内容抽取触发：content script 在 `x.com / twitter.com` 帖文操作区注入 Odaily 按钮，点击后打开 side panel 并切到 `快讯生成`。
- `快讯生成` 的 `AI查重` 复用 Linux 服务器上的 `搜索者` 能力；插件只负责传入抽取正文并展示返回结果。
- `快讯生成` 的 `X快速生成` 和 `X常速生成` 由编辑手动选择 `常规 / 融资 / 链上` 模板，`外媒常速生成` 固定使用 `外媒快讯` 模板；三者复用 Linux 服务器上的 `编写者1 -> 编写者2` 能力，只返回生成结果，不直接进入判断者、发布者，也不接入发布后异步 `文本审查者`。
- 插件轻服务中 `AI查重` 与三个生成动作使用不同模型配置：查重读取 `SEARCH_AI_REVIEW_*`，生成读取 writer 配置；`X快速生成` 走 `odaily-gpt-writer` + `low`，`X常速生成` 与 `外媒常速生成` 统一走 `odaily-gpt-writer`。
- `快讯生成` 的 X 作者命名不直接使用插件页面抽取到的显示名；服务端会按 `x_capture_accounts` 中与 `author_handle` 对应的 `写作名 -> author_display_name -> author_handle` 顺序计算 `effective_author_name`，再交给 `编写者1`。
- `X快速生成` 默认使用 `odaily-gpt-writer`（底层为 `gpt-6-luna`）+ `low`；`X常速生成` 与 `外媒常速生成` 使用现有 writer 模型别名，默认 `odaily-gpt-writer`，并在插件轻服务内固定使用 `medium` reasoning。
- 插件通过独立轻服务命令 `editor-plugin-api-server` 对外提供统一接口：`/plugin/auth/*` 负责插件登录态，`/plugin/feed/*` 负责信息流读写，`/plugin/news-gen/*` 负责快讯生成。
- `快讯生成` 的 `POST /plugin/news-gen/search`、`POST /plugin/news-gen/generate` 与 `POST /plugin/news-gen/quick-generate` 都要求插件登录态；X 生成要求传入 `news_type = regular | funding | onchain`，外媒常速生成不传 `news_type`，改传 `generation_mode = external_media`。
- 生产环境中，插件轻服务由 `deploy/odaily-editor-plugin-api.service` 托管，只监听受部署配置约束的本机回环地址；公网入口由 `deploy/odaily-editor-plugin-api.Caddyfile` 提供 HTTPS 反向代理。实际端口和主机信息属于私有运维资料。
- 插件与控制台共用本地单操作者账号；轻服务验证 SQLite 中的 bcrypt 密码哈希并签发本地短 session。
- 插件轻服务承接邮箱密码登录时，生产地址必须使用 HTTPS；浏览器侧会拒绝向非 localhost 的 HTTP 插件服务提交密码。
- `快讯生成` 与 `信息流` 都只允许本地单操作者访问。
- `信息流` 由插件轻服务读写 Linux 本地 SQLite store；核心业务 worker 产出消息时直接写本地 feed，反馈也留在本地，不存在远程回填或归档。
- `快讯生成` 的请求与结果会单独写入 `editor_plugin_generation_logs`，不写入正式 `tasks` 发布流水线。
- 当前插件安装包内置 HTTPS 插件轻服务地址；值班编辑不需要手填接口地址。
- 插件在线心跳仍未实现；系统错误、积压、心跳和程序异常告警仍以 Telegram 为主，文本审查者、此前消息、巨鲸和新快讯不发 Telegram。
- 插件当前支持 `Side Panel` 打开状态下的新消息短音提醒；新消息标题前 2 分钟使用红色显示，之后恢复普通颜色。
- `文本审查者` 与 `事实审查者` 共用插件 `auditor_alert` 声音配置；事实审查只在最终状态为 `flagged` 时提醒，摘要从各审查阶段的问题结论中提取并限制到 180 字符。
- 模块细节见 `docs/OdAIly代码与整体设计/信息流插件.md`、`docs/OdAIly代码与整体设计/快讯生成插件.md`。

## SQLite 维护契约

- 各 `*-init-db` 命令只初始化本地 SQLite schema。
- SQLite 运行日志和已完成任务大字段清理由 `maintenance-cleanup` 命令承载。
- 命令默认 dry-run，只输出将删除或清理的行数；必须显式传入 `--execute` 才会修改数据库。
- 默认策略：运行日志类保留 `7` 天，插件 `接受 / 拒绝` 反馈保留 `90` 天，已完成任务的大字段在 `7` 天安全窗口后清理。
- 插件“已看”记录不作为业务留存目标；当前只保留反馈记录用于复盘。
- 在线备份、迁移和回退细节见 `SQLite主存储迁移.md`。

## 股票行情播报契约

- `stock_market_broadcast` 与 Gate行情播报、主快讯任务状态机独立运行。它在 worker 启动时及此后每小时从 Binance `exchangeInfo` 发现 `TRADING` 状态的 `TRADIFI_PERPETUAL` `EQUITY / CN_EQUITY / HK_EQUITY / KR_EQUITY` 合约；未来若出现 `JP_EQUITY` 按日股处理。其他 underlying type、指数、商品、外汇和 Pre-IPO 不纳入；普通 ETF 保留，杠杆及反向 ETF 按真实跟踪标的维护排除代码表，并过滤 `2L/3L/2S/3S` 后缀。新增产品在 Binance 上架后按实际产品属性核实并更新名单。
- 每30秒调用一次 Binance 批量 `ticker/24hr`，持久化报价样本并用一小时前的近邻样本计算1H涨跌；24H涨跌使用 Binance 百分比。缺失或过期报价不判断，worker 重启静默建立基线。
- 候选按市场和涨跌方向合并，首批等待3分钟，发稿后30分钟统一处理后续候选；1H/24H共享资产价格记录，同一资产只进入最高档的一篇稿件。5%挂后台、10%直发，汇总前重新检查有效行情。实际价格进一步同向变化及升级条件用于抑制重复；6小时到期、启动和行情中断恢复静默建立基线。启动/行情恢复价作为独立门槛：相对该价格同向变化5%才可挂后台、10%才可直发，并须同时满足原滚动窗口条件；恢复价不随6小时去重锁到期而失效。
- 固定文案使用去掉USDT后缀的资产名、窗口、方向、涨幅和去尾零现价；正文复用编写者2的 `format_brief` 统一署名、空格和标点，不创建主链路编写者2任务。美股多标的合并稿使用编写者模型识别公司与共同主题，主题不明确时回退通用市场描述；模型不生成行情数字。“普涨/普跌”须满足有效样本覆盖、方向占比和中位数条件；合并稿最多展开5个代表资产。`EQUITY` 归属 MSX.COM，韩股及未来日股归属 Gate，A股和港股使用“行情数据”。实际行情来源始终是 Binance。
- 触发调用 Push Data API，5%设置 `isPublish=false`，10%设置 `isPublish=true`，均设置 `isPush=false`；候选、价格记录、样本和事件先原子提交到独立 SQLite，再请求发布接口；不自动重试结果不确定的推送。
- 控制台一级页面位于 Gate行情播报下方，通过认证的 `GET /console/stock-market/get` 只读展示触发状态、最近事件和运行状态；默认显示播报概览，合约列表放在单独的“合约行情”标签中。页面仅在打开时每30秒刷新，不提供规则编辑或单合约启停。模块细节见 `控制台-股票行情播报.md`。

- `whale_watch_hyperliquid` 的官方 Hyperliquid `info` 接口 5xx 故障按上游降级处理：地址状态和 heartbeat metadata 保留失败明细，heartbeat 写 `status=degraded` 且刷新成功时间，避免监督者误判 worker 进程失活；非上游故障仍写失败心跳。

# 运行时代码边界补充

- 常驻服务、控制台、插件、监督者和维护命令只允许通过 SQLite repository factory 访问本地库。
- 运行时包入口不得导出 `Postgres*Repository`，导入运行时包不得加载 `packages.common.postgres`。
- 旧 Supabase/Postgres 读取只允许在一次性迁移命令 `storage-import-legacy` 或旧版本灾难回切审计中显式触达，不能作为新版本环境变量开关或 worker 分支保留。

Hyperliquid 写作契约：编写者1仅接收命中事件的新闻事实白名单，完整来源和统计证据独立留在监测后台；固定尾部避免重复正文。事件按场景选择独立 Prompt，测试预览与已保存任务修订预览复用场景映射。既有事件可独立生成编辑预览并关联展示，不推进任务状态或再次调用发布接口。具体字段与版本激活命令见 `Hyperliquid关键地址与新闻事件.md`，页面展示见 `控制台-Hyperliquid监测.md`。

Hyperliquid 十个正式方向共用成交顺序与最终仓位事实边界；地址操作与巨亏加仓用净变化，主动兑现和实际清算保留成交结果，被动盈亏保留未实现口径。普通监测与账户监测均在成交分页完成后才推进成功基线，完整性和操作门槛在投递前复核。多标签事件的已实现盈亏标题与场景Prompt优先于普通仓位操作，模块字段及失败处理见 `Hyperliquid关键地址与新闻事件.md`。
