# 完整程序架构

## 主存储切换契约

- 新版本唯一允许 `ODAILY_STORAGE_BACKEND=sqlite`；主库路径由 `ODAILY_SQLITE_PATH` 指定，默认 `data/database/odaily.sqlite`。
- `ODAILY_STORAGE_EPOCH` 是一次切换的存储世代。队列只领取当前世代任务，跨世代的 `(source, source_item_id)` 唯一记录继续充当去重账本。
- 回切依赖切换前的旧 commit、旧环境文件和冻结 Supabase 数据；SQLite 时期新增数据允许放弃，因此不做持续双写。新版本本身不能通过环境变量切回 Postgres。
- SQLite 文件、`-wal` 与 `-shm` 必须位于同一台 Linux 主机的本地磁盘。在线备份使用 SQLite backup API 或停服后的完整文件副本，不能只复制主文件而遗漏未 checkpoint 的 WAL。
- 全部业务仓储、网页和插件已经切为本地 SQLite；一次性导入与生产切换步骤见迁移文档。
- 可比较的业务时刻统一以 UTC 写入 SQLite；外部来源携带的 `+08:00` 等偏移必须在仓储边界转换为 `+00:00`。历史混合格式参与窗口筛选或排序时必须使用 SQLite 时间函数解析，不能直接按 TEXT 字典序比较。面向编辑、Prompt 和控制台展示时再转换为北京时间。
- 迁移状态、磁盘门槛、清理和回切步骤见 `SQLite主存储迁移.md`。

## 生产服务器边界

- `Odaily 官方服务器` 是 OdAIly 唯一活动生产节点，承载 `/opt/OdAIly`、本地 SQLite、所有生产 worker、监督者、LiteLLM 和 `api.odaily.uk` HTTPS 入口。
- `原共享服务器` 只保留其他项目；迁移完成后不得运行 OdAIly 的 API、worker、定时任务、Telegram session 或 SQLite 写入。
- 两台服务器之间不做持续双写。迁移窗口内先冻结两边写入，再以旧生产节点的最终一致快照为主源，把官方服务器恢复为单写入节点。
- Vercel 前端和 Chrome 插件只通过 `https://api.odaily.uk` 访问官方服务器；浏览器不连接数据库，旧公网 API 地址不再作为生产兜底。

## 当前有效主链路

所有收集入口在创建 `tasks` 前统一应用 `source_exclusion_rule_groups`。规则组以 `x / competitor / crypto_source / ai_source / mixed_source / jin10` 为固定路径，采用 Unicode NFKC、大小写不敏感、任一词子串匹配，并通过 `match_target` 选择 `title`（仅标题类文本）或 `all`（标题、摘要与正文）范围；URL 不参与匹配。混合信源先检查 `mixed_source`，分类后再检查目标路径；命中后只把来源项目标记为已处理，不创建任务、不保留标题、审计、历史或计数。

`MAGNE.AI` 同时作为竞品源头默认排除词和发布者硬拦截词：竞品标题或正文命中时不创建任务；已进入发布阶段的任意任务若原始标题、原始正文、最终标题或最终正文命中，则以 `hard_blocked_term` 挂后台，推送接口调用保持 `isPublish = false`。

- `X`：`x_capture` 入库后提交本地流水线 `write_flow` job；收集者-X 会在写入任务正文前把 FXTwitter 可能返回的 `solana:<CA>` 代币别名通过 GMGN 解析为 symbol，解析失败时保留原文；X Article 会和外层普通帖子合并进入同一条 `tasks.content` 与后续 Prompt，Article 不拆分任务；标记为 `AI信源` 的 X 账号走 `judge_ai -> search -> write -> format_publish -> publish`，其他 X 走 `judge_crypto -> search -> write -> format_publish -> publish`
- `币安广场`：实验性 collector 只在数据库总开关和独立 systemd 服务同时启用时轮询配置账号；首次只建立最新 20 条基线，后续写入 `tasks.source = 'binance_square'` 并执行 `judge_crypto -> search -> write -> format_publish -> publish`，发布阶段固定挂后台
- `竞品快讯`：`competitor_monitor` 入库后提交本地流水线 `write_flow` job，执行 `search -> judge_crypto -> write -> format_publish -> publish`
- 未命中竞品事件排除规则的竞品与 Odaily 快讯由后端写入 `newsflash_events` / `newsflash_event_sources` 做事件聚合和来源归属；`快讯及数据总览` 通过二级页提供事件与首发复盘，不恢复已废弃的收藏和备注契约。
- 竞品来源的首发比较统一使用系统归一后的发布时间；PANews 在原始发布时间基础上固定顺延 1 分钟，以抵消其可能回改发布时间造成的首发偏差。原始值仅保留在 `raw_payload`。
- 事件归属的业务口径是“同一报道”而非宽泛主题：同一规范化原始 URL 可直接归并，标题+正文 embedding 达到 `0.88` 直接归并，中间区间才进入只返回布尔值的 AI 复核；现有事件以代表来源为稳定锚点，禁止组内链式扩张。实现和 Prompt 细节见 `收集者-竞品.md`。
- `Crypto信源全文`：统一由 `non_mainstream_media` 收集，写入 `tasks.source = 'non_mainstream_media'` 后提交本地流水线 `write_flow` job，执行 `search -> judge_crypto -> write -> format_publish -> publish`
- `Telegram-first Crypto信源全文发现`：`non_mainstream_media_telegram` 独立轮询 `PhoenixNewsEN`，只处理 `CoinDesk / Cointelegraph / Decrypt`，命中原站链接并抓到正文后，同样写入 `tasks.source = 'non_mainstream_media'` 并提交本地流水线 `write_flow` job
- `Crypto信源标题提醒`：统一由 `non_mainstream_media` 的 `alert_only` 站点写入 `tasks.source = 'external_media_alert'` 后提交本地流水线 `alert_only` job，执行 `domain_judge -> search -> notify`
- `混合信源全文`：统一由 `non_mainstream_media` 中 `source_group = 'mixed_source'` 的 `write_flow` 站点收集，先在收集器内分流为 `crypto / ai / discard`，再分别写入现有 Crypto信源或 AI信源链路
- `混合信源标题提醒`：统一由 `non_mainstream_media` 中 `source_group = 'mixed_source'` 的 `alert_only` 站点收集，先在收集器内分流为 `crypto / ai / discard`，再分别写入现有 Crypto信源或 AI信源标题提醒链路
- `AI信源全文`：统一由 `non_mainstream_media` 中 `source_group = 'ai_source'` 的 `write_flow` 站点收集，写入 `tasks.source = 'ai_source'` 后提交本地流水线 `write_flow` job，执行 `search -> judge_ai -> write -> format_publish -> publish`
- `AI信源标题提醒`：统一由 `non_mainstream_media` 中 `source_group = 'ai_source'` 的 `alert_only` 站点写入 `tasks.source = 'ai_source_alert'` 后提交本地流水线 `alert_only` job，执行 `domain_judge -> search -> notify`
- `金十`：`jin10_monitor` 轮询金十快讯接口，写入 `tasks.source = 'jin10'` 后提交本地流水线 `write_flow` job，执行 `judge_jin10 -> search -> write -> format_publish -> publish`
- `Gate行情播报`：独立 `gate_market_broadcast` worker 每分钟读取8个 Gate TradFi 标的，按整数网格和持久化重新武装状态触发固定行情文本；只复用确定性 `format_brief` 与通用推送接口，不进入 `tasks`、现有 Gate 定时简报或主写作状态机。
  - `Meme速递`：OdAIly 内置 `meme_scanner` 每 1 分钟通过有头 Playwright Chromium 打开匿名 OKX MemePump 页面，由页面脚本生成动态校验头，分别读取 BSC `chainId=56` 和 Robinhood `chainId=4663` 的 `memefun/meme-ranking/content` `rankType=4` 最新迁移列表；列表最多 30 条，仅承担首次发现窗口。网页 `mcap`/`vol1h` 只作发现上下文，市值和 24 小时成交量由 `MEME_PRICE_SOURCE` 选择官方签名 OKX `price-info` 或 GMGN `token info` 补齐，列表外持续观察仍用 OKX `tokenDetails` 加选定的市场价格适配器。scanner 启动时会按当前配置收紧历史 active 记录的窗口和调度周期。网页发现失败默认明确报错，不静默消耗官方发现额度；可由显式配置切回官方 `tokenList(stage=MIGRATED)`。Telegram 的 EVM CA 先查询 Robinhood Chain，再以 BSC 作为兜底，并把实际链值贯穿 token payload、快照、观察账本、里程碑、叙事和标题。每次 OKX 列表、市场价格/详情或 Telegram 成功调度都以链+CA 为维度写入不可变 `token_snapshots`，普通市值档位由 `market_cap_milestones` 按链+CA+档位唯一记录首次观测。新发现的普通代币在独立 SQLite `observations` 账本中建立 3 天窗口，仍在窗口内但滚出列表的代币由持久化、串行、错峰的市场价格调度器继续观测，低于本链第一门槛每 4 小时一次，达到门槛每 15 分钟一次。BSC 普通代币跨越 50 万、100 万、300 万美元，Robinhood 跨越 100 万、300 万美元时按链+CA+档位幂等触发，首次发现已跨多档时只触发最高档；普通里程碑和 Telegram 热议均要求 24 小时成交量/市值达到动态门槛，市值不高于 30 万美元为 50%，不低于 300 万美元为 20%，中间线性插值。OKX 风险字段默认 shadow 记录，显式 block 模式才拦截高疑似钓鱼钱包或高 Top10 集中度。Telegram 社区热议按链和市值门槛判断，不受 launchpad/platform 限制；Telegram 先发现的记录在后续 OKX 列表扫描时仍可激活跟踪，过期记录永久停止。该链路不进入 `tasks`，通过 Push Data API 创建挂后台稿件。
- SQLite 主库保存原始记录、阶段结果、最终结果和失败原因；生产主链路通过本地 job 推进，`tasks` 与阶段表作为持久化事实和恢复依据。
- 搜索者查重使用的 Odaily 已发布快讯历史以 Odaily 官方快讯 API 为真实来源；`odaily_reference_items` 保存于主 SQLite，作为本地历史与 API 不可用时的兜底读取源。
- 本地 job 唯一键统一为 `source + source_item_id`，重复来源内容不会重复进入本地队列。
- `local_pipeline` 执行每个处理阶段前，必须按 `task_id + stage` 通过 `tasks` 行锁原子领取任务；即使旧分阶段 worker 被误启动，同一任务同一阶段也只能由一个执行器进入，未领取到的本地 job 退避重试。
- `local_pipeline_jobs` 的一次执行也计入尝试次数；`LOCAL_PIPELINE_MAX_ATTEMPTS` 默认是 `3`。第 3 次仍失败时，队列 job 进入 `exhausted`，不再自动重试；该状态只属于本地队列，不会删除或改写业务 `tasks` 状态。
- 主写作链路查重以服务器本地 `SearchCache` 热 cache 为实时判定来源；查重范围包括 Odaily 历史、运行中 candidate 和默认保留 24 小时的 `recent_processed`。向量召回分别取 Odaily 历史 Top 3 与 candidate Top 5，最高相似度达到 `0.60` 时把整组候选交给一次 AI 裁决，任意候选属于同一事件即拦截；`odaily_reference_items` 与 `search_event_candidates / search_event_sources` 写入主 SQLite 供归档、控制台、插件和复盘使用。
- `SearchCache` 是有界、可重建的运行缓存，不是永久档案：业务文档按 `2 / 8` 天窗口清理，embedding 使用 float32 BLOB；长驻服务只删除过期行，物理压缩由显式维护命令执行。具体生命周期见 `搜索者.md`。
- 所有生产链路写入 `tasks.content`、`odaily_reference_items.content`、`newsflash_items.content`、插件 `post_text` 以及编写阶段正文时，统一保留有效段落内容，但会移除空白段落；多段正文只使用单个 `\n` 作为段间分隔，不保留空行。通用 `PushClient` 调用 Odaily 发布接口时才把每个非空行转换为一个 `<p>` 段落，内部存储仍保持纯文本。
- `tasks.source_url` 表示可透出的原文链接，而不是采集站内详情页。竞品链路中 `blockbeats` 和 `jinse` 只有拿到外部原文链接时才写入；发布者调用 Odaily 发布 API 时才将其作为 `sourceUrl` 传递。律动、金色财经等竞品站内页不作为 `sourceUrl` 对外发布。
- 为满足阶段耗时分析需求，主写作链路需要把各阶段完成时间持久化到 `x_task_pipeline`。当前系统级阶段时间戳包括：`judge_completed_at`、`search_completed_at`、`write_completed_at`、`format_completed_at`、`publisher_decided_at`、`publish_completed_at`。分析时应优先使用这些显式时间戳，而不是仅靠 `tasks.updated_at` 或结果表创建时间反推。
- `耗时看板` 复用这些阶段时间戳做聚合分析，不引入新的任务状态或 worker 交接边界；V1 只覆盖主写作链路，不纳入标题提醒链路 `external_media_alert_pipeline`。

## SQLite 本地主存储架构

- 采集、处理、审核、巨鲸、Writer3、监督和维护全部读写 Linux 主 SQLite。
- 插件信息流由本地 feed store 提供；普通控制台业务表由认证后的 `/console/data` 接口访问主 SQLite，快讯运营跨表查询与写入使用专用 `/console/newsflash-operations`。
- 常驻服务没有 Supabase/Postgres 回退、异步归档或双写路径。
- 详细边界见 `SQLite本地主存储架构.md`。

## Crypto信源与混合信源系统级契约

- 业务上 Crypto信源、AI信源、混合信源都保留两条模式：`write_flow` 与 `alert_only`
- Crypto信源站点还带只读发现模式 `discovery_mode`：
  - `direct`
  - `telegram_primary_direct_fallback`
- Crypto信源 source 映射：
  - `write_flow` -> `tasks.source = 'non_mainstream_media'`
  - `alert_only` -> `tasks.source = 'external_media_alert'`
- AI信源 source 映射：
  - `write_flow` -> `tasks.source = 'ai_source'`
  - `alert_only` -> `tasks.source = 'ai_source_alert'`
- 混合信源 source 映射：
  - 收集阶段先分流，不新增独立 `tasks.source`
- 站点通过 `non_mainstream_media_sources.source_group` 区分 `external_media / ai_source / mixed_source`
- `mainstream_media` 只保留历史兼容，不再作为新的生产入口
- 写作模板层面，Crypto信源全文和 AI信源全文都使用 `mainstream_media_writer`；标记为 `AI信源` 的 X 账号仍按 X 常规写作使用 `x_regular_writer`。
- 非 X 全文写作任务在 `format_publish` 定稿阶段统一把标准站点名追加到正文末尾，格式为 `（站点名）`；名称优先来自 `non_mainstream_media_sources.display_name`，缺失时按原文链接域名硬匹配，标题提醒链路不经过该阶段。
- `external_media_alert_fetcher` 已退役，不再是生产必需 worker

## 运行面

- 本地流水线：
  - `local_pipeline`
  - HTTP 入口默认 `127.0.0.1:8776`
  - 本地 SQLite 队列位于 `data/runtime/local_pipeline.sqlite`
  - 同一主机只允许一个 `local_pipeline` 进程持有 `data/runtime/local_pipeline.lock` 文件锁；旧实例未完全退出时，新实例拒绝启动，避免两个 worker 并发领取同一任务。锁文件是运行资产，进程退出后文件残留不代表仍有锁。
  - 服务启动时会把锁定超过 `30` 分钟的本地 `running` job 回收到可重试状态；已达到最大尝试次数的 job 直接进入 `exhausted`，避免历史僵尸 job 永久卡住队列表现
  - job 执行中如果某个业务阶段失败，SQLite job 进入退避重试；下一次领取会从 `judge_failed / domain_failed / search_failed / write_failed / format_failed / publisher_failed / notify_failed` 对应的失败阶段继续，而不是把业务失败状态当成已完成。失败阶段只能回到对应阶段领取，真正被其他 worker 锁住时才报告占用冲突。
  - `local-pipeline-exhaust` 默认只列出当前 storage epoch 中已超过尝试上限的 `failed/running` job；传入 `--execute` 才会将它们标为 `exhausted`。该命令不删除或修改业务任务。
- 常驻 worker 的单轮外围异常应被捕获并进入下一轮，避免一次配置读取、任务领取、外部 API 或数据库短暂波动导致进程永久退出；真正的异常由 heartbeat、失败状态和监督者 Telegram 告警暴露
- 常驻收集：
  - `non_mainstream_media`
  - `non_mainstream_media_telegram`
  - `x_capture`
    - systemd 服务为 `odaily-x-capture.service`，在 `odaily-local-pipeline.service` 启动后运行
  - `binance_square`（实验性、默认休眠）
    - 独立账号配置、基线和尝试记录保存在主 SQLite；固定每 180 秒读取启用账号的普通帖子
    - 首次只建立最新 20 条基线，后续任务以 `tasks.source = binance_square` 复用 X 常规主链路，但发布阶段固定挂后台
    - systemd 服务为 `odaily-binance-square.service`；生产只安装 unit，不默认 enable/start，总开关也默认关闭
  - `competitor_monitor`
  - `jin10_monitor`
- 独立行情播报：
  - `gate_market_broadcast`
  - 独立 SQLite 位于 `data/runtime/gate_market.sqlite`
  - 独立 systemd 服务为 `odaily-gate-market-broadcast.service`
  - 默认 `backend` 模式真实调用推送接口但固定 `isPublish=false,isPush=false`；切换 `live` 后使用 `isPublish=true,isPush=false`
  - 行情配置、状态和最近触发保存在独立本地 SQLite
  - 推送成功后直接写入插件本地 feed store，类型为 `gate_market`
- 独立 Meme 速递：
  - `meme_scanner` 同时承载 GMGN 发现、任务状态机、Telegram CA 监听和 CommunityMonitor V2 叙事材料管线
  - 叙事管线以精确 CA 为键执行 Telegram 全历史边缘命中与前后文采集、X 原帖收集、Grok 独立研究和结构化 writer 输入
  - 独立 SQLite 位于 `data/processed/meme_scanner.sqlite3`
  - systemd 服务为 `odaily-meme-scanner.service` 与 `odaily-meme-tg-watcher.service`
  - 稿件固定以 `isPublish=false,isPush=false` 进入后台，不进入 `tasks` 主状态机
  - 挂后台成功后直接写入插件本地 feed store，类型为 `meme_digest`
  - `jobs` 持久化首次领取、发布开始和终态完成时间；叙事 JSON 持久化各调用耗时，控制台据此还原排队、叙事、发布和总耗时
- `non_mainstream_media_telegram` 只负责 Telegram-first 发现入口，不替代原 `non_mainstream_media` 站点直抓 worker；两者并行运行。
- 旧分阶段 worker 命令不属于生产 systemd；灾难回滚通过恢复完整旧 commit 完成。
- 收集器提交本地流水线失败时，不把来源 item 标记为已看，下一轮继续重试。
- 切换前未完成旧任务由 `local-pipeline-skip-legacy --execute` 标记为 `legacy_skipped`，不导入本地队列，也不继续补跑。
- 新版本不使用数据库 `LISTEN` 做阶段交接。

## 控制台访问契约

- 控制台是 Vite 前端，全部请求通过 HTTPS 后端访问本地 SQLite 或本地配置文件，不直连数据库。
- 控制台与插件共用本地单操作者邮箱密码和不透明 Bearer session。
- `/console/data` 只暴露固定表白名单、固定过滤操作和安全标识符。
- `/console/newsflash-operations` 只暴露快讯分页、人工字段、花名册、排班、自然周归属、统计、优质快讯、贡献和事件查询动作；浏览器不提交 SQL。优质快讯通过单一 `quality` action 集中完成周门槛、班次归属、首发和信源排除，前端不复制业务判定。
- 发布者规则配置由 `editor-plugin-api-server` 暴露 `/console/publisher-rules/get` 与 `/console/publisher-rules/save`，但权限使用 `console_admins` 白名单，不使用插件白名单。
- 发布者规则运行时读取服务器本地 `data/config/publisher_rules.json`，主 SQLite 保存配置快照。
- 发布者控制台通过服务器接口读写规则；接口失败时明确报错，不回退远程数据库。
- `耗时看板` 通过 `/console/pipeline-timing/get` 读取 `data/runtime/pipeline_timing.sqlite` 聚合快照。
- `Gate行情播报` 通过 `/console/gate-market/get` 只读 `data/runtime/gate_market.sqlite`。
- `Meme速递` 通过 `/console/meme/get` 只读 OdAIly 自己的 `data/processed/meme_scanner.sqlite3`；路径可由 `MEME_SCANNER_DB_PATH` 覆盖。接口返回任务实际链值，前端据此生成对应 GMGN 链接；写入方是 `odaily-meme-scanner.service` 与 `odaily-meme-tg-watcher.service`，控制台本身不推进任务。
- `AI查重` 复用插件已有的 `POST /plugin/news-gen/search`，控制台只提交编辑粘贴的正文并展示搜索者结论和候选，不创建正式任务、不改变主流水线状态。
- Meme 叙事审计复用 `jobs.narrative_json`，叙事流程必须区分成功、空材料和阶段异常；阶段异常进入叙事重试，不得被归类为 `no_usable_narrative`。`/console/meme/get` 只返回摘要，`/console/meme/detail?id=<job_id>` 返回单条完整审计材料，旧任务缺少审计 JSON 时保持兼容并返回不可用标记。
- `Prompt及规则管理` 页面承载 `可编辑 Prompt / 内置规则 / 知名人物` 三类配置视图。代码内置 Prompt、Schema、标题策略、当前知名人物名单、确定性替换和发布者默认规则由认证接口 `GET /console/runtime-rules/get` 返回；知名人物名单由 `/console/known-title-subjects/get` 与 `/console/known-title-subjects/save` 维护，保存到 Linux 本地 `data/config/known_title_subjects.json`，不轮询数据库，不保存逐人标题情景或复杂 JSON。
- `信息周期监控` 将全部受支持来源作为一个查询范围，按可解析的 `tasks.created_at` 倒序分页，并以 `tasks.id` 作为稳定次序；从 `x_task_pipeline.writer_output.trace` 读取任务级标题策略溯源，并显示 writer Prompt、模型、特色模式配置与实际采用状态；历史任务不回填，统一显示“旧任务无标题溯源”。
- `信源管理 / 律动key` 子页通过 `/console/blockbeats-key/get` 与 `/console/blockbeats-key/save` 维护服务器本地 `data/config/blockbeats_key.json`；收集者-竞品 worker 默认在无 key 或额度不足时自动申请、替换并只重试一次，人工保存仍可覆盖当前 key。
- 发布者自动发布是否开启，仅由规则文件中的 `regular.enabled` / `ai_source.enabled` 决定；`tasks.source = 'ai_source'` 和 `tasks.source = 'x'` 且 `tasks.metadata.x_account_is_ai_source = true` 都使用 `ai_source` 发布者规则块。旧 `publisher_settings.enabled`、`publisher_channels.enabled` 和北京时间窗不再参与运行时判定。
- 后端 worker 通过 `ODAILY_SQLITE_PATH` 访问本地主库，不依赖控制台登录态。
- 快讯运营事实以 Odaily `source_item_id` 为稳定键；来源字段同步不得覆盖已锁定的人工发布人，贡献、排班和周归属修改写审计。优质快讯规则以自然周为键冻结监控账号、媒体域名和计分参数，但浏览量及运营事实实时重算；排班人员颜色由前端稳定键生成，不进入存储契约。模块细节见 `控制台-快讯及数据总览.md`。

## X 发言人命名契约

- `x_capture_accounts` 除抓取账号本身的配置外，还承载账号级 `写作名` 配置和插件展示用 `AI信源` 标记。
- `写作名` 的作用仅限于 X 发稿口径标准化，不改动原始抓取到的 `author_display_name`、`author_username` 和正文。
- `is_ai_source` 不改变 `tasks.source = 'x'`，但会让自动化主链路进入 `judge_ai`；保留后仍作为 X 常规快讯写作，发布阶段按 `AI信源` 发布者规则块处理。当前 `AI信源` 发布者关闭，因此这类任务不会调用发布者模型，会直接挂后台。
- 标记账号的新快讯在 Chrome 插件信息流中进入 AI区。
- 自动化 X 主链路与插件 `快讯生成` 共用同一套 X 发言人命名规则，不各自维护映射。
- 进入 `编写者1` 前，X 来源作者名按以下顺序计算 `effective_author_name`：
  - 优先使用账号配置里的 `写作名`
  - 没有 `写作名` 时回退到原始 `author_display_name`
  - 仍为空时回退到 `author_username`
- 常规模板里“{发言人}在X平台发文表示”中的 `{发言人}`，以及其他依赖 X 发言人名称的写作场景，统一使用 `effective_author_name`。

## 插件契约

- 插件是独立 Chrome 插件，不属于控制台；代码位于仓库根目录 `extension/`，当前以 unpacked extension 方式加载。
- 插件当前规划两个一级模块：`信息流` 与 `快讯生成`。
- `信息流` 消费现有业务上游结果，不新增新的抓取或审核来源；正常业务消息以插件展示为主，Telegram 只保留系统级错误、宕机、积压和程序异常告警。
- `信息流` 当前聚合五类内容：`新快讯`、`Crypto信源标题提醒`、`审核者`、`此前消息`、`巨鲸`，当前侧边栏只渲染 `高频区 / AI区` 两个展示分区；`此前消息` 链路默认关闭，历史兼容数据不再单独占用低频区。
- 高频区展示普通 `新快讯 / Crypto信源标题提醒 / 审核者 / 巨鲸`；AI区展示 `tasks.source = 'ai_source'` 和标记为 `AI信源` 的 X 账号新快讯。
- `此前消息` 由编写者3产出，但编写者3当前默认停用。`WRITER3_ENABLED=false` 时，`writer3-worker` 与 `writer3-confirm-worker` 不领取任务、不调用 AI、不写新“此前消息”；CLI、表结构和历史数据保留兼容，恢复时显式设置 `WRITER3_ENABLED=true`。
- 信息流接口返回字段不变，`lane` 当前兼容 `high / ai / low`；新巨鲸消息写入 `high`，旧 `low` 巨鲸读取时归一为 `high`。
- 信息流读模型不再按类型预留可见席位；高频区和 AI区各自只按 `occurred_at DESC` 展示。
- 信息流当前只展示最近 `2 小时` 内的内容，旧消息不再占用侧边栏空间；窗口内多条消息通过各自分区内部滚动承载，不改变两个区的展示高度。
- `新快讯` 在插件里区分 `已直发` 和 `挂后台`；这里的 `挂后台` 仅指发布状态，不等于审核者提醒。
- `审核者` 与 `此前消息` 两类卡片当前提供 `接受 / 拒绝` 反馈，并把反馈人和反馈时间写入数据库，用于值班时效统计与误报复盘。
- `审核者` 与 `此前消息` 的详情链接优先指向 Odaily 对应快讯页；反馈成功后卡片不再展示操作按钮。
- 生产文本 LLM 主链路统一经过本机 `odaily-litellm.service`，后端服务访问 `ODAILY_LLM_BASE_URL`。业务代码使用 `odaily-gpt-writer`、`odaily-gpt-auditor`、`odaily-deepseek-fast`、`odaily-deepseek-review` 和 `odaily-deepseek-auditor` 等业务别名；判断者、竞品事件复核和混合信源分流现使用 `odaily-gpt-writer`（底层为 `gpt-5.6-luna`）且不发送 reasoning 参数。搜索者 AI 复核是独立例外，按 `SEARCH_AI_REVIEW_*` 直接访问当前 GPT 中转。真实 OpenAI 中转配置分别维护在 LiteLLM 配置、搜索者私有配置和服务器 `.env` 中。writer 模型默认客户端超时为 `150` 秒，覆盖 LiteLLM 当前 `120` 秒请求窗口并保留传输余量；其他主处理请求继续使用通用超时。DashScope embedding 不经过 LiteLLM。
- `快讯生成` 由 X 页面内容抽取触发：content script 在 `x.com / twitter.com` 帖文操作区注入 Odaily 按钮，点击后打开 side panel 并切到 `快讯生成`。
- `快讯生成` 的 `AI查重` 复用 Linux 服务器上的 `搜索者` 能力；插件只负责传入抽取正文并展示返回结果。
- `快讯生成` 的 `X快速生成` 和 `X常速生成` 由编辑手动选择 `常规 / 融资 / 链上` 模板，`外媒常速生成` 固定使用 `外媒快讯` 模板；三者复用 Linux 服务器上的 `编写者1 -> 编写者2` 能力，只返回生成结果，不直接进入判断者、发布者，也不接入发布后异步 `审核者`。
- 插件轻服务中 `AI查重` 与三个生成动作使用不同模型配置：查重读取 `SEARCH_AI_REVIEW_*`，生成读取 writer 配置；`X快速生成` 走 `odaily-gpt-writer` + `low`，`X常速生成` 与 `外媒常速生成` 统一走 `odaily-gpt-writer`。
- `快讯生成` 的 X 作者命名不直接使用插件页面抽取到的显示名；服务端会按 `x_capture_accounts` 中与 `author_handle` 对应的 `写作名 -> author_display_name -> author_handle` 顺序计算 `effective_author_name`，再交给 `编写者1`。
- `X快速生成` 默认使用 `odaily-gpt-writer`（底层为 `gpt-5.6-luna`）+ `low`；`X常速生成` 与 `外媒常速生成` 使用现有 writer 模型别名，默认 `odaily-gpt-writer`，并在插件轻服务内固定使用 `medium` reasoning。
- 插件通过独立轻服务命令 `editor-plugin-api-server` 对外提供统一接口：`/plugin/auth/*` 负责插件登录态，`/plugin/feed/*` 负责信息流读写，`/plugin/news-gen/*` 负责快讯生成。
- `快讯生成` 的 `POST /plugin/news-gen/search`、`POST /plugin/news-gen/generate` 与 `POST /plugin/news-gen/quick-generate` 都要求插件登录态；X 生成要求传入 `news_type = regular | funding | onchain`，外媒常速生成不传 `news_type`，改传 `generation_mode = external_media`。
- 生产环境中，插件轻服务由 `deploy/odaily-editor-plugin-api.service` 托管，只监听受部署配置约束的本机回环地址；公网入口由 `deploy/odaily-editor-plugin-api.Caddyfile` 提供 HTTPS 反向代理。实际端口和主机信息属于私有运维资料。
- 插件与控制台共用本地单操作者账号；轻服务验证 SQLite 中的 bcrypt 密码哈希并签发本地短 session。
- 插件轻服务承接邮箱密码登录时，生产地址必须使用 HTTPS；浏览器侧会拒绝向非 localhost 的 HTTP 插件服务提交密码。
- `快讯生成` 与 `信息流` 都只允许本地单操作者访问。
- `信息流` 由插件轻服务读写 Linux 本地 SQLite store；核心业务 worker 产出消息时直接写本地 feed，反馈也留在本地，不存在远程回填或归档。
- `快讯生成` 的请求与结果会单独写入 `editor_plugin_generation_logs`，不写入正式 `tasks` 发布流水线。
- 当前插件安装包内置 HTTPS 插件轻服务地址；值班编辑不需要手填接口地址。
- 插件在线心跳仍未实现；系统错误、积压、心跳和程序异常告警仍以 Telegram 为主，审核者、此前消息、巨鲸和新快讯不发 Telegram。
- 插件当前支持 `Side Panel` 打开状态下的新消息短音提醒；新消息标题前 2 分钟使用红色显示，之后恢复普通颜色。
- 模块细节见 `docs/OdAIly代码与整体设计/信息流插件.md`、`docs/OdAIly代码与整体设计/快讯生成插件.md`。

## SQLite 维护契约

- 各 `*-init-db` 命令只初始化本地 SQLite schema。
- SQLite 运行日志和已完成任务大字段清理由 `maintenance-cleanup` 命令承载。
- 命令默认 dry-run，只输出将删除或清理的行数；必须显式传入 `--execute` 才会修改数据库。
- 默认策略：运行日志类保留 `7` 天，插件 `接受 / 拒绝` 反馈保留 `90` 天，已完成任务的大字段在 `7` 天安全窗口后清理。
- 插件“已看”记录不作为业务留存目标；当前只保留反馈记录用于复盘。
- 在线备份、迁移和回退细节见 `SQLite主存储迁移.md`。

## 定时行情简报契约

- `gate-tradfi` 与 `us-market` 共用 `odaily-worker` 调度进程，但日历规则分开维护。
- `gate-tradfi` 定时简报只读取 `XAUUSD / XAGUSD / USDCNH / USDJPY / EUSTX50 / UK100 / GER40 / XTIUSD / XBRUSD` 这9个 Gate TradFi 标的，不再请求或发布 BVIX、EVIX 波动率指数数据；旧配置中的 `futures_symbols` 会被忽略。
- 两条定时行情简报链路调用 Push Data API 时默认 `isPublish=true`、`isPush=false`，直接发布，不进入后台挂审。
- `gate-tradfi` 只按北京时间工作日执行：
  - `morning`：北京时间上午。
  - `open`：按美东开盘时点触发，但仍要求该触发时刻对应的北京时间是周一到周五晚间。
- `us-market` 按美东交易日执行：
  - `premarket`：只保留手动执行能力，不进入自动调度。
  - `open`：美东开盘。
  - `close`：北京时间次日早晨播报上一美东交易日收盘，因此整条链路从北京时间周一晚间开始，到北京时间周六早晨结束。
- `us-market` 的自动调度必须同时跳过美东周末和 NYSE 休市节假日；`gate-tradfi` 不复用这套美东周末判定。

## Gate行情播报契约

- `gate_market_broadcast` 与既有 `gate-tradfi` 完全独立，不共享任务、配置、状态、数据库或 worker。
- 标的固定为 `EUSTX50 / UK100 / GER40 / XBRUSD / USDJPY / USDCNH / XAUUSD / XAGUSD`，默认每60秒读取 Gate 最新成交价。
- 触发网格以0为原点；同一网格线触发后，必须到达相邻网格线才允许返回触发。首次启动、阈值修改和宕机恢复都静默建立基线，不补发历史突破。
- SQLite 是唯一运行配置和状态来源；分钟样本保留48小时，触发诊断保留最近100条，不保存分钟原始 JSON。
- `backend` 与 `live` 共享按标的持久化的行情触发状态，模式切换不得
  重置同一网格线的防重复锁；两种模式只改变推送接口的发布参数。
  推送失败只告警并放弃，不自动重发。
- 模块细节见 `控制台-Gate行情播报.md`。

## Meme速递系统契约

- Meme速递读者层 reader_text 的唯一目标是最终炒作角度；Telegram 命中频次、群组数量、用户情绪和检索过程只能留在内部审计或控制台统计。
- Meme速递通过 OKX MemePump 网页发现 BSC/Robinhood 迁移代币；市场价格适配器由 `MEME_PRICE_SOURCE` 选择 OKX 或 GMGN，切换价格源不改变发现链路或任务的实际 `chain`。
- Meme速递的 X CA 材料由 FxTwitter `top`/`latest` 各两页提供，按帖子 ID 去重并只排除正文含 `gmgn.ai/` 链接的帖子；FxTwitter 404 作为空页，其他 X 采集异常降级并保留诊断，不阻断其他叙事材料；Grok 只负责独立研究和实体补充。
- Meme速递最终正文由程序统一加上监测开头和公开渠道免责声明；GMGN `data.zh_cn` 通过有头 Playwright + `xvfb-run` 获取并作为独立的 `GMGN补充：` 段落，Grok/实体材料使用 `Grok补充：` 段落；GMGN 浏览器失败只作为可选补充诊断。
- meme tg-discover 只读当前 Telegram 账号可见对话，搜索白名单之外的 0x 命中并输出候选报告，不自动扩充白名单。
- 细节见 控制台-Meme速递.md 和 控制台-Meme速递叙事规范.md。

## 巨鲸监控契约

- `巨鲸` 是独立监控链路，不进入 `tasks` 写作发布流程。
- 控制台维护两组地址配置：`链上` EVM 地址与 `Hyperliquid` 地址；前端不负责轮询逻辑。
- `whale-watch-worker` 使用 Blockscout v2 按地址轮询启用链，默认 `ethereum,base`，不监听全量 RPC。
- `whale-watch-hyperliquid-worker` 轮询 Hyperliquid `userFills`，只识别开多、开空、平多、平空成交。
- 两个 worker 首次看到地址时都只 seed 当前视图，不播报历史活动。
- 链上活动按 `address_id + chain_key + tx_hash + activity_fingerprint` 去重后写入 `whale_watch_activities`；Hyperliquid 活动按 `address_id + fill_key` 去重后写入 `whale_watch_hyperliquid_activities`。
- Hyperliquid 支持两级提醒：单笔门槛和滚动聚合窗口门槛；默认是 `500000` 美元单笔门槛、`1000000` 美元聚合门槛、`600` 秒窗口，提醒链接统一指向 `https://hyperbot.network/trader/{address}`。
- 两条链路正常活动都写入数据库并进入信息流插件，不再发送 Telegram 播报；同时向监督链路写入独立 heartbeat：`whale_watch` 与 `whale_watch_hyperliquid`。
- `whale_watch_hyperliquid` 的官方 Hyperliquid `info` 接口 5xx 故障按上游降级处理：地址状态和 heartbeat metadata 保留失败明细，heartbeat 写 `status=degraded` 且刷新成功时间，避免监督者误判 worker 进程失活；非上游故障仍写失败心跳。
- 模块细节见 `docs/OdAIly代码与整体设计/巨鲸.md`。
# 运行时代码边界补充

- 常驻服务、控制台、插件、监督者和维护命令只允许通过 SQLite repository factory 访问本地库。
- 运行时包入口不得导出 `Postgres*Repository`，导入运行时包不得加载 `packages.common.postgres`。
- 旧 Supabase/Postgres 读取只允许在一次性迁移命令 `storage-import-legacy` 或旧版本灾难回切审计中显式触达，不能作为新版本环境变量开关或 worker 分支保留。
