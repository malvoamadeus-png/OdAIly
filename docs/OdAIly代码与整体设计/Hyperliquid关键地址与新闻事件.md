# Hyperliquid关键地址与新闻事件

## 已确认的产品范围（2026-10-13）

目标是发现真实、突出、容易理解的新闻亮点，自动发现地址、持续监测行为与结果，最终形成快讯。地址标签是新闻事实，不是交易能力认证。2026-10-19 启用七类，2026-10-20 增加单资产高盈利、回吐/转换和清算方向，共十类，均强制挂后台。

只讨论 Hyperliquid 合约，覆盖加密货币、美股、贵金属、原油等资产，包含 builder-deployed perp DEX。保留完整 `dex:coin` 标识，不能把同名不同市场合并。不分析现货控制力、市场冲击、成交量/流动性占比，不考虑亏损占账户权益比例。

### 第一版全部方向

1. 巨大持仓：绝对名义金额、相当于代币市值的比例、占对应合约未平仓量的比例。
2. 巨额单资产浮盈、浮亏：BTC/ETH 初始门槛 500 万美元，其余资产 200 万美元。
3. 单资产高胜率地址的重要开仓、加仓、减仓、清仓、反手。
4. 单资产历史高盈利地址的重要操作。
5. 账户历史总盈利很高的地址的重要操作。
6. 账户总亏损高地址的重要操作，跨品种，只用官方全时段合约账户收益。
7. 大仓反手。
8. 巨额浮盈回吐、双向盈亏转换（浮盈转浮亏或浮亏转浮盈）。
9. 巨额亏损后继续加仓。
10. 大额平仓兑现盈利或确认亏损。
11. 大仓接近清算、实际清算。
12. 重要地址在同一资产上的多空分歧。
13. 首次被系统观察到的地址迅速建立大仓。

重要地址新仓初始金额为 300 万美元。门槛以本文件当前规则表为准；未验收方向的工程试验值明确标记。底层与控制台保留全部方向，正式上线按方向单独启用；当前正式启用下文列明的十个方向。

### 新闻触发与背景

亮点与触发独立：不必预先在聪明钱名单里，陌生地址也可能产生新闻。首次发现的已有仓位及盈亏只建立监测基线，不生成单地址新闻。除多空对决外，候选必须具备前后变化或明确成交动作；持仓大小是亮点，不是独立新闻触发。持仓数量不动但浮盈浮亏跨线、回吐、由盈转亏等新的结果可以触发。

只采用单资产胜率标签，不采用账户所有交易的整体胜率。准入要求该资产至少 5 个完整交易轮，胜率至少 70%。单资产胜率标签附统计起止时间、完整交易轮数、胜率、已实现盈亏；单资产和账户高盈利标签附统计范围与已实现盈亏。仅有近期成交或不完整交易轮不能冒充账户全历史。分批平仓不算多个完整交易轮。新地址仅表示本系统首次观察，不能推断新钱包或首次交易。

重要减仓看实际减少数量对应的动作金额，而不是剩余仓位大小。反手、兑现等以成交事实核验；轮询仓位数量变化只能证明快照间净变化，不足以证明完整成交路径。接近清算是观测时点价格距离，不能断言一定爆仓。

同一事件命中多个方向时合为一个候选，保留全部亮点和证据，不拆成重复快讯。建立基线后，以可核对的跨线、显著扩大、方向变化、平仓结果作为后续触发；首次发现不是跨线，未变化状态不发。多个地址只能称多个地址，不能假定独立主体；所述敞口仅限 Hyperliquid。

## 底层实现边界

独立包 `backend/packages/hyperliquid_news/`；复用公开 HTTP client，不改变旧手工地址成交提醒。持久化使用显式 SQLite 路径；测试仅使用临时库。网络采集不在事务内执行，成功响应才替换基线，失败不推断清仓。候选层只存结构化事实；由独立投递步骤创建任务，复用写作及强制挂后台分支。

接口与能力核验、统计口径、命令、失败处理和实际限制在本文件后续章节同步维护。未通过公开接口核验的能力必须标明，不能宣称已实现全网监测或完整历史。

## 当前代码与证据契约

- `models.py`：Decimal 数值、仓位、候选、规则；NaN/Infinity 拒绝进入证据。BTC/ETH 只指主 DEX 原始标识，不把 `xyz:BTC` 等不同合约擅自归为相同市场。
- `client.py`：`perpDexs`、按 DEX 的 `metaAndAssetCtxs` / `clearinghouseState`、`recentTrades`、排行榜、`userFillsByTime`。命名空间完整保留。
- `history.py`：排除现货成交，按同一资产从零仓位到清仓或反手统计完整轮；缺失开仓、数量路径断裂、同毫秒顺序无法唯一还原的轮不进入胜率。`tid` 是哈希，不是执行序号；成交去重键为 `time + coin + tid`。
- `detector.py`：单地址同资产事件合并；持仓/占比在至少重要动作金额的数量变化下跨线或扩大档位触发，盈亏以可比较快照的变化跨线、扩大档位或相对上次新闻基准的显著绝对变化触发，保留轮次浮盈峰值；地址亮点、成交动作、清算事实、多空分歧作为结构化证据。
- `store.py`：`hl_news_addresses / hl_news_fills / hl_news_state / hl_news_normal_state / hl_news_candidates / hl_news_metadata`。账户监测与普通八方向使用独立基线，事务内原子提交候选与状态。
- `service.py`：`NewsMonitor.run_once()` 采集普通八方向，正式 worker 与 `AccountProfitMonitor` 同进程运行。命中普通方向后按需读取 `portfolio.perpAllTime.pnlHistory`，选取操作时间前最近样本供稿件尾部使用；不以成交区间重算替代账户总盈亏。
- `__main__.py`：仅提供临时测试库离线回放。不会读取生产数据库配置，退出后临时库销毁。

### 候选证据

候选包含 `key / observed_ms / addresses / coin / kinds / evidence`。`evidence` 保存前后仓位、占比分母、实际成交键与开平仓金额、历史统计范围与轮数、浮盈峰值、阈值规则等。在线采集另保存地址发现来源和各 DEX 快照返回时间。

同一地址同一资产同一观察时点只生成一个候选，`kinds` 可以同时命中多个方向。多空分歧是独立多地址事实；默认比较最近 15 分钟内的成功快照，证据中保留各快照时间，不能写成所有地址在同一瞬间建仓。已有分歧在参与地址采样失败或过期时不因数据缺失而重新触发；双方方向和金额档位发生变化可触发，确认分歧消失后允许重新出现。

成交动作金额按 `startPosition + side + sz` 分离开仓和平仓部分，反手成交不能整笔计入开仓；每个方向同时保存按数量加权的开平仓成交均价。仓位变化不能仅靠名义金额判断，价格上涨本身不是加仓；同仓位估值变化达到重要金额时可触发大仓状态变化，但文案不能写成增仓。大仓反手记录的是两个成功快照间的净方向变化，不保证重建了中间每一次反手。标题按证据写同一资产的平仓方向、金额及反向开仓方向、金额。

自行计算的历史金额口径为所取得合约成交的 `closedPnl - fee`，不含资金费，不是账户权益收益、排行榜 PnL 或可证明的全历史总盈利。USDC/USDH 手续费按美元稳定币名义口径合计；其他 feeToken 未接换算，标记货币不完整，并禁用依赖净盈利/胜率的对应标签。统计同时保存请求窗口、实际第一/最后一笔时间、API 分页覆盖状态。默认统计窗口 90 天，可通过构造参数修改；已留存成交不因 API 历史滚动而删除。

大额主动平仓只统计非清算成交的平仓金额和 `closedPnl`；实际清算成交不得归入主动兑现。实际清算只接受成交明确提供 `liquidation.liquidatedUser` 等于当前地址的证据；仓位消失不能推断清算。历史回放对主动平仓和实际清算使用相同区分。

### 采集预算与失败处理

普通八方向每轮轮询 2 个已发现地址，账户方向沿用独立到期调度；市场目录每小时缓存，最近成交按市场轮转补充地址。该采样不是全市场实时订阅，覆盖受地址池、DEX 数量和请求预算限制。账户两方向资格复核仍使用官方榜单与 portfolio。

HTTP 采集以保守估算将本客户端限制到 600 request-weight/分钟，重试也计入节奏；Hyperliquid 官方 IP 总额度为 1,200/分钟，与同 IP 其他服务仍须协调。每请求默认超时 20 秒，最多尝试 3 次；请求参数可在构造 client 时指定。所有网络请求在 SQLite 事务之外。

历史每页最多 2,000 条、默认最多 6 页，分页保留最后毫秒的包含边界，避免漏掉同一毫秒的成交。页预算不足可在下一轮续取；同一毫秒塞满 2,000 条且无法向前推进，标记 `timestamp_saturated`，不宣称历史完整。API 最近 10,000 条保留限制即使分页结束也仍然存在。

任一 DEX 仓位请求失败，当前地址本轮整体失败，上次成功基线不变，不推断清仓。普通八方向和账户方向共用常驻进程，使用分开的状态表与调度；普通方向启动时先建立独立基线。portfolio 尾部样本查询失败不阻断事件，但不生成缺失的盈亏数值。

## 能力核验结果（2026-10-13）

核验是公开 API 的只读短请求，没有启动本地产品 worker，没有查询生产状态。真实地址不写入公开文档或夹具。

实际取得 `xyz` 的 134 个市场，其中包含 `xyz:AAPL / xyz:GOLD / xyz:CL / xyz:BRENTOIL`；最近原油成交返回买卖双方 `users`；按 `dex=xyz` 请求地址仓位可取得 `szi / positionValue / unrealizedPnl / liquidationPx`；`userFillsByTime` 实际返回含 `xyz:` 市场的成交，含 `startPosition / side / sz / closedPnl / fee / feeToken`。具体清算成交没有在本次样本中取得，不能宣称实盘清算识别已经验证。

| 方向 | 底层状态 | 数据与验证边界 |
|---|---|---|
| 巨大持仓金额、OI 占比 | 已实现；接口与离线验证 | OI 名义金额为 `openInterest × markPx`，只提供描述性占比 |
| 持仓相当于市值比例 | CoinGecko 适配与离线测试已实现 | 官方服务器免费无 key 接口已真实返回 BTC/ETH/HYPE 市值；精确 coin ID 映射需配置 |
| 巨额浮盈浮亏 | 已实现；接口与离线验证 | 同一持仓的盈亏扩大达到变化额门槛才触发；浮亏收窄不属于巨额浮亏事件 |
| 单资产高胜率地址操作 | 已实现；成交字段与离线验证 | 限于取得的完整轮，固定附轮数与实际时间范围 |
| 单资产高盈利地址操作 | 已实现；成交字段与离线验证 | 所观察成交已实现盈亏，不是可证明的全历史盈利 |
| 账户高盈利地址操作 | 官方周期榜单与观察成交两种事实已实现 | 官方 PnL 直接使用，标注周期/来源；自行计算成交合计不含资金费，不能混为同一口径 |
| 账户总亏损高地址操作 | 用户批准正式接入 | 全时段合约账户亏损≥2000万美元＋净操作≥300万美元 |
| 大仓反手 | 已实现；离线验证 | 净方向快照变化；采样间多次反手可能遗漏 |
| 浮盈回吐、由盈转亏 | 已实现；离线验证 | 峰值从成功观测起积累，历史未观察峰值不能补造 |
| 亏损加仓 | 已实现；离线验证 | 前次浮亏、实际开仓成交与数量增长一起核验 |
| 大额兑现 | 已实现；离线验证 | 当前平仓结果或新完成完整轮的累计结果 |
| 接近清算 | 已实现；仓位字段与离线验证 | 观测距离；不是清算预测，null 保留为不可判断 |
| 实际清算 | 条件适配与离线验证 | 需 API 明确返回本地址 liquidation 事实；实盘样本尚待取得 |
| 多空分歧 | 已实现；离线验证 | 限于采样新鲜窗口与有历史亮点的地址，不推断独立主体 |
| 新观察地址迅速建仓 | 已实现；离线验证 | 成功建立初始基线后才判定新动作；首次看到已存在的大仓仅建基线，不出状态稿 |
| 自动发现地址 | 已实现；公开接口与离线集成验证 | 排行榜及大额最近成交采样，不保证发现静默大仓或全部地址 |

公开数据路径可以支撑主要方向；目前无法仅凭这些接口保证全历史统计、全网实时地址覆盖或恢复未观察的中间行为。这些限制留作下一轮产品取舍，当前不因此删除对应方向。

## 地址范围与属性查询（2026-10-13 修订）

之前“最近成交的双方都进池、只有 allTime 盈利榜排序”的实现不足以满足发现目标，已替换。当前明确分两层：

1. **候选地址入口**：官方日/周/月/全部时间正负 PnL 榜单的有界并集；最近成交样本合计至少 300 万美元的地址；后续可显式加入单资产榜单/人工指定地址（不自动调用尚未核验的第三方 API）。没有遍历全网地址。
2. **属性查询资格**：候选来自上述榜单或大额成交，或者轻量持仓查询显示至少 300 万美元仓位、巨额浮盈亏、突出 OI/市值占比，才回取历史成交并统计资产属性。没有资格的地址跳过历史接口，记录 `not_queried_no_eligibility`；以后达到资格再从完整请求窗口开始回取。

后续操作是否播报仍看标签与重要动作，不因出现在榜单就立即生成操作新闻。官方盈利事实保存在 `official_account_performance`，包含不同周期的 `pnl / rank / side / observed_ms`，最多使用 24 小时内取得的值。它可直接触发 `official_account_high_profit` 标签，不依赖本系统重算账户已实现盈亏。自行统计的账户成交收益保留为不同标签和字段。

**单资产高胜率**严格查询当前事件合约的历史：原油胜率不能触发 BTC 的胜率标签，更不能用整体账户胜率代替。代码标签明确改为 `asset_high_win_rate`。目前范围是“先在其他入口发现地址，再查其单资产胜率”；并未实现“直接找出全网原油胜率排名前列的地址”。单资产榜单入口是否可行，须以第三方真实数据/API 核验为准。

发现池仍有 500 个地址上限、每轮 10 个地址的工程预算；尚未完成地址淘汰和重点地址优先调度。因此当前是明确可验证的有界发现方案，不是已完成全网实时监测。大额成交采样也会漏掉不在返回样本里的分批成交和没有近期成交的存量大仓。

## 限量测试与写作接入（2026-10-13）

用户确认不增加新闻价值筛选。每条硬规则事件先做内部事件/行为防重，再运行共享搜索者跨来源查重；不调用判断者或发布者新闻价值模型。搜索者复核只判断同一事实是否已报道，不判断新闻价值。`dispatch.py` 用事件键与结构化行为指纹，在同一 SQLite 事务中落库 task 与投递映射；队列提交失败保留同一个 task 重试。硬规则状态持续不变已经在检测层抑制，投递层再做持久化去重。

Hyperliquid 按场景使用独立、可版本化 Prompt：大仓持仓变化、单资产浮盈亏变化、单资产交易表现、账户盈亏与操作、大仓反手、浮盈回吐、浮亏加仓、平仓兑现、清算、多空分歧、新观察地址。单资产高盈利与高胜率共用交易表现 Prompt，账户盈利与亏损共用账户结果 Prompt。编写者1只写标题与正文，不写固定开头、地址尾部或链接。正式写作和编辑预览绕过全局特色模式。标题平实直述；高胜率标题加“近期”，正文称谓统一以“某地址”引出，后续用“其”。正文需自然交代与该次操作有关的胜率、交易轮数和统计周期，不能在尾部重复。定稿固定以 `Odaily星球日报讯 据Odaily监测，` 开头。尾部始终附地址；只有事件时点前 1 小时内取得的官方 `perpAllTime` 合约账户总盈亏才附数值，不显示样本时间，过旧或缺失时不放总盈亏占位。不将有限成交区间盈亏冒称总盈亏。账户总盈亏包含未实现盈亏，不称已实现盈利。开平仓均有成交均价时程序补充均价并压缩无意义小数。金额低于 1 亿美元按整数万美元表达，达到 1 亿美元后以亿美元表达，最多两位小数并省略尾零；胜率、占比、回吐比例和清算距离用整数百分比，取整改变原值时加“约”。BTC / ETH 数量最多两位小数。多单是仓位方向，不写成“买入”；没有成交或前后仓位证据时用“持有”，不推断开仓或加仓。

编写者2来源分支复用 `format_brief`，定稿固定开头 `Odaily星球日报讯 据Odaily监测，`。程序尾部始终附地址；账户总盈亏只显示事件观察时刻前 1 小时内的官方 Portfolio `perpAllTime` / `allTime` 样本，不显示样本时间，过旧或缺失时不补盈亏占位。候选样本须带 `hyperliquid_portfolio` 来源和包含未实现盈亏的官方口径；在事件观察时刻之前选最新一条，旧的 `official_account_total_pnl` 不得遮住较新的合规 allTime 样本。公开排行榜、成交窗口自算盈亏和来源不明的旧字段均不作为总盈亏。账户累计盈利或亏损标题必须明确出现地址主体；定稿清除“官方口径含浮盈亏”等机械括号声明。完整证据仍保留 `dex:coin`；新闻标题与正文展示冒号后的 ticker（例如 `xyz:SKHY` 显示为 `SKHY`），不据此合并不同 DEX 的市场。单资产高胜率标题加“近期”，统计轮数、胜率和周期在正文只写一次。原文链接使用首个目标地址的 Hyperbot 页面，`sourceUrl` 不让模型生成。

`hyperliquid_news` 以 `judged` 状态进入共享 `search / write / format_publish / publish`；该状态表示硬规则已准入，不执行判断者。搜索者通过后为 `deduped`，重复为 `duplicate`，失败为 `search_failed`。发布阶段强制挂后台，与常规/AI信源发布开关无关，`isPublish=false / isPush=false`，使用稳定 task Idempotency-Key。正文、Prompt 版本、模型、流程时间及提交结果都复用共享流水线留存。

控制台独立一级标签细节见 `控制台-Hyperliquid监测.md`。正式常驻 worker 同时运行普通八方向和账户高盈利/总亏损方向；十方向投递限制对手工 dispatch 同样生效。

服务器命令（本地禁止在线采集与产品服务，只允许临时库测试/回放）：

```bash
.venv/bin/python backend/src/main.py hyperliquid-news init
.venv/bin/python backend/src/main.py hyperliquid-news collect --addresses-per-pass 6 --leaderboard-seeds 2 --markets-per-discovery 3
.venv/bin/python backend/src/main.py hyperliquid-news dispatch --limit 3
.venv/bin/python backend/src/main.py hyperliquid-news status --page 0
.venv/bin/python backend/src/main.py hyperliquid-news activate-prompt
# preview --task-ids 使用具有变化证据的实际任务 ID；首轮三个静态样稿不能再生成新闻预览
```

`init` 初始化主 SQLite 独立表及专用 Prompt；不覆盖已经发布的 Prompt 版本。`collect` 只取得公开事实、不投递；可传 `--market-cap-mapping` 指向服务器本地运行配置。`dispatch` 最多按 limit 投递，可以用 `--event-keys` 精确指定样稿事件；超出 1..100 拒绝执行。`status` 查看候选与共享流水线结果。`activate-prompt` 可用 `--template-key` 指定任一 `hyperliquid_*_writer` 场景模板，读取已提交的专用模板全文，事务内创建并激活新版本；内容相同不新增版本，旧版本不覆盖。定稿还会确定性压缩金额、百分比和数量，并将“名义金额 / 名义价值 / 参考价 / 执行价”等术语转换为读者表达。`preview` 接受 1..10 个有变化证据的已有 Hyperliquid task，缺少变化证据会拒绝，调用相同编写者1/编写者2路径，将修订结果保存到事件关联元数据；不修改原任务状态、不入队、不调用挂稿或发布接口。写作失败不覆盖已成功预览。采集、生成、投递分开，可单独复盘和重试。

更新场景模板时，在官方服务器逐个执行 `hyperliquid-news activate-prompt --template-key hyperliquid_asset_performance_writer` 等命令；模板版本按场景独立激活，服务重启后写作 worker 使用新版本。

### 变化性准入修正

`detector.py` 第一次成功快照仍完整保存 signals、峰值和仓位，但不因大仓、占比、巨额浮盈浮亏或接近清算的静态状态出候选。巨大持仓和占比跨线需前后净数量变化按当前估值至少达到重要动作线（当前 300 万美元），不因价格或分母变化独立出持仓稿；实际重要成交继续走动作规则。浮盈浮亏以可核对的前后值变化跨线或扩大档位触发，数量可以不变。首次发现此前未见的持仓，没有明确成交也不能当成新建仓。

变化候选附 `news_change`，包括前后观察时间、数量、持仓价值和浮盈亏；写作材料提供前后事实与时间，专用 Prompt 要求在正文说清变化。仅观察到数量净变化时不虚构中间逐笔交易。多空对决为当前明确静态例外。

### 全方向链路补齐与搜索者恢复

内部防重 `hl_news_dispatch` 负责避免同一结构化事件重复创建任务；搜索者负责与 Odaily 已发布快讯、运行中 X/竞品候选、近期已处理内容（包含已收集的 Lookonchain 内容）查重。没有全网 X 实时搜索，未采集到的帖子不在本地候选范围。恢复跨来源查重不恢复新闻价值筛选。

投递的 tasks.title/content 是确定性中文事实摘要，不是整份证据 JSON；包含地址、资产、前后仓位/盈亏、动作方向金额时间、相关历史亮点、回吐、清算或多空角色。原始证据仍在 raw_payload。固定 Hyperbot 主页只是地址链接，不是事件标识；相同主页不精确判重。涉及 Hyperliquid 的相同通用标题和高向量相似度也不直接判重，召回后交给共享搜索者 AI 比较具体事实，防止挡掉同一地址后续动作。普通来源原有直接判重阈值不变。搜索失败阻断写稿，重复记录实际命中对象，后台展示搜索时间、对象和复核资料。

13 个产品方向拆成 25 个离线情形，验证检测 → 变化性准入 → 可读搜索材料 → 可领取搜索任务 → 专用写作材料 → 固定组装。单资产高胜率分别覆盖开仓、加仓、减仓、清仓、反手；高资产盈利、高账户盈利（成交/官方周期）、历史大亏/连亏动作分别覆盖；大额平仓分盈利和亏损。真实全方向样本仍取决于市场实际发生，不能用离线验证冒充实盘已经全部命中。

成交动作保存开多/开空/平多/平空各自金额和首尾成交时间；净快照重要数量变化可以形成大仓/历史亮点地址的重要加减仓、清仓或反手，并把净变化估值与真实成交金额分开。亏损后净加仓也能在成交不可得时触发。

数量未变且本轮没有开平仓成交时，以同一可比仓位观察浮盈峰值和回吐。减仓、增仓、先平后开导致原始浮盈变化，不冒充被动价格回撤；变化后重建可比峰值。已超线浮盈浮亏允许相对上次新闻基准累计改变一个对应盈亏门槛后再次播报，不只等待翻倍。基准金额/时间保留，内部指纹含盈亏变化或净仓位变化，以免把新事件误判成重放。

单资产交易日期使用该资产实际第一/最后成交时间；账户日期独立，不能拿其他资产交易跨度扩充单资产胜率范围。市值精确映射、免费 API 真实返回、胜率历史完整性和实盘清算成交等限制仍按能力表记录，没有擅自删掉方向。

独立写作模板要求所有 Hyperliquid 标题绕过特色模式，直接写明最重要的成绩/结果和本次操作；正文必须再次体现这些核心信息。单资产高胜率操作需同时写明该资产胜率与此次动作，统计周期依据实际数据字段，不够 5 轮的地址不能使用该方向标题。

### 地址发现、资格与调度

- `account_monitor.py` 每小时读取官方榜单，对返回的所有 day/week/month/allTime 达标地址取并集，不截取测试 top-N，不受通用测试发现池的 500 地址上限阻挡。此来源仍只是榜单返回范围，不代表全网完整覆盖。
- 合约目录每小时缓存一次；每 5 分钟轮转一个市场的最近成交采样，用现有金额规则补充榜单外候选。成交采样并不覆盖完整交易窗口，地址必须通过官方 portfolio 资格核验才能成为正式监测对象。
- 来源仍存在 `hl_news_addresses`；新表 `hl_news_account_pool` 单独保存本方向的 tier / qualified / next_poll_ms / last_action_ms。历史来源、成交与状态不因降级删除，未来其他方向可复用。已有测试种子首次进入正式监测也须重新核验并建立新基线；榜单直接达标的新地址可取得监测预算优先级，但仍须 portfolio 核验，不凭榜单直接发稿。
- 只读 portfolio 的 perpDay/perpWeek/perpMonth/perpAllTime，不混入现货曲线。请求缓存最多 1 小时，收益样本超过 24 小时或在未来则不使用；本次操作形成候选后，再请求一次官方收益确认仍达标。请求失败保留旧基线、5 分钟后重试，不冒充零收益或清仓。
- 重要持仓或最近一小时有成交的达标地址，下一次检查目标间隔 3 分钟；闲置达标地址 30 分钟；不达标地址降级后一天复核。榜单或大额成交重新发现可提前唤醒。不删除地址，只释放高频监测预算。
- 每轮最多处理 10 个地址，保留至少一个新候选/不达标复核名额，其余按最早到期时间服务达标地址，避免活跃地址或新地址独占预算。3 分钟是调度目标，不是覆盖保证；实际延迟由请求预算、DEX 数量和地址数量决定。
- 正式客户端预算为每分钟 300 request-weight，重试同样计入，给同 IP 旧手工巨鲸服务留出余量。首次只取仓位基线，不回填 90 天交易；后续先做轻量仓位检查，数量变化时增量取成交；数量未变也每 15 分钟补查一次成交，覆盖快照间开平仓抵消的行为。每次最多 2 页，保留包含边界并续取；未取完分页先缓存并保留原基线，取完整后再生成动作事件，避免把同一次操作拆成多条。最长补取最近一天的上线后成交；中断更久的成交不能宣称补齐。
- 任一 DEX 仓位或成交请求失败，本地址不推进成功基线；收益降级后再次达标重新建基线，不把未监测期间的操作当实时新闻。持续相等的状态不出稿，真实连续同金额减仓通过前后数量区分，不能误判同一行为。

### 正式投递边界与运行

`production_account_profit` 元数据记录十个 `enabled_scenarios` 及 `scenario_started_ms`。账户高盈利/总亏损保留各自上线起点、资格和新鲜度校验；普通八方向只接收新普通基线生成的事件，测试回放不得投递。投递查询和创建 task 的事务内均按方向、起点及证据检查。共享流水线行为防重、跨来源查重和后台提交保持有效。

服务 `deploy/odaily-hyperliquid-account-profit.service` 使用 `hyperliquid-news run-account-profit`，每轮采集普通八方向和账户两方向，并投递最多 10 条；循环间隔 30 秒，异常写入 `last_pass` 并重试。日志以 JSON 行写入 stdout/journald：外层 `account_profit_worker.*` 记录轮次及账户监控、普通监控、派发各阶段的开始/结束/异常；`account_monitor.*` 记录榜单刷新、市场目录、轮转成交发现、地址检查、收益资格、仓位、成交历史和候选复核的耗时与结果。地址异常包含失败阶段；分页未完成会记录延后原因；派发结果附 `event_observed_ms` 与 `dispatch_delay_ms`，用于区分监测发现、派发和后续流水线延迟。旧手工 `odaily-whale-watch-hyperliquid.service` 不受此方向开关控制。

服务器同步已提交代码并激活模板后执行：

```bash
.venv/bin/python backend/src/main.py hyperliquid-news enable-approved-scenarios
# 普通八方向以独立基线启动，只投递上线后的新事件
.venv/bin/python backend/src/main.py hyperliquid-news run-account-profit --once
.venv/bin/python backend/src/main.py hyperliquid-news prune-tested-cases
install -m 644 deploy/odaily-hyperliquid-account-profit.service /etc/systemd/system/
systemctl daemon-reload
systemctl enable --now odaily-hyperliquid-account-profit.service
```

重复 enable 不改变已经启用的上线起点；重启从持久化调度、基线和成交键继续。停止常驻采集使用 `systemctl stop odaily-hyperliquid-account-profit.service`；停止投递还需关闭 production_account_profit.enabled，不能把停采集等同于撤销待投递事件。

## 账户净操作与成交顺序修正（2026-10-30，已部署）

账户高盈利与账户总亏损操作统一采用同一资产、同一前后成功快照间的净数量变化，以当前仓位参考价估值；清仓使用前序快照参考价。反手使用有符号数量之差判断重要操作，标题仍分别描述旧方向平仓和新方向开仓。价格变化不能制造加仓，开平仓周转金额及不同价格的成交额之差不能充作净操作。两方向均需净操作至少300万美元；零净变化或未达门槛不产生账户操作候选，其他独立方向仍按各自规则判断。

`actions.py.snapshot_net_change` 由采集筛选、投递门控和写作层复用。`account_event` 保存 `net_action_notional_usd` 与 `net_position_change`；`production_allowed` 从前后仓位重新计算并检查，拦截修复前已生成但尚未投递的无效候选。缺少可估值仓位证据时不放行。已挂后台的历史稿不会自动撤回或覆盖。

`actions.execution_sequence` 按时间和 `startPosition + side + sz` 的数量连续性还原，合并连续同类操作并保存起止时间、数量和成交额；同毫秒排序不唯一或路径断裂时为 null，不把 tid 当执行序号。写作白名单保留该顺序及各段时间，并额外提供 `current_position_status`（持仓/空仓）。累计开平仓字段继续保留，但不代表先后。格式层不再补造“平仓后再开仓”，并拒绝与完整顺序证据冲突的明确先后表述。

同方向标题确定性概括净操作：“增持约XX万美元空单/多单”“减少约XX万美元空单/多单”，全部平仓写清仓；金额为净数量的估值，不能冒称成交额。正文先交代净结果及当前仓位，可在顺序证据支持时展开多步操作。账户专用 Prompt 与通用模板同步约束此规则。2026-10-30经用户授权部署 `bee8757`，按现有 `activate-prompt` 流程激活账户模板v4及通用模板v13。

## 十方向事实边界统一修正（2026-10-30，已部署）

本节将前述账户净操作要求扩展到全部正式方向。四种地址亮点（单资产高胜率、单资产高盈利、账户高盈利、账户总亏损）均以净数量变化估值判断重要操作，不用窗口毛成交额；各自金额门槛不变。巨亏后加仓按同方向净增仓，并排除成交中原仓位曾归零或反转的窗口，证据 `actions.position_episode_closed` 标记原持仓中断。主动平仓兑现、实际清算保持实际成交事实，巨额浮盈亏和回吐保持未实现盈亏事实，接近清算保持风险状态，不对十类统一套用净操作过滤。

普通监测的 `normal_pending_fills:<address>` 元数据保存未完成分页的成交及游标，分页不完整时更新轮询错误和覆盖状态，不提交部分候选、不推进成功基线；完整后合并去重、一次性提交并清空 pending。账户补查继续使用独立 `account_pending_fills`。投递门控拒绝分页未完整的旧候选，并按命中方向复核净门槛；多标签事件只要存在有效的正式方向仍可按该方向投递。

所有正式方向共用成交顺序约束和空仓结果兜底。`actions.execution_sequence` 不能由总额或 tid 顺序推断；没有完整顺序时，不写确定先后。格式层校验常见连接词串联的开平仓先后表述，允许正文描述完整路径中的连续两段，不要求正文复述整个窗口；此规则不是对任意自然语言的完整语义核验，其他写法仍受Prompt事实约束。单资产亮点标题也采用净增持、净减少或清仓；巨亏后加仓标题使用净增仓估值。`single_reversal_legs` 只在完整路径恰好平掉旧方向、建立最终新方向两段且数量与快照吻合时提供反手成交金额，多次反手或缺路径用前后方向与最终仓位价值。

大额主动平仓兑现优先使用真实已实现盈亏标题，不被普通减仓标题或地址亮点覆盖；Prompt优先级相应提前兑现、反手和巨亏后加仓。`liquidated_long_notional / liquidated_short_notional` 区分实际被清算方向，按平仓部分计量，不把反手超出旧仓的开仓部分计入清算。清算后的新方向不能替代原清算方向；旧候选缺少清算方向证据时，标题只写合约清算及金额。四舍五入及账户收益口径规则保持原契约。
