# 商务快讯追踪文档

## 目标与范围

- 面向多个商务客户群接收客户文字消息；SoSo 仅作为首个测试群，不为其单独建立接收逻辑。
- 首版生产只启用 Soso 群；其他自动发现群保持未启用，后续由控制台维护客户映射后再启用。
- 每条 Telegram 消息独立判断，不把多条消息拼成一份素材。图片、文件、视频、媒体说明文字等非纯文本消息跳过。
- 当前只处理快讯。活动消息保留为待接 API 的状态，不进入写作和发布；其他、无法判断及失败内容丢弃。
- 快讯挂入 Odaily 后台后，在插件信息流写一条极短提示。人工审核与向客户回复不属于本流程。

## 分类与脱水约定

- 所有达到 15 字门槛的纯文字消息都必须得到 Writer4 AI 分类结果；规则只提供边界和示例，不用关键词命中替代 AI 判断。
- Writer4 分类为 `newsflash`、`activity`、`long_content`、`other` 或 `uncertain`。`long_content`、`other` 和 `uncertain` 都跳过，不进入写作；分类失败、结构不合法或 AI 调用失败也丢弃。
- 快讯与活动同时出现时，只要原文包含可独立报道的事实事件，就分类为 `newsflash`，围绕该事件组稿，并可保留理解事件所需的活动事实。活动本身有参与任务，不会自动把产品上线、研究发布或数据变化降成活动。
- `activity` 指正文主要在邀请或说明用户参加有明确参与行为和奖励机制的促销：交易赛、打卡、任务、抽奖、积分兑换、奖励领取等。是否出现“活动”二字不作为单独判据。
- `newsflash` 指主体做了或说了什么、产品或服务发生什么变化、研究报告发布了什么观点，以及可报道的数据或事件结果。明确的 APR、净流入、奖励发放人数等数据报道仍可属于快讯；是否存在参与任务和领取条件是区分活动与报道的关键。
- `long_content` 指客户主要只提供外链，让读者阅读长篇文章、研报或其他长内容，群消息本身没有可独立组成快讯的事实摘要。只有链接或“详情见链接”不因此成为快讯。
- 快讯再由 Writer4 识别写作属性 `plain` 或 `promotional`。`plain` 尽量保留原文措辞和事实，只做标题提炼、正文整理及固定词语规范；`promotional` 才做完整脱水。
- 脱水只改写客户原文中的夸张宣传表达，不扩写、不核验外部事实、不改变数字、主体、时间、条件或事件关系。去掉或按语境弱化“领先”“首个”“首发”等绝对化表达；“全网首发黄金 CFD”这类语法上不能直接删除的表述改为“推出/上线黄金 CFD”；“瓜分”改为“分配”。这些词是判断线索，不是脱离语境的全局替换词表。
- `activity` 不做脱水，保留原文并等待活动 API；不因活动文案夸张而改写。

### 已确认案例归类

| 案例 | 分类 | Writer4 处理口径 |
| --- | --- | --- |
| Gate Live 直播打卡、互动抽奖 iPhone / GT / USDT | 活动 | 有打卡、互动和抽奖参与机制；原文保留待 API |
| Gate 合约积分空投，积分兑换 SKHYG / 仓位体验券 | 活动 | 核心是限时兑换和领取条件；原文保留待 API |
| Gate 上线 Ritual 及 CandyDrop 奖池 | 快讯 | Ritual 上线是可独立报道的产品事件；保留相关空投事实，“瓜分”改“分配” |
| ZEC 现货 ETF 单日净流入 | 朴素快讯 | 数据及时间范围原样保留，不做宣传性改写 |
| Gate Launchpool XAUT 池 APR 数据 | 朴素快讯 | 按平台当前收益率信息报道；没有明确用户任务或比赛招募，不因出现质押奖励而归为活动 |
| Gate 黄金 CFD 周末交易、“全网首发” | 宣传性快讯 | 保留交易时段、开放范围和杠杆事实；将“全网首发”按语法改为“推出/上线” |
| Gate WCTC 交易赛、战队、奖池及多赛道 | 活动 | 以报名参赛、交易任务和奖池为核心；原文保留待 API |
| Gate 研究院时间切片市场及事件合约研究 | 朴素快讯 | 研究内容及产品事实按原意整理，不添加评价 |
| Bitget 同行计划已发放奖励及人数统计 | 朴素快讯 | 报道已完成的奖励发放结果，不是邀请用户参加活动 |
| Bitget 联合发布研报并计划推出股票基差策略 | 宣传性快讯 | 保留研究结论、模拟数据和合作分工；删去“首个”等绝对化宣传词 |
| Bitget CFD 王者冠军赛、盲盒及交易排名奖励 | 活动 | 以报名时间、交易任务和奖励规则为核心；原文保留待 API |

Writer4 必须按上述样例区分“活动正在发生”与“报道活动/产品的数据结果”。例如，进行中的 Launchpool APR 报道仍按既定案例分类为快讯；有明确兑换、打卡、比赛或抽奖参与要求的内容分类为活动。若文本缺少可确认的主事件且无法稳定区分，返回 `uncertain` 并丢弃。

## 群发现与接收

- 一个专用常驻 worker 使用同一个 Telegram Bot API token 以 `getUpdates` 长轮询接收所有群消息。长轮询超时建议为 50 秒；有更新时立即返回并交给本地处理队列，消息收到后目标为 5 秒内开始处理。这里不使用每群一次的 5 秒轮询。
- 群数增加不会增加 Telegram 轮询次数。一个接收器快速持久化更新，后续 AI 与写作由全局有界 worker 并发处理；首版并发数设为 4，可依据队列积压和模型耗时调整。
- 商务接收器独立负责商务群消息；Writer3“此前消息”与本流程无关。已弃用的 Writer3 Telegram callback 查询入口已移除，不能与商务接收器竞争同一个 Bot token。
- Telegram bot 需允许加入群组并关闭 Privacy mode，才能收到群内普通文字。
- Telegram 更新订阅包含群消息和 `my_chat_member` 群成员变更事件。收到 bot 入群事件或该群的首条更新时，自动按 `chat_id` 登记群 ID、群名和发现时间，初始状态为未启用。控制台配置该群的客户名并启用后，才处理此后的新消息；启用前和停用期间的消息不回放。
- 所有已启用客户群中的普通文字消息都进入规则筛选，不按发送者白名单或是否为其他 bot 过滤。过滤阈值、活动识别和闲聊识别由后续规则及 Writer4 完成；只排除接收 bot 自己发出的消息，避免自触发。
- 收件器把 Telegram `update_id`、`chat_id`、`message_id`、发送者标识和文字消息写入主 SQLite 收件箱，并在同一事务中推进 update offset。唯一键防止重复更新。网络长轮询和 AI 请求期间不持有 SQLite 写事务。
- 首次启动先快速消费 Telegram 已积压的 update，只登记其中出现的群并推进游标，不把启动前消息放进收件箱；后续收到的新 update 才进入处理。游标与新消息入库在同一事务提交。

## 单条消息处理

1. 仅处理已启用客户群的新文字消息。正文移除空白和 URL 后，按 Unicode 字符数计算长度；少于 15 字立即丢弃，不调用 AI。达到 15 字是硬门槛。
2. URL 不进入编写者2正文。优先取主消息中的第一个有效 URL；主消息没有 URL 时，扫描同群、同发送者的上一条和下一条已收到消息，找到 URL 后作为原文链接。只读取扫描时已存在的邻条，不等待后续消息；不把邻条正文合并进素材。两侧都有 URL 时优先取上一条。
3. 对达到门槛的消息只调用一次 Writer4 AI，使用现有 `odaily-gpt-writer` 快速模型配置。结构化 AI 结果包含分类、简短判定理由；快讯还包含 `plain/promotional` 属性、标题和正文。Writer4 同时完成分类和快讯初稿，不额外调用分类模型。
4. Writer4 按“分类与脱水约定”判断。分类为活动时保留原文等待 API；`long_content`、`other`、`uncertain`、结构无效或 AI 调用失败时丢弃，不重试。
5. Writer4 对快讯从原文提取或归纳标题和正文。朴素快讯保守整理；宣传性快讯按约定脱水，尽量保留原意、事实、表达顺序，不补充外部事实。没有明确标题时，只能从原文概括；无法可靠概括则丢弃。活动无需脱水。
6. Writer4 输出快讯后，仅调用现有编写者2格式整理能力，再使用现有 Push API 挂后台，固定 `isPublish=false`、`isPush=false`。找到原文链接时传入 `sourceUrl`，没有链接则省略，不做缺链接标记。此路径不经过编写者1或编写者3，也不进入旧 `write_flow` 队列。
7. Push API 成功后，在插件信息流写入一条且仅一条提示：`{客户名}商务有新消息`。不附正文、链接、操作按钮或额外说明。活动、跳过和失败消息不写插件提示。

## 状态与失败处理

- 收件箱按 `chat_id + message_id` 幂等保存，记录群/发送者/时间等元数据、AI 分类与简短理由、Writer4 结果、来源链接、处理状态和后台推送结果。收件事务提交后才确认 Telegram offset，服务重启可以继续处理已收件但尚未开始的消息。
- `business_telegram_recent_messages` 暂存启用群内最近 10 分钟的相邻消息 ID、发送者和 URL，用于同发送者上一条/下一条链接扫描；正文不拼接到候选消息，过期行随接收新消息清理。
- 业务状态至少包括：待处理、字数过滤、非文本跳过、长内容跳过、其他跳过、不确定跳过、活动待接 API、待格式整理、已挂后台、失败丢弃。活动待接 API 保留客户原文，不调用 Writer2、Push API 或插件提醒。
- 长度不达标、分类为其他或不确定、AI / Writer4 / Writer2 失败及 Push API 明确失败，都标记为已丢弃，不自动重试、不发业务提醒。进程在处理前意外退出时，可恢复尚未开始的收件行；已明确失败的行不恢复。
- 已挂后台快讯及活动待接 API 原文保留。跳过内容仅为相邻 URL 扫描短暂保留，扫描完成后删除原文；去重所需的最小状态记录可以保留。非文本消息不保存媒体内容。
- Push API 当前没有“死链接”字段。未来事项：特定客户每天首条正常发布，其余稿件设为死链接；需要另行确认 API 契约与日期口径，本设计不实现该规则。

## 实现运行约定

- 常驻入口为 `business-telegram-worker`，生产 unit 为 `odaily-business-telegram.service`。接收与处理共享一个 token 级 Bot API 长轮询，不依赖 Writer3 确认按钮 worker。
- 接收器从主 SQLite 读取持久化 `update_id`，每次收件最多领取 100 条；处理并发默认 4，可由 `BUSINESS_NEWS_WORKERS` 调整，轮询超时默认 50 秒，可由 `BUSINESS_NEWS_POLL_TIMEOUT_SECONDS` 调整。
- Writer4 复用 `X_PROCESS_*` / `ODAILY_LLM_*` OpenAI 兼容连接配置，模型默认使用 `X_PROCESS_WRITER_MODEL` 对应值，可用 `BUSINESS_NEWS_MODEL` 覆盖；一次调用同时返回分类、理由、朴素/宣传属性和快讯初稿。
- AI 与 Push API 请求均只尝试一次。处理中的服务崩溃行在下次启动时标记为失败并清理临时原文，不自动重放，以避免未知的外部 Push 结果造成重复稿件。
- 群发现、启停和消息分类详情由控制台认证接口管理。消息页面由 `editor-plugin-api-server` 读取主 SQLite；群启用只影响启用后新收到的 update。

## 控制台页面

- OdAIly 控制台新增一级标签 `商务快讯`，对所有客户群统一展示，不把 SoSo 固定为唯一客户。
- 页面包含 `消息记录` 和 `客户群` 两个视图。消息记录按接收时间倒序显示群/客户、发送者、AI 分类、快讯朴素/宣传属性、处理状态、来源链接及挂后台结果；详情展示仍保留的原文、AI 判定理由、Writer4 标题正文、脱水结果和 Writer2 定稿。
- 字数过滤、非文本、其他、长内容、不确定及处理失败记录只展示可保留的元数据、AI 分类结果（如有）和跳过/失败原因。按既定保留规则清理后的原文不在页面恢复或展示。活动记录显示原文和 `待接 API` 状态。
- 页面提供客户群筛选、分类筛选、处理状态筛选、时间范围和关键词搜索；不提供重试、重新分类、手工发布或人工审核操作。人工审核仍在 Odaily 后台完成。
- `客户群` 视图展示自动发现的群 ID、群名、发现时间、客户名和启用状态；允许配置客户名、启用或停用。启用只影响之后收到的新消息，不回放历史消息。
- 页面默认进入或手动刷新时读取数据，不做自动轮询；业务结果由后台持续写入，插件仍只收到成功挂后台后的单行提示。
- 页面接口、表和字段细节见 `控制台-商务快讯.md`。
