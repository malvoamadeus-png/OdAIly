# 控制台-全量信息流

## 职责与边界

全量信息流是跨业务只读查询入口，不接管原有业务状态机，不触发采集、写作、重试、发布或 Telegram。后端认证后开放 `list`、`detail`、`registry`、`health` 和管理员专用 `reset_history` 动作。历史重置取得与投影器相同的 advisory lock，在短事务中跳过屏障前尚未投影的 outbox，清除信息流 items、级联事件与来源身份，并清除旧巡检问题、决定、分析尝试、运行记录、pins 和决定样本；不锁来源 outbox 表，因此来源主业务事务可继续。它保留巡检运行配置/预算/channel observation、AI 文本升级案例快照、主业务数据和仍被主业务引用的 X 阶段响应证据。无其他业务引用的观测证据由后台有界 GC 删除。浏览器不传 SQL、表名、文件路径或业务库地址。

`五天任务复盘` 是独立的只读入口，读取主 `tasks` 及对应 X 流水线、外部媒体告警流水线阶段快照。未终结任务持续可见，终态任务按主任务更新时间保留五天；不依赖六小时信息流快照，也不读取仅供列表展示的投影事件。

查询库和巡检状态默认共用 `data/runtime/system_information.sqlite`，压缩证据默认位于同级 `system_information/evidence/`。设置 `ODAILY_SYSTEM_OBSERVABILITY_DIR` 可切换整个目录。生产推荐 `/data/OdAIly/system-observability`；切换目录只影响新增观测库，不搬动或替代主 SQLite、HotTopic、Meme、行情等业务库。

`ODAILY_STORAGE_BACKEND=postgres` 时，API 使用 PostgreSQL 原生观测表、巡检仓储和 `PostgresSourceStateProjector`；PostgreSQL 查询库位于 `system_observability` schema，大证据仍使用上述兼容路径下的内容寻址 gzip 文件，小证据字节存于 `small_evidence`。当前官方生产使用本机 PostgreSQL。

投影、巡检和列表请求共用的观测 SQLite 使用 WAL，写锁等待上限为 60 秒；连接使用退出上下文即关闭的连接类。只读业务库统一经 `connect_sqlite_readonly` 打开并设置 `query_only`。标准库 `sqlite3.Connection` 的上下文管理只提交/回滚事务，不关闭连接。短间隔 worker 若漏用关闭型连接会耗尽 API 的文件描述符并导致 SQLite 无法打开，回归测试覆盖该生命周期。观测库写入失败会在健康状态暴露，并由常驻投影/巡检线程在下一轮继续处理。

## 新闻视图与诊断视图

`list` API 默认 `view=news`；显式 `view=diagnostic` 查询技术主体。默认新闻视图展示通过门槛的主任务及重复项，价值不足的原始材料、配置、采集尝试、股票行情、内部研究和审查记录不单独占据新闻列表。竞品库 `newsflash_items` 只作为原始来源记录保留在诊断视图；它精确关联到主任务后作为任务子项展示，不把没有处理状态或理由字段的原始行伪装成“结果未知”的新闻主体。搜索先于判断而停止的重复项仍展示，准入标识为重复，不补造“价值通过”。`deduped` 表示通过前置步骤，不代表重复；`publisher_pending` 表示等待投递决定，不代表已挂后台。直发、挂后台等状态直接解释本系统 API 的内部状态，不核验官网。

标题优先使用稿件标题、原始标题及正文摘录，纯数字 ID 不作为主标题。详情增加准入结论、重复命中对象、来源名和已知的来源更新时间；未知时间保持空值。关联按 task_id、精确来源键以及 delivery_key 与审查稿件 ID 完成；无法精确关联的技术行仍仅保留在诊断入口，不做标题相似猜测。发布后审查作为原稿详情事件，不替换原稿发布状态。

任务的 `notified`、`expired`、`legacy_skipped` 状态分别解释为“已通知”“已过期”“旧任务已跳过”，对应结果不再退化为“结果未知”；`expired` 和 `legacy_skipped` 归入正常停止。具体阶段理由仍只使用任务已保存的错误、判断、查重、写作或投递字段，缺少这些字段时才显示状态本身的简短说明。正常阶段理由不等于错误；时间线仅在来源明确提供错误码或状态/结果确实失败时显示错误码，失败事件没有具体错误码时才使用 `unknown`。

默认按最后实际处理操作时间倒序，取任务时间、阶段时间和尝试时间的最大值；关联后续处理也刷新原稿。只更新时间不会另存证据或追加历史事件；页面读取、投影时刻和心跳不刷新业务排序。列表按所选排序字段固定限制在请求结束时间之前六小时内，未提供结束时间时取当前时间；翻页沿用稳定 `(time,item_id)` 游标和同一窗口。每页固定 50 条，传入的关键词和更早起始时间均不扩大查询范围。独立的五天任务复盘从主库直接读取任务与阶段结果，未结束任务持续显示，终态任务按主任务更新时间保留五天。SQLite 不再创建、读取、写入或重建搜索 postings；已有搜索表与位置表可离线备份后单独维护，服务启动和常规投影不会触碰这些表。

## 数据模型与查询

- `system_information_items` 保存一条稳定业务身份的轻量快照；重试不创建新主体。新增 `news_visible`、`admission`、`parent_item_id`、`duplicate_json`、`source_name`、`source_updated_at_ms` 和新闻活动时间部分索引。首次升级按有界水位重新分类历史主体，不重置来源 outbox 水位。
- `system_information_events` 保存投影观察到的状态变化、历史初始快照和 X 阶段尝试事件。X 阶段尝试保存在主库的 `x_processing_attempts` / `x_processing_attempt_events`；主库只留模型返回的内容引用、SHA-256、字节数和短摘录，完整压缩证据直接写到 `ODAILY_SYSTEM_OBSERVABILITY_DIR` 下的内容寻址归档，再进行解析或业务校验。
- `system_information_evidence` 登记内容寻址压缩文件；重复 JSON 只存一份。详情读取时才解压。
- SQLite 查询库不再维护关键词 posting 表；搜索是已移除的能力。部署切换不在服务运行时删除旧表，避免大表删除造成长时间写锁或 WAL/磁盘峰值。离线维护需停 API 和投影器、完成一致备份后评估副本空间，再决定删除 `system_information_search`、`system_information_search_positions` 及相关索引；SQLite 文件不会因删除自动缩小，VACUUM 需要额外接近数据库大小的可用空间并应单独安排。
- `idx_system_information_business_source` 覆盖健康页按业务和来源聚合的来源统计；`idx_system_information_business_activity` 支持按业务过滤后按最近活动时间倒序。新闻活动部分索引支持默认视图；无关键词新闻列表与总数显式使用该索引，避免升级后无统计信息时误选 parent_item_id=NULL 并全表扫描。来源数据库/表/行 ID 组合索引支持逐条归档核对，证据引用索引支持跨日清理引用闭包，避免对每条材料重复扫描全部历史事件。上述索引避免大库查询建临时分组/排序表，首次升级由 SQLite 幂等创建。
- 时间在读模型内统一保存 UTC epoch 毫秒。列表先服务端过滤，默认按最近活动时间倒序，也可切换为创建时间；时间缺失的记录排在已知时间之后。游标按 `(time,item_id)` 稳定分页。详情才返回大证据。
- 每页默认 50 条，游标不随新入库记录漂移；刷新会重新读取快照，不做页面自动轮询。

PostgreSQL 全量导入须保留每条 item/event/evidence 原记录和外键身份，以支持巡检证据、详情和迁移审计；历史搜索 postings 可选择不导入运行库，若执行导入则按 item 保存并核对 posting 数与 SHA-256。PostgreSQL 原生运行不生成或整理关键词索引，列表忽略旧客户端的关键词参数。SQLite `system_information_search` 历史索引仍按原规则用于兼容运行。旧 `source_database` 路径不能直接当 schema，身份回填必须使用显式路径到物理 schema 的映射并保留原 `item_id`，相同来源元组映射到不同 item 时中止导入。

已接入的 PostgreSQL 来源事件通过同事务 outbox 写入。投影在单个事务中锁定未确认事件、更新主体和时间线并确认事件；失败时全部回滚。`main.tasks` 与 `main.x_task_pipeline` 分别由任务 ID 和 task ID 标识，但都投影到 `(main,tasks,id)` 的同一主体。当前状态按来源修订号防止回退。X 账号采集尝试按 `username_lower` 收敛为一个账号主体，状态只展示最新已结束尝试；较早尝试仍推进来源 outbox 水位，但不各自形成信息流主体、时间线事件或证据副本。新增接入商务、Hyperliquid、巨鲸、竞品、热点、Meme、行情、审核及队列的关键状态表；事件字段白名单和确切表名以 `postgres_sources.py` 为准。仅记录插入及关键字段更新，不把定时刷新或留存删除当作新事件，不回灌接入前的历史。列表接口按服务端当前时间强制限制最近六小时，客户端窗口结束时间最多截到服务端当前时间，翻页游标继续稳定；每页上限 50。外置证据写入与回收使用同 ref advisory lock，压缩和孤立回收使用独立有界游标；仅主业务 `response_ref`、AI 升级案例快照和运行配置等明确业务所有者延长数据/证据保留。

X 采集尝试由 `main.x_capture_attempts` 的 INSERT/UPDATE 事务触发器写入 outbox，采集留存删除不产生事件；账号主体只保留最新状态，不追加每次采集的时间线，来源身份按账号而非尝试 ID 保存。PostgreSQL 投影器每分钟最多清理 5,000 条六小时前的信息流主体副本，并级联清理该副本的时间线和身份映射；不因巡检决定样本、pin、问题卡、失败状态或近期子项而保留旧信息流副本。清理不删除业务表、主任务、Prompt 或仍有主业务引用的证据；主库阶段尝试 `response_ref` 是共享证据引用，回收会显式核对主库 attempts 与 attempt events。PostgreSQL 的普通 VACUUM 可复用已删除空间，文件不会因删除立即缩小。

六小时主体保留以 `system_information_items` 的观测副本为限，不延伸到主业务事实。投影器支持“信息流历史重置”：取得与普通投影相同的 advisory lock，在短事务中确认屏障前未投影事件并清空信息流主体及来源身份，不对 outbox 表加锁，不阻塞来源业务事务。重置同时删除旧巡检问题、决定、分析尝试、运行记录、pins 和决定样本；保留巡检 state、预算和 channel observations、`ai_text_self_upgrade_*` 案例以及业务源表。主业务 attempts 仍引用的证据通过 `response_ref` 保留，其他孤立信息流证据由有界 GC 删除。屏障后提交的 outbox 事件仍按 `projected_at IS NULL` 正常投影。切换失败时事务整体回滚。

### 详情读取与页面性能

详情在同一个数据库连接中读取主体、关联事件及证据索引；PostgreSQL 先按主体及其子项 ID 使用事件表索引，不使用带子查询的 `OR` 条件触发全表扫描。证据引用在同一请求内去重并只读取一次，不跨请求缓存；后续请求仍遵守清理、脱敏和跨日外部错误隐藏规则。返回内容及缺失证据的表达保持原契约。

`/console/system-information` 对超过 4096 字节、客户端接受 gzip 的 JSON 响应启用压缩，并返回 `Vary: Accept-Encoding`；跨域预检允许缓存 600 秒。这只缓存预检许可，不缓存业务响应，不跳过请求认证。

前端保留完整详情响应，模型原始返回、原文、写作输出、投递回执、输入规则和技术 JSON 的折叠区只在展开时生成文本节点；关闭后卸载正文，重新展开仍可查看完整内容。此优化减少大详情首次渲染开销，不截断或删除审计证据。

普通成功采集的事务状态事件，如果精简证据不超过 8 KiB，则与事件一起保存到观测数据库，并在详情中还原为同样的证据内容；普通成功采集的短快照和短事务载荷保存在独立的 `system_information/small_evidence.sqlite`，观测库保留内容引用。较大证据和故障仍使用文件。新旧证据均可通过原详情接口读取；来源不明的历史文件不会仅按年龄删除。

未出现在上述现有表/字段的来源结果不会因注册目录存在而自动变成已接入数据。`registry` 接口同时返回观察到但未登记的来源；`health` 返回适配器状态、投影水位和失败信息。发现表缺失或适配失败时显示未就绪/失败，不显示假“0 条”。

## 主流程尝试写入

主 X 流水线在领取任务后创建阶段尝试；模型调用前记录实际 Prompt、模板 key/version、规则、模型、思考等级、输入摘要和代码 revision。模型返回先直接 gzip 写入独立观测卷的内容寻址归档，来源主库只保存引用、hash、字节数和最多 1000 字摘录，再进行 JSON 解析和业务校验。投影后详情复用同一证据引用；证据回收按信息流、巡检、AI 文本升级案例和主库阶段尝试的实际引用判断，不以旧 pin 延长信息流副本留存。成功、失败和停止事件按留存规则追加写入；跨日外部错误明细例外删除，不承诺保留早先失败详情；调用超时但未取得响应时保留异常和失败，不伪造原始返回或 request ID。生产 API 与 X worker 均要求 `/data` 挂载并写入 `/data/OdAIly/system-observability`，避免大响应占用根盘。

其他可变业务表的触发器在原 SQLite 写事务内追加精简状态事件。业务 outbox 只含受限身份、状态、错误/理由、投递摘要和时间；配置 outbox 另按字段白名单记录启停、间隔、适用范围和版本元数据。两类记录都排除凭据；业务 outbox 不复制正文或模型返回，配置 outbox 不复制请求头或任意配置 JSON。更新触发器仍把时间戳放入实际状态变化事件 payload，但只刷新 `updated_at`、`last_seen_at`、`last_polled_at`、`last_checked_at`、`heartbeat_at`、`last_attempt_at`、`last_success_at`、`polled_at` 或 `checked_at` 时不追加事件。X 采集尝试只记录插入和真实字段更新，1 天保留清理的删除不入 outbox；既有此类删除事件在投影时跳过并推进水位。触发器定义带版本号，投影器发现版本变化时幂等重建。观测库不可用时，来源事务仍可在 outbox 表内留待重试，投影失败不触发业务重试或外部投递。X 尝试表仍属于观测扩展与业务更新的分步写入，不能把模型响应审计等同于发布 outbox。投影按水位恢复，稳定事件 ID 防止重复；来源 outbox 每批默认读取 2000 条、上限 5000 条，并在查询库单个事务内提交主体、时间线和水位。时间线事件按各自留存规则保留；同一批中一个业务行的最新状态快照只写入一次。来源库 outbox 每 5 分钟最多清理 5000 条，且只删除已投影并超过 24 小时的事件；不存在到期记录时不启动来源库写事务。清理遇到写锁最多等待 2 秒，后续周期重试。

`tasks` 的事务 outbox 既追加每次主流程状态变化，也更新同一任务的当前快照。投影为 outbox 新建任务主体时补齐任务 ID、业务分类和准入/新闻可见性；更新既有主体时只改状态、阶段、摘要和活动时间，保留主快照中的稿件标题、来源材料、证据及查重关系。重复任务在新闻视图中仍可见。快照仅接受时间不早于已保存状态的事件，避免积压旧事件覆盖较新的主流程状态；这样即使全量历史回填存在积压，任务状态也可由 outbox 及时推进。

## 留存和磁盘

新闻主体、稿件、审核结论、来源身份和已有链接保留。常规新闻任务完成 30 天后，清理源正文、原始载荷和 metadata 中的原文上下文；关联的事实审查等待或执行中时暂缓，无法关联时采用保守保护。待处理、挂后台、失败任务以及确定性生成的数据任务不在该规则内。主库中竞品原文在 30 天后且其事件无近期变更时清除，Odaily 已发布正文保留。各阶段每分钟按主键最多扫描 100 行，游标循环，积压不会在恰满 30 天时立即清完；删除不自动缩小 SQLite 文件。

判断、查重、写作与发布主任务在终态后保留五天供控制台复盘，未结束任务持续保留；复盘读取主库任务及完整阶段行，包括判断、搜索命中目标、写作稿件、发布决定和回执。信息流副本仍只保留六小时，不复制五天复盘数据。常驻 AI 自我升级 worker 每日北京时间 06:00 后首次轮询时运行五天业务清理，按主任务更新时间选择终态任务，每表每轮最多处理 500 行，分批清空任务 raw payload 和 X 流水线判断、搜索、写作过程输出与草稿；保留任务正文、来源/账号身份 metadata、最终定稿、发布快照及回执。关联审核仍为 `pending` / `processing`，或关联拒绝反馈 outbox 仍为 `pending` / `queued`，或任务仍被未过期活动事件查重候选引用时，暂缓清理该任务及对应阶段输出；单纯 `flagged` 审核状态不永久延长保留期。清理不删除实时查重身份、发布幂等记录或其他业务表。批次每轮有界处理；若跨过北京时间午夜仍有待清理数据，下一轮先续跑未完成的旧日期批次，再启动当天批次。

外部依赖错误具体内容仅留北京时间当天。投影器每分钟有界清理来源表、事务 outbox、观测主体、时间线、证据及搜索索引中的跨日副本；来源事务计数器在失败写入同一事务增加日期/来源/阶段/类别计数，不保存对象清单。同一失败的管线、队列和投影副本不重复计数；重试次数变化可计为新尝试。首次接入只统计尚存的历史失败，不能重建已丢失尝试。查询层在物理清理尚未追平时也隐藏过期外部错误；对应业务失败状态、恢复输入与调度信息保留。健康页通过 external_error_daily 展示汇总。正常空结果/过期筛选不归入故障；本机 SQLite 锁、磁盘与程序问题仍保留可行动诊断。仅覆盖注册适配表及受管理观测材料，不清理 systemd journal 等操作系统日志。

PostgreSQL 信息流每分钟最多清理 5,000 条六小时前的主体副本，不按 pin、巡检样本、失败/活动状态或旧时间线延长保留；该清理只删观测副本，不删除来源任务、X 阶段尝试、发布幂等或其他主业务数据。reset 会清理旧 pin 与巡检样本。信息流证据 GC 每分钟最多处理 1,000 个候选，删除不再被信息流、巡检、AI 案例分析响应或主库 X processing attempts 引用的证据；共享证据引用由主库 `response_ref` 保护。五天业务复盘所需材料只保存在主任务及阶段表中。来源 outbox 增量投影仍在查询库单事务内确认；纯时间戳刷新不生成 outbox 事件。PostgreSQL 每分钟最多删除 5000 条超过 24 小时的中转事件：已投影事件正常清理；未投影事件仅在 event ID 不高于持久 reset barrier 时清理。候选按批重查并使用 `SKIP LOCKED`，中断后下一轮继续，不跨过并发锁定的行，也不等待主业务事务释放行锁。

主任务普通状态事件清理同样复核主库当前状态、失败尝试和活动审核；源库不可用或审核关联不明时保留事件。复核按主库、信息流的顺序获取写锁，避免与证据写入顺序相反。

阶段尝试及文件回收由 `ODAILY_COMPLETED_EVIDENCE_RETENTION_ENABLED=1` 启用，默认关闭；上线前必须切换所有证据写入进程至同一版本，避免旧进程绕过写入与删除的并发保护。执行情况及错误分别记录在信息流 state 的 `attempt_retention`、`attempt_event_retention`、`attempt_evidence_reclaim` 对应结果字段中，累计回收文件数与删除前分配空间估计单独记录；候选和引用无法核实则保留。

已成功结束的 X 和币安广场采集事件，超过一天后可将明确无故障的过期快照加入同一回收队列；先保留账号身份，账号身份不明或快照包含错误时不清除。每批最多登记 50 个证据，仍须通过其他引用检查后才回收。历史文件仅在内容完整、哈希正确、明确属于成功的 X 采集且账号和结束时间可核对时进入候选，其他未知文件不按年龄删除。

D 类每日抽样、历史问题卡和人工巡检决定不再依赖信息流数据，信息流 reset 时清理其历史结果。系统仍保留巡检运行 state、预算和 channel observation，以便当前监控和任务调度继续运行。五天复盘从主业务任务/阶段表读取，不创建新的复盘页面或信息流副本。

存储健康页展示所在文件系统总量、可用量、最低安全余量 `max(10 GiB, 15%)`、查询库和证据体积、采样天数及按历史样本估算的未来 30 天增长。生产 API 将查询库、巡检记录与压缩证据放在 `/data/OdAIly/system-observability`；2026-11-03 实测 `/data` 为约 98 GiB ext4 卷、可用约 92 GiB，根盘仍接近满载，因此观测数据继续全部放在 `/data`。无足够样本时增长估算为零但会同时显示样本数，不能据此解释为增长为零。巡检不会自动删除主业务库或关键证据腾空间。

## 生产启用与回退

### SQLite 来源冻结与 outbox 追平

原生 PostgreSQL 切换前，先停止所有会写入来源 SQLite 的 worker、API、采集器和定时任务，并确认没有旧进程仍持有写入职责。使用 `packages.system_observability.native_import_cutover.run_frozen_cutover_drain` 对每个来源库执行只读就绪检查，捕获 `odaily_observability_outbox` 的最终 `MAX(seq)`，再调用 `MainTaskProjector.drain_source_outbox` 按有界批次追平到该水位。调用方必须显式确认 `source_writes_stopped=True`；代码不能自行证明其他进程已停止。

冻结 drain 不安装或重建触发器，不运行常规全量快照、搜索重建、证据回收或 retention 清理，也不删除或改写来源 outbox 行。每批仅在目标查询库事务中提交事件投影和水位。完成条件是所有来源报告 `complete=true` 且 `watermark >= target_sequence`；写入仍开启时不要把某一时刻的水位当作最终切换水位。完整 PostgreSQL/SQLite 行数、摘要、外键核对仍由原生导入器与切换审计完成，不能用 outbox 追平代替。

1. 在官方服务器确认 `/data` 持久挂载和余量后，将 systemd API 环境配置设为 `ODAILY_SYSTEM_OBSERVABILITY_DIR=/data/OdAIly/system-observability`，建立仅 `root` 可读写的目录。
2. 拉取代码并重启 `odaily-editor-plugin-api.service`。service 固定设置 `ODAILY_SYSTEM_OBSERVABILITY_DIR=/data/OdAIly/system-observability`；独立查询库从空库幂等初始化，并为登记的可变来源表创建 SQLite outbox 触发器。投影器按 `tasks` ID、来源 rowid 与 outbox 水位有界回填，不调用模型、不推进业务、不投递内容。
3. 检查 `GET` 对应受认证接口返回的固定 50 条列表、六小时窗口、按实际剩余任务行统计的投影 lag 和适配器状态，再验证代表业务与详情；巡检历史重置后不要求存在旧的人工巡检决定。
4. 关闭时回退 API 代码版本或设置 `ODAILY_SYSTEM_OBSERVABILITY_DIR` 回默认路径；保留 `/data` 上新增库和证据。关闭投影/巡检不停止原有 worker，不删除证据，不重投已提交稿件。

生产首启应保留原代码版本，并记录目录权限、挂载 UUID、查询库路径和新服务心跳。主业务库可由独立运维步骤通过既有 `ODAILY_SQLITE_PATH` 切换到 `/data`，本次代码不会搬动文件、执行 VACUUM 或释放根盘空间；迁移仍需按 `SQLite主存储迁移.md` 完成停写、一致性核对和回退准备。
