# 控制台-AI文本自我升级

## 职责

本模块研究 Writer1 稿件被 AI 审核者标记的问题。文本审查者和事实审查者是并列触发源：任一方将已发布稿件标记为 `flagged`，且该稿件能与 Writer1 已发布定稿精确关联时，都会建立独立案例。`gpt-6-luna` 作为第三方审核者，判断对应审核意见是否成立，以及问题能否归因于 Writer1。模块只积累案例和人工评审结果，不自动修改 Prompt、审核规则、稿件或发布状态。

文本审查者的人工拒绝也是独立触发源。拒绝反馈写入本地后，将审核记录 ID 和操作者持久写入 AI 自我升级待办表；常驻 worker 验证审核仍为 `flagged` 且版本哈希正确后保存案例，不等待来源关联，因此有效拒绝不会因缺失元数据无限重试。AI 稿在能精确匹配 Writer1 发布快照时保存完整草稿和定稿；`outlet_category = manual`、`origin_key = manual` 或发布人事实 `publisher_kind = human / human_unmapped` 可确认人工稿来源。人工拒绝案例没有 Writer1 快照、没有明确非人工发布分类，也不存在 `odaily-task-*` 投递键或 `id_match_status = ambiguous` 时按人工稿处理；有明确非人工分类或 Writer1 映射歧义但无法匹配快照时才标为来源未知。旧案例缺少来源依据字段时按此人工拒绝队列规则解释；明确非人工或映射歧义的案例保留来源未知。上述案例均只保存审核记录和已发布审核稿，`task_id` 留空且不伪造 Writer1 草稿。第三方结论区分审核者意见不成立、审核意见成立但未归因 Writer1、Writer1 草稿本身有误和证据不足；已确认人工稿时明确说明 Writer1 归因不适用，不表述为作者责任未确认；来源未知时仍明确保留来源未知，不据此推断为人工稿。墓碑命中的待办标记为已删除并终止处理，不能重建案例。事实审查者反馈不属于此入口。升级案例快照独立于普通审核记录保留，控制台管理员可删除；删除事务写入永久 case_key 墓碑并删除案例及决定历史，后续扫描不能自动重建。

AI 自我升级队列仅展示文本审查者的人工拒绝案例，排除有明确非人工发布来源或 Writer1 映射歧义的记录。按发布时间保留滚动 72 小时内及未来时间的案例；发布时间缺失时使用案例创建时间。列表先按此范围和来源筛选，再应用人工决定状态与分页。

列表与详情展示当前存储中的案例编号；“已最终审核”筛选合并审核者正确和原文正确两种人工决定，具体决定仍在每条案例中展示。已忽略案例单独筛选。

## 案例范围与关联

模块记录首次启用时间，只处理该时间之后完成的审核；人工指定时间范围的回放可以重跑该范围。文本审核取 `auditor_checks.status = 'flagged'`，事实审核取最新一次 `fact_check_runs.status = 'flagged'` 且当前 `fact_checks.status = 'flagged'` 的记录。

案例按审核来源、Odaily 已发布 ID 和审核记录自带的版本哈希区分。同一稿件版本被文本和事实审查者分别标记时，分别建案，避免单一结论掩盖两种审核意见可能不一致的情况。文本审查者哈希为标题和正文的 MD5；事实审查者哈希为标题、正文和原文定位链接的 SHA-256。哈希只在各自审核记录内标识版本，不跨算法比较。每案保存对应审核意见、Writer1 素材、草稿和定稿。

关联必须满足：

- 找到已完成 Writer1 写作和发布的 `x_task_pipeline` 记录，并存在 Writer1 模型、草稿和定稿。
- 有唯一的已发布 ID 映射时优先按映射关联 Writer1 任务，并将审核记录中的稿件版本与 Writer1 草稿、定稿都交给第三方比较；文本审查哈希须与审核记录标题和正文一致。
- ID 映射缺失时，先按发布时间前后两天检索；只有 production metadata 标题与 Writer1 定稿标题一致，且移除固定刊头并按发布格式归一空格后的正文一致，才允许关联。若审核标题与定稿标题有差异，还可在审核来源 URL 与 Writer1 来源 URL 完全一致、归一化正文完全一致、production metadata 标题仍与定稿标题一致且候选唯一时关联。也接受完整标题、正文哈希精确一致的唯一匹配。
- 若同一时间窗口中有多个完全相同哈希的 Writer1 定稿，因来源无法唯一确定而不建案，计入未关联数。
- 除了唯一 ID 映射外，无法唯一关联、Writer1 草稿缺失或稿件版本不能匹配时不建立案例。

生产主 SQLite 只读。SQLite 模式下，案例快照、第三方判断、批次和人工决定保存在 `ODAILY_SYSTEM_OBSERVABILITY_DIR/ai_text_self_upgrade.sqlite`；选择 `ODAILY_STORAGE_BACKEND=postgres` 时，这些表迁移到本机 PostgreSQL 的 `system_observability` schema，主库、文本审查者记录、事实审查者记录和 Writer1 发布记录仍按原有只读来源读取。PostgreSQL 实现保留 `source_type`、`auditor_check_id`、`fact_check_id` 和 `source_item_id` 的独立身份字段。来源查询按稳定复合键分页，每页单独 checkout/release 连接，避免长时间持有连接或一次取回过大的结果集；库存导入只初始化表结构，不播种运行状态或恢复任务。

## 调度、判断与回放

常驻 worker 每 30 秒检查人工拒绝待办，并检查北京时间 `00:00 / 04:00 / 08:00 / 12:00 / 16:00 / 20:00` 分析时槽；人工拒绝队列消费不受当前时槽是否已执行影响。暂缺精确关联的待办按 30 秒起步、最多 6 小时的指数退避重试；进程重启会将处理中待办恢复为可重试。每天北京时间 06:00 后首次轮询时，以日期唯一键执行一次有界的主流程五天字段清理，不触发鲸鱼活动、插件记录或 worker 心跳等其他模块的通用维护；失败会记录状态并在 5 分钟后重试，清理异常不阻断拒绝队列和分析批次。分析时槽每槽最多运行一次。空分析队列记录零案例批次且不调用模型。每个案例独立调用 `gpt-6-luna`，思考等级为 `medium`；单案失败可在后续时槽重试。

第三方结论及模型、Prompt 版本会随案例保存：

第三方逐条核对审核者实际提出的问题，有多项意见时分别说明；其他未提出的错误或可补充信息不能用来证明原审核意见成立。

- `writer1_error`：审核意见成立，且问题在 Writer1 草稿中已存在。
- `reviewer_correct_unattributed`：审核意见成立，但没有依据归因给 Writer1。已确认人工稿表示 Writer1 归因不适用；来源未知则仍是来源未知，界面分别展示。已确认人工稿和来源未知的人工拒绝案例若返回 `writer1_error`，结果解析会拒绝入库。
- `auditor_false_positive`：有直接证据证明审核意见不成立或超出该审核者的职责范围。
- `inconclusive`：现有证据不足以判断审核意见本身是否成立，或证据冲突、疑点无法核验。此状态不归责任一方。

人工决定 `reviewer_correct / writer_correct / ignored` 分别表示审核者正确、原文正确、忽略；前两者均计入人工确认的研究样本。人工可以独立判断，包括第三方无法定论的案例；无论第三方分析处于等待、处理中、失败或完成状态，都可以直接作出人工决定。旧 `accepted / rejected / ignored` 决定保留原始含义并标为历史决定，不自动转换，可重新作出判断。新决定保存在独立字段及历史表，旧历史不删除。模块不会据此自动改进系统。

页面展示已审核稿件，不重复展示草稿和格式化稿件；后台仍保留它们用于归因。第三方审核对内容仅有格式和来源尾缀差异的草稿、发布稿不重复引用；页面也对历史重复稿件证据去重，保留有实质差异的证据。

普通未人工处理的审核记录仍按审核模块期限清理；升级案例中保存的审核意见、快照和第三方判断不依赖源记录存续。删除墓碑仅保留去重键、操作者和时间，用来防止人工删除的案例在扫描或回放时自动重建。

运维人员可用命令对明确的时间窗执行一次回放：

```bash
python backend/src/main.py ai-text-self-upgrade-replay \
  --since 2026-11-11T00:00:00+08:00 \
  --until 2026-11-12T00:00:00+08:00
```

回放仅处理给定审核完成时间窗内的案例；已完成案例保持原结果，失败案例可重试。回放运行和结果在控制台模块中可见。
