# 控制台-AI文本自我升级

## 职责

本模块研究 Writer1 稿件被 AI 审核者标记的问题。文本审查者和事实审查者是并列触发源：任一方将已发布稿件标记为 `flagged`，且该稿件能与 Writer1 已发布定稿精确关联时，都会建立独立案例。`gpt-6-luna` 作为第三方审核者，判断对应审核意见是否成立，以及问题能否归因于 Writer1。模块只积累案例和人工评审结果，不自动修改 Prompt、审核规则、稿件或发布状态。

## 案例范围与关联

模块记录首次启用时间，只处理该时间之后完成的审核；人工指定时间范围的回放可以重跑该范围。文本审核取 `auditor_checks.status = 'flagged'`，事实审核取最新一次 `fact_check_runs.status = 'flagged'` 且当前 `fact_checks.status = 'flagged'` 的记录。

案例按审核来源、Odaily 已发布 ID 和稿件内容哈希区分。同一稿件版本被文本和事实审查者分别标记时，分别建案，避免单一结论掩盖两种审核意见可能不一致的情况。每案保存对应审核意见、Writer1 素材、草稿和定稿。

关联必须满足：

- 找到已完成 Writer1 写作和发布的 `x_task_pipeline` 记录，并存在 Writer1 模型、草稿和定稿。
- 有唯一的已发布 ID 映射时按映射关联 Writer1 任务，并将两个稿件版本都交给第三方比较。
- ID 映射缺失时，先按发布时间前后两天检索；只有 production metadata 标题与 Writer1 定稿标题一致，且移除固定刊头并按发布格式归一空格后的正文一致，才允许关联。也接受完整标题、正文哈希精确一致的唯一匹配。
- 若同一时间窗口中有多个完全相同哈希的 Writer1 定稿，因来源无法唯一确定而不建案，计入未关联数。
- 除了唯一 ID 映射外，无法唯一关联、Writer1 草稿缺失或稿件版本不能匹配时不建立案例。

生产主 SQLite 只读。案例快照、第三方判断、批次和人工决定保存在 `ODAILY_SYSTEM_OBSERVABILITY_DIR/ai_text_self_upgrade.sqlite`。

## 调度、判断与回放

worker 每 30 秒检查北京时间 `00:00 / 04:00 / 08:00 / 12:00 / 16:00 / 20:00` 时槽，每槽最多运行一次。空队列记录零案例批次且不调用模型。每个案例独立调用 `gpt-6-luna`，思考等级为 `medium`；单案失败可在后续时槽重试。

第三方结论及模型、Prompt 版本会随案例保存：

- `writer1_error`：审核意见成立，且问题在 Writer1 草稿中已存在。
- `auditor_false_positive`：审核意见不成立、证据不足，或超出该审核者的职责范围。
- `inconclusive`：证据冲突、原文无法核验，或问题只在 Writer1 之后的环节出现。此状态不归责任一方。

人工决定 `accepted / rejected / ignored` 分别表示认可第三方结论、否定结论、特殊例外；只有接受的案例计入研究样本。模块不会据此自动改进系统。

运维人员可用命令对明确的时间窗执行一次回放：

```bash
python backend/src/main.py ai-text-self-upgrade-replay \
  --since 2026-11-11T00:00:00+08:00 \
  --until 2026-11-12T00:00:00+08:00
```

回放仅处理给定审核完成时间窗内的案例；已完成案例保持原结果，失败案例可重试。回放运行和结果在控制台模块中可见。
