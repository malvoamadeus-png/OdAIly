## 三、当前代码为什么没有形成 GIWA 热点

### 1. 非资产话题的归并门槛

当前文档和代码对非资产事件采用了较保守的归并条件：

- 至少两个稳定的命名实体或命名片段共同出现；
- 事件动作类别相同；
- 合并后的话题至少有三个独立账号。

代码位置：

- [topic_aggregator.py:1409](/mnt/d/Coding/OdAIly/backend/packages/hottopic/topic_aggregator.py:1409)
- [topic_aggregator.py:1414](/mnt/d/Coding/OdAIly/backend/packages/hottopic/topic_aggregator.py:1414)
- [控制台-热点话题.md:14](/mnt/d/Coding/OdAIly/docs/OdAIly代码与整体设计/控制台-热点话题.md:14)

“GIWA 上线了”“GIWA 主网快上线了”这类内容通常只有一个稳定主体 `GIWA`，没有第二个稳定实体。因此不同账号的内容没有稳定地合并到同一个话题。

### 2. 归并目前主要是确定性代码，不是 AI 判断

当前话题归并主要经过：

- token、实体、合约、引用关系和时间的候选召回；
- 本地分数与硬规则判断；
- `_consolidate_dirty_topics()` 中的确定性话题合并。

本次线上聚合审计记录显示 `model_candidate_count=0`，GIWA 相关错误合并记录的 `decision_source` 为 `local_merge` 或 `local_score`。AI 正文模型不是这次话题归并的主要判断者。

### 3. 一部分内容被硬关系吸入其他话题

例如，GIWA 官方辟谣内容与 `$GPEPE` 话题共享同一条被引用的官方推文，引用关系被加入候选硬键，导致内容以 `hard_relation` 高分挂入 `$GPEPE`。

另外，GIWA 链 RPC 内容因为共享合约地址和 `GIWA`、`bridge`、`DEX` 等词，被记录为：

```text
shared named event identity=['bridge', 'dex', 'giwa']; kind=launch
```

随后被并入 PONS/Arcus 话题。这说明当前引用关系和通用词身份可能同时造成“漏合并”和“错合并”。

## 四、热点展示门槛与归并门槛的区别

当前代码有多个阶段：

```text
帖子
  -> 创建或附加到 seed
  -> seed 之间归并
  -> 评估参与者和话题资格
  -> active + hidden
  -> 正文生成成功
  -> active + visible
  -> 控制台展示
```

可见热点的参与账号常量为：

```python
MIN_VISIBLE_PARTICIPANTS = 5
```

代码位置：[topic_aggregator.py:30](/mnt/d/Coding/OdAIly/backend/packages/hottopic/topic_aggregator.py:30)。

因此，GIWA 当前并不是“已经合并了 11 个账号但没有展示”，而是先在事件身份归并阶段被拆散；拆散后每个分支的参与账号数量又不足以形成可见热点。

## 五、当前不作出的结论

本次不把以下方案直接定为修复：

1. 只把“至少两个实体”改成“至少一个实体”。
2. 为链、平台、项目等建立固定的主体/背景实体分类。
3. 为 GIWA 增加项目特例或白名单。
4. 直接依赖 AI 替代所有确定性归并规则。

原因是这些方案分别可能带来：

- 单一主体的不同事件被合并；
- 同一生态内多个项目被串成一个话题；
- 业务特例持续增长；
- 模型错误直接污染话题长期状态。

## 六、待后续重新设计的问题

后续如果重新处理，应先明确一个比“实体数量”更普适的事件兼容性判断：

- 什么证据足以证明两个内容描述的是同一个事件；
- 什么证据足以证明两个内容明确不同；
- 哪些情况只能判为证据不足并等待后续内容；
- 引用同一条原文是否只能作为支持证据，而不能直接作为硬归并键；
- 通用词如 `chain`、`bridge`、`DEX` 是否可以进入事件身份；
- 不同合约、Cashtag、官方账号或项目名称如何形成冲突证据；
- AI 是否只处理确定性规则无法决定的候选，而不是直接替代归并模块。

暂定的设计讨论方向是让归并模块输出三态结果：

```text
same_event
different_event
uncertain
```

但该方向目前只是讨论记录，不是已接受的实现方案。

## 七、结论

GIWA 未进入热点的直接原因是：相关内容虽然被成功采集，但被当前确定性归并规则拆成多个 seed，并有部分内容因引用关系、合约和通用词被误挂到 `$GPEPE`、PONS/Arcus 等其他话题。账号订阅、采集 worker、inbox 处理和控制台查询均未发现阻断故障。

这次问题暴露的是非资产事件的身份归并设计问题，暂不通过修改一个阈值或增加 GIWA 特例解决。后续需要单独完成事件兼容性判断的设计后，再决定是否改代码和生产数据。

## 八、GPT Web Search 账号发现实测

为验证热点自动快讯的第零步替代方案，使用 GIWA 假链事件向项目当前配置的 OpenAI-compatible 路由发起一次只读 Responses API 请求，并显式启用 `web_search`。本次没有修改代码、数据库或账号配置。

### 实测结果

- HTTP `200`，Responses 状态为 `completed`；
- 原始响应包含 `6` 个真实 `web_search_call`，不是模型在文本中声称搜索；
- 返回 `10` 个 URL 引用；
- 模型建议优先关注：`@GIWA_by_Upbit`、`@Official_Upbit`、`@DYORSWAPDEX`；补充关注 `@lookonchain` 和媒体账号；
- 模型把 `@GIWACat` 识别为生态社区账号，不建议作为事故官方响应渠道；
- 模型没有确认 `766 ETH` 精确数字的一手依据，并将其标为待进一步核验。

这次结果证明 GPT 可以从事件描述中找出“官方主体、母品牌、涉事方、链上追踪方、媒体”的不同账号角色，而不是只能回答一个固定账号名。但 `@GIWA_by_Upbit` 等候选仍需通过账号主页、官网互链和事件原帖做确定性核验后才能进入追踪。

### Token usage

单次请求 usage 为：输入 `56,177` tokens，输出 `3,820` tokens，总计 `59,997` tokens；其中 cached input `7,808` tokens，reasoning tokens `1,254`。由于当前使用的是 OpenAI-compatible 中转和模型别名，没有可靠的中转价格表，本次只记录 token，不估算美元成本。

这个数量级说明 GPT Web Search 适合按热点创建或复核时调用，不适合每分钟重复搜索。账号发现完成后，应交给 X 采集链路读取账号动态。
