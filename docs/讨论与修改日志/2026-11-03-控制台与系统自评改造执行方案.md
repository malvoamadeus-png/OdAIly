# OdAIly 控制台、全量信息流与系统自评改造执行方案

日期：2026-11-03。状态：功能已实施并部署；生产登录、代表业务详情和认证接口 p95 待可用操作者会话完成验收。执行记录见 `2026-11-03-控制台与系统自评实施验收.md`。本文是执行入口，用户已确认的方向与本文件工程默认值在这里收敛；旧讨论和研究笔记只提供证据，不覆盖本文。

## 1. 任务与最终决定

完成控制台分组、全量信息流、全流程可追溯记录、交互流程导览，以及现有 AI 审阅之外的五项巡检。直接交付能运行的完整功能、必要测试、同步文档和验收结果；不止交付原型、接口空壳或计划。

用户确定：

- “快讯及数据总览”显示名称统一改为 **Odaily快讯总览**。
- **需要保存的数据全部保留在官方服务器，用户负责扩容。**采用服务器本地 SQLite 与本地压缩文件保存证据。本项目不创建 R2/B2/云数据库，不迁出数据。
- 海量最终无用的 X Agent 原文仍使用有限工作窗口、少量抽样和清理；扩容不要求永久保存所有丢弃原文。关键处理、重试、有效规则、稿件、理由和复核证据必须能追溯。
- 保持快讯速度：新增 AI 巡检异步执行，不给每篇快讯再插入一轮同步 AI 检查。
- AI 提交有证据的问题与改进建议，人工最终审阅；认可问题不自动修改 Prompt、监控名单、发布资格或已发稿。
- 对已认可的界面与工程细节由执行者自主完成，不重复要求用户选择存储字段、分页方式、卡片样式等常规方案。

本文件的留存期限、预算、周期、性能目标均是可直接采用的首版工程默认值。执行者可因实际数据/业务约束作小幅调整，记录原因及测试，不改变上述用户决定或擅自缩减交付范围。

## 2. 开始执行与生产前置检查

1. 阅读仓库根 `AGENTS.md`。涉及读者内容或写作/审阅 Prompt 时，先读 `docs/OdAIly代码与整体设计/中文写作风格规范.md`。保持 SQLite 为活动存储；不读取旧云数据库连接信息。
2. 查看当前 `git status`、分支和 HEAD，保留其他任务修改。本轮准备执行方案时存在其他任务的 `frontend/src/styles.css` 修改、一份 Solana API 研究笔记，以及含访问凭据的未跟踪 `test.txt`；实际状态以新 session 重查为准。只提交本任务文件，不读出、提交或顺手删除凭据文件。
3. 生产状态、样例与数据规模先到官方服务器只读检查。每次远程操作前说明 SSH 别名 `odaily-official`、Linux 用户 `root`、路径 `/opt/OdAIly` 和用途；WSL 使用 Windows OpenSSH 与 `C:/Users/A/.ssh/config`。
4. **重新核实扩容已在文件系统生效。**2026-11-03 上次测量为总计约40GiB、已用约35GiB、可用2.44GiB、使用率94%。这是历史基线，不是执行时现状。用户说将扩容，不能当作扩容已经完成。
5. 大回填、索引构建、保留期延长、完整库备份或压缩前，估算临时副本、索引、WAL 和回退资产的峰值占用；完成后应仍有至少 `max(10GiB, 文件系统容量的15%)` 可用余量。空间不足时继续本地实现和离线验证，暂缓相应生产写操作，报告测量及缺口；不靠删除业务证据凑空间。禁止在旧余量上直接 VACUUM 或复制大库。

本地只运行测试、构建、离线迁移演练与数据夹具，不启动 OdAIly 产品服务/worker/API，不使用本地产品 SQLite 判断线上事实。生产样例脱敏成小夹具，不将生产数据库复制到仓库。

## 5. 统一记录与查询设计

### 5.1 记录身份与事件

保留各业务原数据库、调度和状态机。推荐新增 `packages/system_observability`，集中实现身份关联、证据引用、尝试历史与查询投影；实现者可调整包名，外部职责必须集中。使用独立本地 SQLite 保存统一读模型和巡检状态；大证据可存本地内容寻址压缩文件，运行资产均在 `data/` 下且不入Git。

统一表达“来源材料 → 业务处理实例 → 产出版本”，支持一对多、分叉和多材料合并。原模块ID保留；同一业务重试不新建信息流主体。明确区分原始发布时间、采集时间、业务创建时间、最后处理时间、投稿/公开发布时间。

最低记录内容：

- **采集窗口**：预期源/频率、尝试、成功/失败/降级、返回数、消费水位、时间范围、分页/截断完整性。成功但无新消息单独表达。
- **处理实例**：业务/流程版本、来源身份、当前阶段与原状态、业务结果、关联事件/任务/产出、首尾时间。
- **每次阶段尝试**：开始/结束、尝试序号、执行器/上游、输入/输出证据引用、规则组合、成功/失败/跳过/降级/未知、错误码和可用请求ID、是否重试及时间。成功不擦除早先失败。
- **规则组合**：模板版本、附加规则、特色配置、输出约束、关键配置和代码revision；按内容hash去重，动态材料用引用组合。hash必须有可取回的内容，不能只留无法解释的hash。
- **产出版本**：模型原始文本、解析后草稿、格式化/组装稿、实际提交稿、回读镜像和审核对象；相同文本复用一份内容，不同版本记录转换关系。
- **投递回执**：真实传入的直发/后台参数、返回码/安全返回摘要、接收方ID及关联状态；HTTP超时可能已被接收，标记结果不确定并沿用原重试边界。

在解析、normalize、规则validate前保存模型原始返回或其证据引用，保证解析失败也有证据。错误应从调用边界获取结构化信息，文本推断仍标明依据与不确定性；记录安全摘要，不保存鉴权头或浏览器认证材料。

### 5.2 可靠性与迁移

业务原库在状态提交时记录小型变更事件/outbox，再增量投影到查询库；跨库不假设事务原子性。允许采用能证明同等可靠的其他设计。投影有单调水位、稳定事件ID、幂等、断点恢复和可重建能力。记录失败/索引落后必须可见；不得静默丢掉成功产出，也不得因观测同步失败而重复发稿。

旧记录有多少回填多少，保留来源库ID和时间；历史缺失、已清理、未保存失败返回、官方ID未关联等明确标注。绝不借当前配置倒填历史规则，也不猜补丢弃理由。增量迁移分批、可暂停恢复，schema迁移幂等；首轮回填不调用AI、不推进业务、不推送快讯/插件提醒。

业务注册目录统一维护流程节点、来源映射、能力与开关状态。流程导览、信息流标签和巡检覆盖读取这份目录。目录和实际运行不一致产生可见缺口；新来源不能因没有写进白名单而永远消失。

### 5.3 信息流界面与查询

- 列表：摘要、入口/信源、当前环节、处理状态、业务结果、异常简述、创建/更新时间；显示快照生成时间、索引落后与受影响模块。默认按创建时间倒序，允许切换最近活动排序。
- 筛选：时间范围、业务/流程分支、具体来源、阶段、状态、业务结果、故障类别、关键词。状态与结果分开：例如技术成功可以对应挂后台、提醒成功、内部分析完成或业务停止。
- 关键词搜索至少覆盖留存的标题、正文/稿件、已有摘要/理由、来源名、帖子ID、任务ID、URL、CA/地址；支持中文两字词和英文大小写。原始大材料清理后不承诺仍可全文检索；提示可搜索范围。词过短时明确说明，不默默退回当前页搜索。
- 过滤先在后端执行，再分页；可筛所有适用业务的直发/挂后台/失败。时间统一规范为可索引UTC数值，显示北京时间，不能直接按混合格式字符串排序。
- 专用受约束查询接口，建议 `/console/system-information` 的列表/详情/统计动作；不允许浏览器任意SQL或文件路径。稳定游标以选定时间和唯一ID排序，刷新才更新快照，不强制实时轮询。
- 列表只读轻摘要，详情再取原文、各次尝试、有效规则和稿件差异；禁止每行附带全阶段大JSON。大证据按需解压和鉴权读取。
- 中文索引需验证实际分词/子串行为；SQLite FTS默认配置不自动满足中文两字搜索。执行者选择可用索引方案并检验，禁止通过逐页拉取或全库大JSON解析实现搜索。

详情默认顺序：业务结果→实际处理时间线与原因→稿件/原文→异常与恢复；技术JSON折叠。历史没有理由显示“当时未保存原因”，不是新一轮AI补写。

## 6. 本地留存默认策略

实施前检查所有现有清理命令，确保它们不会把已登记为保全证据的内容提前删除。首版按下表实行，压缩与引用去重可采用服务器文件，无需把大字段都塞进主库。

| 数据 | 默认策略 |
| --- | --- |
| 信息流主体/来源身份、业务结果、阶段尝试、结构化错误、版本关联、关键回执 | 长期保留；保留可查询轻摘要，长堆栈按hash单独保存。不要用同一行last_error替代尝试历史 |
| 最终稿、实际提交稿、不同的审核/镜像版本、已展示研究结果、有效规则版本 | 去重后长期保留；修改产生新版本 |
| 产出真正采用的原始材料、模型成功/失败原始文本、关键触发事实快照 | 默认完整保留90天，可压缩；到期保留必要证据摘录、来源、版本和结果。待审、未结束、受争议或已固化案例保全到结案，人工认可的回归案例长期留存 |
| 普通最终无候选/无引用帖子 | HotTopic沿用48小时工作窗口；所有相关消费者完成且无引用后才清理。投资线索的组合分析先维持现有30天窗口，不能因“暂未产出”提前删掉仍参与组合的材料 |
| 无候选轻决定索引 | 30天：来源ID、账号、模块、时间、当时规则版本、已有reason_code/短理由；现有模块没有理由就留空，不新增AI调用编造 |
| 无候选抽样原文 | 全系统每日最多50条，按模块/规则/结果分层，14天、原文总量20MiB双上限；长文被截断要标识，不用不完整样本证明完整语义判断 |
| 普通高频行情、采集空轮询和运行明细 | 沿用业务所需短期窗口；按小时汇总长期保留，触发时的关键数值/口径/时间进入保全证据；Gate最近100条/股票500条不能再限制统一结果账本 |

清理只影响达到期限且无保护引用的材料，不修改业务去重账本、锁、市场基线和任务终态。保全/清理引用闭包必须可验证；孤立文件清理有dry-run，先校验引用再删除。空间/增长可见，按当前增长估算未来30天占用；磁盘不足提前提醒人工扩容，不自动把关键证据当垃圾清掉。

## 7. 交互流程导览

两种入口同时交付：

1. **跟着例子走**：选业务入口→选场景→逐步选允许分叉，展示本步目的、判断依据、可能下一步和终点；能返回改选、重置、展开其他分支。使用标明为示例的数据，不触发真实任务/AI/发布。
2. **查看实际路径**：从信息流实例打开相同流程图，只高亮已记录路径，明确跳过、重试、等待、降级与终点。旧数据缺某步即标记未知，不按目录补出“已经执行”。

覆盖第4节所有业务路径。Meme至少可选迁移、TG热议、今日热门及Grok等待/降级；Hyperliquid区分普通提醒和新闻场景，场景从注册目录展开；行情展示阈值、防重复、合并、直发/后台。多个信号合为一稿能回查全部输入。

默认文案面向新接手管理员：“已收集帖子，判断是否值得报道”“发现重复，停止写作”“材料不足，稍后重试”。隐藏 `tasks.source`、job、状态枚举等实现术语；需要的技术映射放开发详情。规则/路径变更必须同步注册目录和对应模块文档，测试检查关键分支覆盖。

## 8. AI质量中心：既有一项、新增五项

保留现有AI审阅的两类竞品事件、原始链接要求、推荐信源功能、历史人工决定及预算，不改造成另一个万能Prompt。新增问题任务复用证据与人工审阅交互，单独管理状态和用量。

| 任务 | 触发与输入 | 检查与输出 |
| --- | --- | --- |
| A. 信源扩展（现有） | 沿用现有每日任务，最近3天竞品先发我们后发/多家竞品发我们没发的事件与原链接 | 给值得持续关注的原账号/网站及报道证据；不自动添加监控 |
| B. 渠道中断 | 每5分钟复用监督者，读取启用计划、逐源采集成功/错误、水位、消费与积压 | 连续3次计划尝试失败，或距应成功窗口超过 `max(3×配置间隔,15分钟)`，生成问题；休市/停用不算故障。限流冷却不误报进程失活，但底层上游异常仍进入降级/故障汇总。展示影响范围、起止、错误、是否恢复。成功空结果不算中断 |
| C. 漏闻复盘 | 每日复用A的事件窗口，按原帖ID/URL查覆盖配置、轻决定索引、任务、回执和公开稿 | 区分未配置、采集异常、已丢弃、判重、写作失败、已后台收稿、公开稿关联缺失、本来只做内部研究；有原文才能复核错筛。只对明确事件有界回取，不全账号回扫；无历史证据写无法判断 |
| D. 产出与审核复盘 | 每日处理新增审核标记和人工驳回；抽查最多30项已通过/未被标记的稿件、热点与投资线索；另检查无候选抽样 | 先对齐输入、各稿件与审核版本，再区分来源矛盾、写作错、程序组装、版本变化和审核误报。热点/线索检查归因、条件、时间和推导越界；同根因合并并给修改位置。不存在官方改稿事件时不能猜是人工还是镜像错 |
| E. 规则冲突与执行 | 活动规则/配置/代码版本变化后异步检查受影响组合；每日扫新增产出的确定性要求 | 比较同一场景有效模板与附加规则，输出互相矛盾的原句和适用条件；验证固定开头、强制后台、结构化时间/金额等已明确要求。先确定性检查，再AI复核复杂冲突；不把不同场景合理差异判冲突，不新增未获确认的编辑规则 |
| F. 故障与恢复汇总 | 每日，兼容B的紧急异常，读取逐次错误/重试/停止和恢复 | 按上游+错误码+阶段+版本聚合“影响多少、恢复多少、还卡多少”；根因未知保持未知。复用现有故障分类，不建立相互矛盾的第二套分类 |

日常任务默认北京时间06:00后运行一次，按日期/策略版本幂等；进度跨轮询可恢复。E按规则内容hash触发，仅看变化组合。执行应复用合适的现有常驻调度，若确需新worker，加入systemd、心跳、重试、监控与文档，不能只增加一个无调度的CLI。

新巡检合计初始每日最多100次模型请求、100万输入tokens，达到任一上限保留积压顺延，不当作通过；预留预算后调用、按实际用量结算，重试也计入。复用现有适合的模型路由和超时配置。确定性巡检不消耗模型预算；现有信源审阅预算保持独立。任务失败最多自动尝试3次，错误、预算暂停、证据不足分别呈现。

问题卡至少包括：具体问题、发现类别、影响交易/名誉的程度、受影响范围/计数、期望与实际、可点击证据和相反证据、归因确定性、建议修改位置、验证方法、首次/最近发生、是否恢复、人工认可/驳回/暂缓及理由。不要只输出“请优化Prompt”。

稳定问题键按根因+适用规则/版本组合生成；新增受影响实例更新原卡，实质新证据才重新提醒。人工作过决定的卡保留决定历史；后续新问题不能被同名旧驳回永久屏蔽。运行恢复不等于人工认可，二者分开记录。

渠道异常/故障复用现有监督者Telegram告警去重；质量问题默认在控制台集中待审，不新增正常巡检刷屏或新的外部消息目的地。系统审阅不能自行发稿、改规则或添加来源。

三种验收卡的预期形态（示例，不是本次新生产事实）：

- **规则冲突**：链上模板要求“据{发言人}监测”，同场景附加规则允许“发文称”；展示两处原句、版本、受影响稿件和建议校验。既有修复仍生效，不能为了演示再次制造冲突。
- **版本误归因**：定稿和提交稿无漏字，镜像有漏字，审核针对镜像；结论是无法归责编写者，提示核对外部修改/镜像，不能自动记作审核误报。
- **故障恢复**：上游限流影响12项、9项重试恢复、3项耗尽；一张卡可展开12项，保留原错误和恢复过程。

## 9. 实施顺序、测试与完成标准

按S0→S1→S2→S3→S4推进。可在接口确定后并行完成界面和采集接入；每步都是真实可验收增量，不在任一步声称整个任务完成。

| 步骤 | 实施 | 完成标准 |
| --- | --- | --- |
| S0 | 生产只读核查、覆盖/存储/清理矩阵，记录基线 | 第4节各业务逐一有实际来源和成功定义；已验证扩容，或明确把生产重操作留作待办并继续本地开发 |
| S1 | 统一身份、尝试、证据、规则组合、版本与回执，增量投影/回填 | 主链路解析失败原始返回可查；重试后成功仍有之前错误；回填重跑不重复且不投递业务；各业务接入均有样例 |
| S2 | 导航、全量信息流、服务端搜索过滤和按需详情 | 原有页面全可访问；中文关键词搜到当前页之外记录；跨业务筛直发/后台/失败；投影落后可见；没有虚构状态和重复统计 |
| S3 | 流程导览、运行健康、证据清理/保全 | 所有业务有目录；X链上、Meme、Hyperliquid、股票合并稿各有可探索分叉和真实路径；保全证据不被旧清理误删 |
| S4 | B—F实际调度、质量问题页、用量与人工闭环；保留A | 三种验收卡能由检查逻辑生成；人工决定可持久化；预算暂停/故障/恢复有记录；新增同步AI调用数为0 |

必要验证：

1. 后端测试使用临时SQLite/压缩证据夹具；外部模型、抓取、发布、Telegram均mock。重点验证幂等、水位恢复、多消费者引用、来源身份/合并、真实中文搜索、混合时间迁移、解析失败证据、超时投递不确定、原始状态保留、版本归因与去重提醒。
2. 留存测试覆盖到期普通材料删除、未完成/待审/回归案例保全、引用闭包、重复内容去重、原文删除后的明确缺口；长期账本不能被独立模块的条数上限删掉。
3. 巡检测试使用明确正/反例：成功无新帖、已停用、休市、预算暂停不是隐性丢失；内部研究完成不是漏发；不同规则适用路径不是冲突；有镜像差异不直接判人工或模型责任。
4. 性能离线夹具至少10万处理实例，包含中文/长稿件/多个来源。首屏及跨页关键词、状态筛选、深分页各测试；预热后至少10次记录p50/p95。首版目标：列表/索引查询p95≤1秒，生产服务端列表接口p95≤2秒；端到端另记网络/渲染。未达目标需定位优化，不能只写“有分页应该快”。
5. 前端执行现有构建并验收登录、导航、筛选、分页、错误/空状态、展开详情、证据与版本差异、人工决定和流程分支。可用浏览器工具时实际交互；不以TypeScript编译代替交互验收。
6. 按改动运行相关旧后端回归，检查 `pytest.ini` 当前发现范围，显式包含所改业务的 `backend/test_*.py`，不假定裸pytest会覆盖它们。既有Meme测试依赖未mock导致的旧失败应核实，不能自动当作与本次无关。

实现者持续更新一份简短进度/验收清单：每项完成状态、命令和结果、性能基线、已知缺口、迁移与回退步骤。最终每个业务至少有一个可核对处理实例；未启用/无当期样例的用离线夹具验证并明确覆盖性质，不伪造生产样例。

## 10. 文档、部署与验收交接

修改实现时同步维护：`完整程序架构.md`只补系统契约和索引；`控制台.md`及信息流/流程展示/AI审阅细节、`监督者.md`、相关生产模块文档各维护自己的规则。新增统一记录与系统巡检细节文档，集中记录字段、保留期、命令、调度、错误处理和迁移。旧文档中“仅查当前页”“只覆盖旧来源”等说明随实现替换。

发布范围由新session收到的用户指令确定。用户明确要求按本方案完整实施并部署时，正常流程是：本地代码/文档和测试完成→只暂存本任务修改→提交并推送GitHub→官方服务器fetch、pull --ff-only→执行经演练的增量schema迁移/回填→只重启受影响后端→验证前端Vercel构建与生产功能。遵守AGENTS，不在生产手工覆盖repo-tracked文件。

首次启用前保存可用的回退资产与上一个代码版本，说明新增schema向后兼容及如何关闭新采集投影/巡检。关闭观测模块不应停掉原生产业务；回退不删除新证据、不重投已提交稿件。生产查询索引回填完成前显示初始化/落后状态，不能展示假“0条”。

生产验证至少检查：磁盘剩余与增长、HEAD/工作树、相关服务/心跳、主链路正常推进、代表业务可查询、投稿没有因回填重复、CJK历史搜索、每次尝试详情、已保留的旧AI审阅决定、新巡检已真正调度且人工操作持久化。验证只读为默认；不得为了验收制造真实对外发稿或篡改生产原文。

若用户只要求本地实施，完成本地可发布产物并说明生产尚未验收；若已授权部署但仅扩容未就绪，完成可独立完成的工作并保留准确阻塞项，不能把部署未完成写为全任务完成。执行者不要自行创建新聊天，也不要向引用聊天发送消息。
