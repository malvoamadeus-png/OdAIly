日期：2026-11-03。状态：历史现状核查与研究依据，产品功能尚未实施。

**实施请直接阅读[控制台与系统自评改造执行方案](2026-11-03-控制台与系统自评改造执行方案.md)，它是唯一执行规格。**

最终决定：显示名为“Odaily快讯总览”；需要保存的数据留在官方服务器，用户扩容；关键证据使用本地SQLite与本地压缩归档，海量无用原文仍按工作窗口清理。先前的云端外迁候选方案已撤下。留存期限、巡检任务、交付范围与验收以执行方案为准，新session无需重新完成一轮方案讨论。

## 结论与根本目的

用户的四类诉求可以归纳为同一个目标：让 OdAIly 成为一套别人能理解、管理者能追溯、AI 能根据证据主动发现偏差的生产系统，逐步减少开发者凭记忆解释和人工逐条找问题。

当前瓶颈在于：业务链路持续增加，而导航分类、流程说明、任务查询和质量复盘的覆盖范围各不相同。已有记录也没有形成跨链路、跨尝试、跨稿件版本的一致证据。

建议形成三项共用基础：

1. **业务流程目录**：有哪些生产入口、如何分叉、哪些规则适用、预期结果是什么。
2. **信息处理档案**：一条信息实际经过什么处理、基于什么材料和规则、得到什么结果。
3. **评审标准与案例**：什么算符合设计、什么会影响交易判断或名誉、已认可和已驳回的问题分别是什么。

控制台分类、交互流程导览、全量信息流和 AI 巡检都使用这些基础，避免分别维护四套解释。

## 已核实的现状

| 方面 | 现有能力 | 本轮核实的缺口 |
| --- | --- | --- |
| 导航 | 已有信源、生产规则、业务专题、监控和质量页面 | 多种层级混为一级栏目；同一业务的配置、结果和说明缺少相互入口 |
| 任务记录 | 主链路保留原始信息、阶段结果、写作者原始输出、模板版本、定稿、发布理由与推送结果 | 阶段结果主要更新同一行；成功会清空最后错误；不能据此还原每次失败和恢复经过 |
| 失败诊断 | 已有欠费、限流、鉴权、网络、解析等分类；任务详情懒加载诊断 | 相当部分根因来自错误文本推断；跨独立业务链路覆盖不一致；重试历史不足 |
| 信息周期监控 | 最近任务分页，支持主链路部分来源 | 搜索与主要筛选作用于当前页；来源名单漏掉已进入主任务表的 Hyperliquid、MSX、事件追踪，也没有统一独立业务库 |
| 流程展示 | 前端静态目录，展示主要快讯与标题提醒链路 | 技术字段占用默认视图；缺少多条独立链路；无法沿具体场景逐步选择与探索 |
| 监督者 | 心跳、队列、失败、卡住任务与异常告警 | 不等于按每个信源检查采集完整性，也不判断产出是否符合业务设计 |
| AI 审阅 | 从两类竞品事件中发现值得持续关注的原始信源，保存人工决定 | 当前范围专门针对信源建议，不承担全系统一致性评审 |
| 数据保留 | 已有分模块清理策略 | 主链路大字段默认 7 天后可清理；Meme 普通详情保留 3 天；行情诊断有条数上限。历史上“搜不到详情”可能是正常清理，必须明确展示 |

## 生产只读测量

访问目标：Windows SSH 别名 `odaily-official`，Linux 用户 `root`，仓库 `/opt/OdAIly`。主状态库以 `mode=ro` 和 `query_only=on` 读取；不复制数据库，不读取数据库连接密钥。

- 当时生产提交为 `5692dc0`，工作树干净。
- `odaily*` 服务列表有 28 项处于 active，其中包括独立的 `odailyseer-*`，因此不能把这个数量当作 OdAIly 业务模块数量，也不能以 active 证明业务输出正常。
- 主 SQLite 文件约 11.1 GB，`tasks` 当时共 99,166 条。最近 3,000 条任务实际出现 `hyperliquid_news / msx / event_tracking`，周期页的来源名单没有这些值。
- 按周期页实际来源、字段、时间排序、51 条分页做一次直接 SQL 测量：任务读取 **3.619 秒**；随后 51 次阶段读取 **0.045 秒**；组装的原始 JSON 约 **226 KB**。没有测量真实浏览器端到端耗时或网络压缩体积。
- 同样时间排序只取 ID，仍需 **2.428 秒**。对照按 ID 排序约 **0.021 秒**，仅用于定位排序成本；ID 排序不具有与创建时间排序相同的语义，不是可直接采用的修复。
- 查询计划使用 `idx_tasks_source_status_created(source,status,created_at)` 筛来源，再 `USE TEMP B-TREE FOR ORDER BY`；`datetime(created_at)` 和当前索引顺序无法直接提供需要的排序。分页条数小，并不能保证数据库只处理 51 行。
- 最近 30 分钟、每服务最多 200 行日志的有界样本中，流水线有 5 行包含 `database is locked`，监督者有 1 行。它们表明运行健康仍需关注；本轮没有证明锁竞争造成上述页面查询慢，也没有展开锁故障根因诊断。

性能建议：专用轻量列表查询、统一可索引的 UTC 时间、匹配筛选与排序的索引、稳定游标分页、详情按需读取。筛选和搜索在服务端执行；中文搜索需明确支持的子串、分词、地址与精确 ID 语义，不能假定默认全文检索就能处理全部中文关键词。优化后要以相同数据窗口测量首屏、跨页搜索和深翻页，记录数据库、接口、传输与渲染各段耗时。
