## 一、目标

OdAIly 要代替新闻值班人员发现正在发生的事，并继续盯住少数会在数小时到数天内出现关键进展的事件。完整自动链路固定为：

```text
HotTopic
  -> GPT 判断是否值得短线追踪
  -> GPT Web Search 搜索 X 账号候选
  -> FXTwitter 读取账号简介和最多 4 条最新原创帖
  -> AI 判断是否为事件主体/直接涉事者
  -> 通过身份判断的账号加入事件追踪列表
  -> 事件主体/直接涉事者账号发出新帖
  -> GPT 判断是否为该事件的实质进展
  -> 全站查重、写作、格式化
  -> 挂入后台，人工审核后发布
```

事件账号不会变成普通 X 信源的一部分。搜索只提供候选；程序读取候选账号的公开简介和最近原创帖子，由 AI 判断其是否代表事件主体/负责处置主体或直接涉事者。媒体、研究员、KOL、社区、行情/链上观察和其他转述者不纳入追踪。通过身份判断后，账号帖子仍需判断与事件的相关性和信息增量，只有实质进展才进入主快讯链路。账号关系属于 AI 对公开资料的判断，不是外部认证；帖子主张仍由人工在发布前审核。

### 账号身份判断

GPT 搜索最多返回 3 个符合 X handle 格式的候选，不要求搜索引用或官网链接。程序通过 FXTwitter `/2/profile/{handle}/statuses` 读取简介和最多 4 条最新原创帖子；身份判断 Prompt 只以这些公开资料判断账号是否代表事件主体/负责处置主体或直接涉事者，不使用搜索结果中的身份推测。身份判断结合简介、显示名和近期原创帖的整体内容，不要求引用逐字匹配或外部身份证明。只有 `subject` 或 `directly_involved` 可以通过；媒体及其他第三方不会追踪，资料明显不足时判为 `unclear`。

FXTwitter 或身份模型暂时失败时，不把候选作为已通过账号，也不重复 Web Search；搜索结果与身份判断状态保留，后续只重试资料读取/身份判断。升级前仍活动的账号绑定统一进入待判断状态，在通过前不轮询、不分析帖子、不投递快讯。最近 72 小时内由旧身份规则判为 `unclear` 的已结束事件，会自动复用原候选开启一次身份复查 cycle，不重复 Web Search。新候选也必须通过同一身份判断。

### 不存在人工运行时闸门

- 任务 1 只有 `track` 和 `do_not_track`，不存在“需要人工确认”。证据不足是 `do_not_track`；模型、网络或结构化输出失败是可见的自动失败，按重试规则处理。
- 账号候选发现、身份判断、启用、延长和自动结束由系统执行；通过身份判断后无需值班人员确认即可追踪。只有实质进展稿件进入编辑后台，编辑在发布前人工审核。管理员也可以人工忽略一条事件，语义是停止追踪并软删除控制台展示。

## 二、领域模型与状态

### 1. 事件不是单条 HotTopic

`tracking_event` 是可长期引用的真实事件线，例如“Bitget 热钱包异常转账”。它与 `topic_id` 不是一对一关系：同一事件的异常转移、提币处理、冻结地址、赔偿说明可以形成多条 HotTopic，但应归入同一个 `tracking_event`。新的相关 HotTopic 只补充事件证据，不再次发现账号或重复开一条追踪线。

每次进入追踪创建一个 `tracking_cycle`。同一事件后来出现新的重大发展时，复用 `tracking_event`，创建新的 cycle，保留上一轮的判断、账号和结束原因。

### 2. 必要记录

事件运行库位于现有 `data/runtime/hottopic.sqlite`，但使用独立表，不复用 `hottopic_accounts` 或 `hottopic_inbox`：

- `event_tracking_events`：事件主线、归并键、当前 cycle、关联 HotTopic、追踪理由、状态和终止原因；
- `event_tracking_cycles`：开始、最后实质进展、到期、硬上限、结束原因；
- `event_tracking_account_discoveries`：一次 GPT Web Search 的工具调用、引用、候选结果、模型和 Prompt 版本；
- `event_tracking_accounts`：规范化 handle、公开主体信息、有效状态和下一次轮询时间；
- `event_tracking_bindings`：事件与账号的关系、身份判断状态及审计结果、启用原因、最后贡献；
- `event_tracking_inbox`：事件专用的候选账号原帖，按 `tweet_id` 幂等；
- `event_tracking_updates`：相关性和实质进展判断、证据、使用模型、已知时间线；
- `event_tracking_publication_outbox`：跨库快讯投递、主任务 ID、幂等键、重试和最终结果；
- `event_tracking_audit`：所有模型决策、自动启用、拒绝、结束和失败的审计。

普通 HotTopic 的 `hottopic_inbox` 和市场情绪、项目推介的分析任务不消费事件专用 inbox。反过来，事件账号也不把原帖回灌进普通 HotTopic。

### 3. 自动状态

事件 cycle 使用 `discovering`、`active` 和 `ended`。Web Search 或身份资料暂时不可用时，cycle 保持 `discovering` 并保留待重试状态；身份判断完成但没有符合条件的账号时结束 cycle，原因记录为 `discovery_failed`；无实质进展时记录 `silence_24h`；达到保护上限时记录 `hard_cap_7d`。

## 三、任务 0：GPT Web Search 账号候选发现

GPT Web Search 替代 Grok，且只承担一次性账号发现，不承担后续抓取或发稿判断。

### 调用与成本边界

- 每个新 cycle 最多一次初始搜索；只有请求或结构化响应失败时，才允许一次有界重试。
- 不因“没有找到账号”重复搜索，也不每分钟重新搜索。后续新证据只能在新的 cycle 再触发发现。
- 输入只给事件标题、摘要、最近时间线和少量代表性证据；不上传历史全量帖子。输出最多 3 个候选。
- 程序保存 Responses 原始工具类型、引用 URL、usage、模型、耗时和失败分类作为审计数据；工具调用和引用不作为候选准入条件。GIWA 实测曾消耗 59,997 tokens，继续观察真实 usage，不以手写 Prompt 长度估算成本。

### GPT 输出与自动纳入

GPT 输出最多 3 个候选，至少包含 handle；显示名和候选理由可选。程序检查 handle 格式并去重，再对每个候选读取 FXTwitter 简介及最多 4 条最新原创帖子，由 AI 评估主体关系。该阶段不要求 Web Search 引用、官网主页或官方关系证明，也不要求身份理由逐字引用资料。只有 AI 判断为主体/直接涉事者的候选建立 active 绑定；媒体等第三方和身份资料明显不足的候选不会被轮询。暂时性接口或模型错误会保留候选并在后续 worker 周期重试，不重复调用 Web Search；没有合格候选且身份检查无待重试错误时结束该 cycle。

## 四、任务 1：是否值得短线追踪

任务 1 的分类是解释和观测标签，不是人工工作流。模型只能返回 `track` 或 `do_not_track`。

只有同时满足以下条件才可 `track`：

1. 对读者的资产安全、交易环境、持仓判断，或高传播的花边、争议、趣味事件有明确价值；
2. 不是已经结束的标准化单点动作；
3. 未来数小时到数天内，官方主体或涉事者本人有合理动机继续回应、调查、处置、辟谣、赔偿、公布结果或升级处理；
4. 下一条官方信息可能明显改变读者对“发生了什么、谁负责、钱怎么办、争议是真是假”的理解。

可追踪的少数类型为：

- `security_asset_incident`：被盗、攻击、假链/假桥、漏洞、资产冻结、交易所/链/协议重大异常、用户资产损失和严重服务事故；
- `official_dispute_or_denial`：高关注度的账号被盗、合作或授权真假、责任归属、重大指控、项目方与用户冲突、名人或机构争议，且等待当事人公开回应；
- `exceptional_project_decision`：影响资产迁移、交易入口、协议存续或项目命运的罕见重大决定，例如重大链迁移或生死存亡级回购/销毁。

普通上线、开放、关闭、解锁、投票、回购、销毁、产品发布、长期法案、价格波动、仓位、爆仓、巨鲸买入、做市商吸筹、一次性转账和仅靠第三方链上追踪才会继续更新的事情，默认 `do_not_track`。

证据不足也输出 `do_not_track`，但系统会在同一真实事件出现新的 HotTopic 证据时重新判断；这不是人工确认队列。

## 五、任务 2：自动加入事件追踪列表

当前实现先在 HotTopic 层确认同一真实事件并归并话题。任务 1 输出 `track` 后仅为该 HotTopic 创建或更新其 `tracking_event` 和 `discovering` cycle，不再在追踪层按身份词寻找其他 HotTopic 的事件。若两个已经追踪的话题后来归并，保留一个事件并终止另一事件的未发布工作。

账号选择遵循以下运行容量限制：

- 单个 event 最多 3 个候选账号，按搜索相关性顺序选择；
- 全局最多 15 个激活事件账号；容量满时，不挤掉正在追踪的账号，新 event 记录 `capacity_exhausted` 并自动结束；
- 一个 handle 被多个事件使用时只保留一条事件轮询记录，以绑定数服务多个事件；
- 事件账号只存在于事件追踪表，不自动写入人工 X 信源账号、HotTopic 基线账号或其订阅开关。

身份资料读取和事件账号轮询共用 FXTwitter 客户端、统一 2 秒 pacer、429 冷却和退避。只有 `identity_status='verified'` 的事件主体/直接涉事者绑定进入调度队列；待判断、被拒绝或身份不明的账号不会抓取事件新帖。最多 15 个已通过账号时，2 秒 pacing 能在一分钟内完成一轮请求；正常目标是每账号 1 分钟。每次抓取只取新帖并写入 `event_tracking_inbox`。

## 六、任务 3：实质进展、自动发稿与生命周期

### 1. 实质进展判断

每条已通过身份判断的事件主体/直接涉事者账号新帖都先用 GPT 与该 event 的已知时间线比较，只能输出：

- `material_progress`：新增可报道信息或主张，可能明显改变事件理解，例如影响范围、资金处置、调查发现、风险控制、服务恢复、冻结追回、赔偿、责任判断或争议升级；
- `relevant_no_progress`：与事件有关但只是重复、安抚、营销、转发、无新增事实或旧结论换说法；
- `irrelevant`：与事件无关。

只有 `material_progress` 可以写入发布时间线、延长 cycle 和进入快讯投递。该判断同时给出 `news_type`（`regular`、`onchain` 或 `funding`）、事实摘录、与上一条的差异和可信度。账号与事件的关系已经由公开简介/近期原创帖的 AI 判断通过，但这不是外部认证；帖子只能证明账号发布了这些内容，主张仍须保留归属并由人工审核。

### 2. 快讯桥接

`material_progress` 不直接调用发布接口。它先进入 `event_tracking_publication_outbox`，再通过一个窄的发布 Adapter 跨越到主 SQLite：

```text
event_tracking_updates
  -> publication outbox
  -> tasks(source='event_tracking', status='judged')
  -> search -> write -> format_publish -> ready_review -> human review -> publish
```

Adapter 在一个主库事务中写入任务和 `x_task_pipeline` 的专用判断结果，使用事件主体/直接涉事者账号 `tweet_id` 作为 `source_item_id` 和跨库幂等身份，并保存账号身份判断摘要。它预先写入 `news_type`，因此不再运行普通 X 的初始判断器；但必须运行全站搜索者，和 Odaily 历史、运行中 candidate、近期已处理内容查重。查重判定为重复时，outbox 记录 `duplicate`，不会发稿。

`event_tracking` 需要成为主写作链路的显式 source。写作和格式化复用既有模板、格式校验、失败重试和监控；发布阶段使用通用人工复核路径，以 `isPublish=false` 挂入编辑后台并将任务置为 `ready_review`。编辑审核并决定发布后才公开。后台推送以任务 ID 幂等，保证 worker 重试和服务重启不会重复创建稿件。

发布前的写作或后台推送失败遵循现有自动重试和可见失败记录；只有成功挂入后台后才等待人工审核。编辑审核不由自动 worker 执行。

### 3. 生命周期

- cycle 初始最长观察窗口：72 小时；
- 从最近一条 `material_progress` 起 24 小时没有新的实质官方进展，则自动结束，原因 `silence_24h`；初始事件本身记为起点，因此无任何后续官方更新时也会及时结束；
- 每条 `material_progress` 最多把当前窗口延长 48 小时；
- 从 cycle 开始计算，任何情况下硬上限是 7 天；到期自动结束，避免无限续订；
- 之后若同一真实事件出现新的重大 HotTopic，先在热点层归入现存主题，再由该主题复用原 `tracking_event` 并按生命周期需要开启新 cycle。

结束时解除该 cycle 的账号绑定。没有其他活跃绑定的事件临时账号停止轮询；账号和所有审计记录保留，以便以后复用和复盘。

## 七、Prompt、模型与控制台

### Prompt

- 任务 1、账号候选发现和事件更新判断各自使用不可变的版本号和完整 Prompt 快照；每次结果存入对应审计记录。
- 控制台只读展示当前 Prompt、版本、生效时间、调用次数和使用该版本的事件；不提供编辑、复制回写或人工确认按钮。
- 未来若由 AI/开发流程修订 Prompt，必须新建版本，不能改写已使用的文本或历史结果。

### 模型

- 任务 1、实质进展判断和身份判断：默认 `gpt-6-luna`，失败时使用 `gpt-6-luna` fallback 路由，两次均按各自 JSON 契约运行；身份判断可通过 `HOTTOPIC_EVENT_IDENTITY_MODEL` 和 `HOTTOPIC_EVENT_IDENTITY_RETRY_MODEL` 覆盖；
- 账号候选发现：使用支持 Responses `web_search` 的 GPT 路由；返回有效 handle 后，再用 FXTwitter 公开简介和最多 4 条最新原创帖输入身份判断 Prompt；只有 `subject` 或 `directly_involved` 判断通过。FXTwitter 或模型暂时失败时保留结果并重试身份判断，不重复 Web Search；
- 账号身份判断：默认使用事件追踪文本模型配置，失败时按 fallback 模型重试；保存身份结论、公开资料、判断理由、Prompt 版本和失败原因；
- 所有模型调用在 SQLite 短事务外执行，持久化实际模型、Prompt 版本、usage、耗时、重试与失败原因。

### 控制台

`X Agent / 热点自动快讯` 是事件上下文运营视图，展示：

- 激活和近期结束事件、当前 cycle、追踪理由、类型、剩余时间和自动结束原因；
- 通过身份判断的账号、判断理由和引用、最后轮询、最近贡献；
- Web Search 候选的身份判断结果，包括被拒绝的第三方、身份不明和暂时读取失败；可展开查看简介及最多 4 条最新原创帖；
- 账号原帖、进展判断、差异说明、快讯任务、查重或发布结果；
- 只有 `material_progress` 的已通过身份判断账号帖子进入快讯投递区；投递区展示任务状态、生成阶段、可用草稿或终稿标题/正文、发布决定、失败原因、时间和原帖链接。`ready_review` 表示已挂后台，须由人工审核后发布；
- GPT 搜索工具调用、引用、Prompt 版本、模型 usage、失败与重试。

它不提供账号手工添加、人工修改身份判断、暂停、恢复或 Prompt 编辑，但提供“删除热点自动快讯”操作。删除通过人工忽略记录软删除事件：结束活动 cycle、释放账号绑定、取消尚未发布的 outbox，并将已进入主 SQLite 的未完成 `event_tracking` 任务置为 `event_tracking_cancelled`；事件从默认 dashboard 隐藏，后续同一事件身份不会重新创建。搜索、写作、格式化和发布阶段都检查取消状态，最终挂后台前再次检查，已经进入后台或已发布的稿件不回滚。

删除接口为 `POST /console/auto-newsflash/dismiss`，请求体为 `{ "event_id": "tracking-event:..." }`。接口要求控制台管理员认证，返回事件隐藏结果、取消 outbox 数量和取消任务数量；缺少 `event_id` 返回参数错误，不存在事件返回未找到，重复删除返回幂等成功。事件原始记录、候选账号帖子、进展判断、发布记录与人工操作审计仍保留，当前网页不提供恢复入口。
