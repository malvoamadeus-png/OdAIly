# 热点自动快讯：事件追踪升级计划书

## 文档状态

- 状态：已完成本地实现与回归测试，等待部署授权；本文件是该模块的正式业务与跨模块契约。
- 任务 0 已完成：项目网关已实测 GPT Responses `web_search`，GIWA 样本返回真实 `web_search_call` 和 URL 引用。Grok 的 X Search 因额度不可用，不再是本模块依赖。
- 任务 1 已完成：追踪判断只保留少数短线新闻线，使用二元 `track` / `do_not_track` 结果；当前 Prompt 见《热点短期持续追踪类别尝试性报告》。
- 当前代码已实现独立事件表、调度、发布桥接和只读控制台页面；尚未代表已部署到生产。

## 一、目标

OdAIly 要代替新闻值班人员发现正在发生的事，并继续盯住少数会在数小时到数天内出现关键进展的事件。完整自动链路固定为：

```text
HotTopic
  -> GPT 判断是否值得短线追踪
  -> GPT Web Search 发现并核验官方 X 账号
  -> 自动加入事件追踪列表
  -> 官方账号发出新帖
  -> GPT 判断是否为该事件的实质进展
  -> 全站查重、写作、格式化
  -> 自动发布 Odaily 快讯
```

这不是“把某些账号变成普通 X 信源”。事件账号的每条帖文都必须先证明与该事件相关且有实质信息增量；普通帖、营销帖、重复澄清、第三方观察和无关内容不得进入 HotTopic 或主快讯链路。

### 只追踪官方账号

最终可读取的账号只能是事件主体的官方公开渠道：

- 项目、交易所、协议、公司、基金会、链、官方安全团队、官方母品牌、监管或执法主体的官方账号；
- 涉事自然人的本人公开账号，且必须有官网、认证资料或其本人长期公开身份可验证，且该账号是其对本事件作正式回应的渠道。

媒体、链上追踪机构、研究员、KOL、社区号、转发号、Lookonchain、Odaily、ChainCatcher 以及未证实的“内部人士”一律不是可追踪候选。它们可以出现在 HotTopic 证据或 GPT 搜索引用中，但绝不能被自动加入事件账号列表。

### 不存在人工运行时闸门

- 任务 1 只有 `track` 和 `do_not_track`，不存在“需要人工确认”。证据不足是 `do_not_track`；模型、网络或结构化输出失败是可见的自动失败，按重试规则处理。
- 账号发现、身份核验、启用、延长、结束、是否发快讯全部由系统执行；没有等待值班人员点击确认、暂停、恢复或结束的状态。
- 人可以在事后通过代码、配置或 Prompt 版本修复错误，但控制台不提供逐事件的人工审批入口，后台也不得把失败伪装成“等待人工”。

## 二、领域模型与状态

### 1. 事件不是单条 HotTopic

`tracking_event` 是可长期引用的真实事件线，例如“Bitget 热钱包异常转账”。它与 `topic_id` 不是一对一关系：同一事件的异常转移、提币处理、冻结地址、赔偿说明可以形成多条 HotTopic，但应归入同一个 `tracking_event`。新的相关 HotTopic 只补充事件证据，不再次发现账号或重复开一条追踪线。

每次进入追踪创建一个 `tracking_cycle`。同一事件后来出现新的重大发展时，复用 `tracking_event`，创建新的 cycle，保留上一轮的判断、账号和结束原因。

### 2. 必要记录

事件运行库位于现有 `data/runtime/hottopic.sqlite`，但使用独立表，不复用 `hottopic_accounts` 或 `hottopic_inbox`：

- `event_tracking_events`：事件主线、归并键、当前 cycle、关联 HotTopic、追踪理由、状态和终止原因；
- `event_tracking_cycles`：开始、最后实质进展、到期、硬上限、结束原因；
- `event_tracking_account_discoveries`：一次 GPT Web Search 的工具调用、引用、候选、核验结果、模型和 Prompt 版本；
- `event_tracking_accounts`：规范化 handle、官方身份依据、有效状态和下一次轮询时间；
- `event_tracking_bindings`：事件与账号的关系、优先级、启用原因、最后贡献；
- `event_tracking_inbox`：事件专用的官方原帖，按 `tweet_id` 幂等；
- `event_tracking_updates`：相关性和实质进展判断、证据、使用模型、已知时间线；
- `event_tracking_publication_outbox`：跨库快讯投递、主任务 ID、幂等键、重试和最终结果；
- `event_tracking_audit`：所有模型决策、自动启用、拒绝、结束和失败的审计。

普通 HotTopic 的 `hottopic_inbox` 和市场情绪、项目推介的分析任务不消费事件专用 inbox。反过来，事件账号也不把原帖回灌进普通 HotTopic。

### 3. 自动状态

事件 cycle 的业务状态只使用：`discovering`、`tracking`、`ended`、`failed`。`failed` 是自动任务重试耗尽后的运行事实，不是人工待办状态。账号发现没有可用官方候选时记录 `discovery_failed` 结束原因；无实质进展时记录 `silence_24h`；达到保护上限时记录 `hard_cap_7d`。

## 三、任务 0：GPT Web Search 官方账号发现

GPT Web Search 替代 Grok，且只承担一次性账号发现，不承担后续抓取或发稿判断。

### 调用与成本边界

- 每个新 cycle 最多一次初始搜索；只有传输失败、无真实工具调用或引用解析失败时，才允许一次有界重试。
- 不因“没有找到账号”重复搜索，也不每分钟重新搜索。后续新证据只能在新的 cycle 再触发发现。
- 输入只给事件标题、摘要、最近时间线和少量代表性证据；不上传历史全量帖子。输出最多 3 个候选。
- 程序必须保存 Responses 原始工具类型、`web_search_call` 数量、引用 URL、usage、模型、耗时和失败分类。GIWA 实测曾消耗 59,997 tokens，正式实现必须观察真实 usage，不以手写 Prompt 长度估算成本。

### GPT 输出与自动核验

GPT 只能输出官方候选，并为每个候选给出：handle、主页 URL、主体、官方身份依据、事件直接关系、事件后可能发布的内容、支持引用和置信度。任何第三方类型必须明确输出为拒绝项，不能混入候选列表。

候选自动启用前必须同时满足：

1. Responses 结果包含真实 `web_search_call` 和至少一个可追溯引用；
2. GPT 必须以官网/官方资料与 X 链接或 handle 的引用形成身份闭环；后续抓取只接受该 handle 自身发出的原帖；
3. 有官方身份闭环：官方域名链接该账号，或该账号资料可回链到官方域名/组织，或可验证为涉事自然人的本人公开账号；
4. 引用能证明该主体与本事件有直接关系，而不只是名称相似；
5. 账号类型不是媒体、研究、社区、KOL、链上观察或其他第三方。

通过核验后立即建立绑定并轮询；不能通过即自动拒绝并记录原因。没有任何通过核验的账号时，cycle 以 `discovery_failed` 结束，不降级到第三方账号，也不等待人工补录。

## 四、任务 1：是否值得短线追踪

任务 1 的分类是解释和观测标签，不是人工工作流。模型只能返回 `track` 或 `do_not_track`。

只有同时满足以下条件才可 `track`：

1. 对读者的资产安全、交易环境、持仓判断，或高传播的花边、争议、趣味事件有明确价值；
2. 不是已经结束的标准化单点动作；
3. 未来数小时到数天内，官方主体或涉事者本人有合理动机继续回应、调查、处置、辟谣、赔偿、公布结果或升级处理；
4. 下一条官方信息可能明显改变读者对“发生了什么、谁负责、钱怎么办、争议是真是假”的理解。

可追踪的少数类型为：

- `security_asset_incident`：被盗、攻击、假链/假桥、漏洞、资产冻结、交易所/链/协议重大异常、用户资产损失和严重服务事故；
- `official_dispute_or_denial`：高关注度的账号被盗、合作或授权真假、责任归属、重大指控、项目方与用户冲突、名人或机构争议，且等待当事人公开回应；
- `exceptional_project_decision`：影响资产迁移、交易入口、协议存续或项目命运的罕见重大决定，例如重大链迁移或生死存亡级回购/销毁。

普通上线、开放、关闭、解锁、投票、回购、销毁、产品发布、长期法案、价格波动、仓位、爆仓、巨鲸买入、做市商吸筹、一次性转账和仅靠第三方链上追踪才会继续更新的事情，默认 `do_not_track`。

证据不足也输出 `do_not_track`，但系统会在同一真实事件出现新的 HotTopic 证据时重新判断；这不是人工确认队列。

## 五、任务 2：自动加入事件追踪列表

任务 1 输出 `track` 后，系统先把相邻 HotTopic 与既有 `tracking_event` 做事件归并。若命中活跃或近期结束的同一事件，只更新证据和必要的 cycle；否则创建新的 `tracking_event` 和 `discovering` cycle，并运行任务 0。

账号选择遵循以下硬限制：

- 单个 event 最多 3 个官方账号；优先事件主体，其次官方安全/处置主体，最后才是已验证的涉事当事人本人公开账号；
- 全局最多 15 个激活事件账号；容量满时，不挤掉正在追踪的账号，新 event 记录 `capacity_exhausted` 并自动结束；
- 一个 handle 被多个事件使用时只保留一条事件轮询记录，以绑定数服务多个事件；
- 事件账号只存在于事件追踪表，不自动写入人工 X 信源账号、HotTopic 基线账号或其订阅开关。

事件轮询使用现有 FXTwitter 客户端、统一 2 秒 pacer、429 冷却和退避，但事件账号在调度队列中优先。最多 15 个账号时，2 秒 pacing 能在一分钟内完成一轮请求；正常目标是每账号 1 分钟。每次抓取只取新帖并写入 `event_tracking_inbox`。

## 六、任务 3：实质进展、自动发稿与生命周期

### 1. 实质进展判断

每条新官方帖都先用 GPT 与该 event 的已知时间线比较，只能输出：

- `material_progress`：新增可报道事实，明显改变事件理解，例如官方确认/否认、影响范围、资金处置、调查发现、风险控制、服务恢复、冻结追回、赔偿、责任结论、可验证证据或争议升级；
- `relevant_no_progress`：与事件有关但只是重复、安抚、营销、转发、无新增事实或旧结论换说法；
- `irrelevant`：与事件无关。

只有 `material_progress` 可以写入发布时间线、延长 cycle 和进入快讯投递。该判断同时给出 `news_type`（`regular`、`onchain` 或 `funding`）、事实摘录、与上一条的差异和可信度；未确认的说法必须标注为未确认，不得在快讯中写成事实。

### 2. 快讯桥接

`material_progress` 不直接调用发布接口。它先进入 `event_tracking_publication_outbox`，再通过一个窄的发布 Adapter 跨越到主 SQLite：

```text
event_tracking_updates
  -> publication outbox
  -> tasks(source='event_tracking', status='judged')
  -> search -> write -> format_publish -> event_tracking auto publish
```

Adapter 在一个主库事务中写入任务和 `x_task_pipeline` 的专用判断结果，使用官方 `tweet_id` 作为 `source_item_id` 和跨库幂等身份。它预先写入 `news_type`，因此不再运行普通 X 的初始判断器；但必须运行全站搜索者，和 Odaily 历史、运行中 candidate、近期已处理内容查重。查重判定为重复时，outbox 记录 `duplicate`，不会发稿。

`event_tracking` 需要成为主写作链路的显式 source。写作和格式化复用既有模板、格式校验、失败重试和监控；发布阶段为该 source 建立专门自动分支：通过上述实质进展和全站查重后，固定 `isPublish=true`，不调用会返回 `manual_review` 的通用发布者规则。推送使用 `Idempotency-Key: event-tracking:<tweet_id>`，保证 worker 重试、跨库投递重试和服务重启不会重复发布。

发布、写作或推送失败遵循现有自动重试和可见失败记录；绝不改成“等待编辑审核”。失败修复后可按同一幂等键自动续跑。

### 3. 生命周期

- cycle 初始最长观察窗口：72 小时；
- 从最近一条 `material_progress` 起 24 小时没有新的实质官方进展，则自动结束，原因 `silence_24h`；初始事件本身记为起点，因此无任何后续官方更新时也会及时结束；
- 每条 `material_progress` 最多把当前窗口延长 48 小时；
- 从 cycle 开始计算，任何情况下硬上限是 7 天；到期自动结束，避免无限续订；
- 之后若同一真实事件出现新的重大 HotTopic 或官方进展，事件归并器复用原 `tracking_event`，开启新 cycle，而不是恢复旧 cycle 或另建重复账号。

结束时解除该 cycle 的账号绑定。没有其他活跃绑定的事件临时账号停止轮询；账号和所有审计记录保留，以便以后复用和复盘。

## 七、Prompt、模型与控制台

### Prompt

- 任务 1、官方账号发现和实质进展判断各自使用不可变的版本号和完整 Prompt 快照；每次结果存入对应审计记录。
- 控制台只读展示当前 Prompt、版本、生效时间、调用次数和使用该版本的事件；不提供编辑、复制回写或人工确认按钮。
- 未来若由 AI/开发流程修订 Prompt，必须新建版本，不能改写已使用的文本或历史结果。

### 模型

- 任务 1 与实质进展判断：默认 `gpt-5.6-luna`，失败时 `gpt-5.6-terra`，两次均按同一 JSON 契约运行；
- 官方账号发现：仅使用确认支持 Responses `web_search` 的 GPT 路由。禁止以不带真实工具调用的普通模型文本充当成功结果；
- 所有模型调用在 SQLite 短事务外执行，持久化实际模型、Prompt 版本、usage、耗时、重试与失败原因。

### 控制台

`X Agent / 热点自动快讯` 在实现后是只读运营视图，展示：

- 激活和近期结束事件、当前 cycle、追踪理由、类型、剩余时间和自动结束原因；
- 官方账号及其身份/事件证据、最后轮询、最近贡献；
- 官方原帖、进展判断、差异说明、快讯任务、查重或发布结果；
- GPT 搜索工具调用、引用、Prompt 版本、模型 usage、失败与重试。

它不提供账号手工添加、人工确认、暂停、恢复、结束或 Prompt 编辑。运行错误只作为观测和后续修复依据。

## 八、完成情况与上线验收

1. **已完成**：独立 `event_tracking_*` 表、cycle、账号发现审计、事件专用 inbox、绑定和 durable outbox 已落入 HotTopic SQLite；任务 1 和事件归并已有历史样本回归。
2. **已完成**：GPT Responses Web Search 适配器拒绝没有真实 `web_search_call` 或 citations 的响应；官方核验会拒绝第三方、假 handle、身份关系缺失、引用不匹配和无候选结果，并限制为一次初始搜索加一次回退重试。
3. **已完成**：事件账号在共享 FXTwitter pacer 前优先轮询，目标间隔 1 分钟；全局最多 15 个账号、每事件最多 3 个、同账号可绑定多个事件，72 小时初始窗口、24 小时静默退出和 7 天硬上限均由自动维护处理。
4. **已完成**：官方原帖仅进入事件专用 inbox；只有 `material_progress` 才会创建 outbox 和主库 `tasks.source = 'event_tracking'`，不会回灌普通 HotTopic 或普通 X 信源。
5. **已完成**：`event_tracking` 从全站搜索开始，复用查重、写作和格式化，并以官方 `tweet_id` 作为发布幂等键自动直发；SQLite 与 PostgreSQL 领取条件均允许预判为 `judged` 的事件任务进入搜索。
6. **已完成**：控制台只读展示事件、账号证据、帖子、进展、outbox/发布结果、搜索引用和不可变 Prompt 版本；没有账号手工添加、人工确认、暂停、恢复、结束或 Prompt 编辑接口。Bitget/GIWA 调研、普通上币/解锁、巨鲸买入和长期监管议题的边界已固化在 Prompt 与回归测试中。

上线验收必须证明：只会追踪已验证的官方账号；无关官方帖不会进入主链路；实质进展只发一次；事件会在 24 小时静默、72 小时初始窗口或 7 天硬上限下自动停止；任意自动失败都不会产生人工确认状态。
