# X Agent 升级总计划书

## 状态与范围

- 状态：本地实现和 v8 初始化审阅材料已完成，尚未部署到生产服务器。独立账号目录、三个订阅开关、共享采集、市场情绪/项目推介结果、失败重试和控制台页面均已落地。
- 初始筛选：`scripts/x_agent_local_screen.py` 只读取显式传入的相邻 HotTopic 本地账号清单和帖子快照，先用确定性规则粗筛，再用低成本兼容 API 对两个方向合并判断；它不读取或修改 X 快讯信源、主 SQLite 或发布链路。脚本默认 Luna、不思考，失败时使用 Terra、不思考，并按输入指纹复用已有判断。
- 最终本地报告为 `data/exports/x_agent_local_screening_historical_v8_20260926.{json,md}`，覆盖 2,538 个现有账号。它由多个明确指定的本地采集批次组成 30 天 `historical_sample`，不是连续的实时覆盖：329 个账号进入模型判断，实际发出 393 次 HTTP 请求（Luna 329 次、Terra fallback 64 次），15 个双路超时保留待人工审阅。严格证据门槛后，建议打开市场情绪 10 个、项目推介 42 个，其中 2 个同时打开。
- 初始化导入必须显式使用该 v8 报告和 `x-agent-import-screening --apply-suggestions`；2,538 个账号均默认打开热点话题，市场情绪和项目推介仅按该报告的 `include` 建议开启。导入完成后的人工网页改动不会被 worker 或报告自动覆盖。
- X Agent 是控制台中的上层框架，包含四个平级组件：热点话题、热点自动快讯、市场情绪、项目推介。
- 热点自动快讯沿用既有专项任务书；本计划只确认其与热点话题平级，不重新设计其功能。

## 账号与采集边界

X Agent 使用自己的账号目录，与 X 快讯信源、Crypto 信源及其他信源完全独立。可以复用底层 X 抓取、标准化和限流组件，但不复用信源账号属性、发布权限或主写作链路。

每个账号只有三个订阅开关：热点话题、市场情绪、项目推介。新账号默认打开热点话题；本次实施时由系统根据任务书直接给一批已有账号打开市场情绪和项目推介，管理员随后在网页上审阅并手动切换开关。系统不保存账号画像，也不在运行中自动覆盖人工纠错。

一次采集结果供多个组件消费，避免重复抓取。开关更新必须短事务立即保存，采集 worker 延迟批量重载，合并连续点击，不能每次点击启动 AI、重建 worker 或触发全量同步。

## 模型与发布边界

所有需要模型的初筛、内容抽取和汇总默认使用 `gpt-5.6-luna`，不思考；不可用时 fallback 到 `gpt-5.6-terra`，不思考，并记录实际模型与失败原因。去重、窗口聚合和开关保存使用确定性代码。

市场情绪和项目推介只生成内部分析结果，绝不发快讯。热点自动快讯未来可以产生发布候选并进入既有发布设计，但不属于本次两个新模块的发布范围。

## 实现记录

- `HotTopicService` 仍是唯一 X Agent 采集 worker 边界，技术运行库仍为 `data/runtime/hottopic.sqlite`。这不意味着它复用旧热点话题的账号业务：X Agent 不访问主库的 X 信源账号、任务或发布权限。
- `hottopic_inbox` 以 `tweet_id` 去重保存一次原帖；热点话题保留自己的消费标记，市场情绪和项目推介各有唯一 `(tweet_id,module)` 分析任务。
- 市场情绪结果按大盘、Crypto 具体标的、美股具体标的保存五级态度和来源；项目结果按合约地址、官网或原帖隔离身份归并，保存项目和逻辑，不保存推介强度或账号画像。
- 控制台使用 `/console/x-agent/*` 专用管理员接口，账号和结果均服务端分页。单个开关采用本地乐观更新和单字段短请求，批量写入上限 500 个账号，均不等待 AI 或发起全量抓取。
- worker 内的抽取默认 `gpt-5.6-luna`、`reasoning_effort=none`，失败后使用 `gpt-5.6-terra`、`reasoning_effort=none`；模型配置缺失、最终失败和 5 分钟以上的遗留 `processing` 任务均是可见错误。失败任务可在网页或 `x-agent-retry-failed` 有界重排，原帖会保留到成功或明确忽略。

## 分阶段任务

1. 建立 X Agent 独立账号目录、三项订阅开关和一次采集多模块消费契约。
2. 按《市场情绪任务书》完成已有账号初始筛选和开关建议。
3. 按《项目推介任务书》完成已有账号初始筛选和开关建议。
4. 建立两个模块的独立结果、来源查看、失败重试和模型调用审计。
5. 在控制台提供 X Agent 账号总览、批量开关和模块结果页，验证短事务与延迟重载性能。
6. 用历史样本回放评估误纳入、漏纳入、标的识别和项目归并质量，再决定是否调整规则。

## 详细实施顺序

### 阶段一：建立独立账号与采集边界

1. 盘点当前 X Agent 已有账号，形成账号迁移清单；不读取 X 快讯信源的账号开关作为业务依据。
2. 为 X Agent 账号定义唯一 handle、显示名、来源时间、启用状态和最近采集状态。
3. 增加三个独立订阅开关：`hot_topic_enabled`、`market_sentiment_enabled`、`project_promotion_enabled`。
4. 默认打开热点话题；本次初始化脚本根据两个专项任务书直接打开一批市场情绪和项目推介账号。
5. 采集层按账号和时间窗口只抓取一次；分析模块使用同一份原文，不为每个开关重复调用 X 接口。
6. 将 X Agent 原文、分析结果和失败记录存入独立运行边界，不写入 X 快讯的 `tasks -> write_flow -> publish` 链路。

### 阶段二：初始账号批量判断

1. 读取每个已有账号最近约 30 天的代表性内容，优先选择包含明确标的、项目、交易观点或推介理由的帖子。
2. 分别运行市场情绪账号筛选和项目推介账号筛选；两个结果可以同时命中同一账号。
3. 保存初始化报告：账号、拟打开的开关、代表性帖子、判断依据和不确定原因。
4. 将报告结果写入初始配置，随后由管理员在网页逐个审阅和切换。
5. 初始化完成后，自动流程不得覆盖人工切换结果；后续只对新加入且尚未确认的账号提出建议。

### 阶段三：运行时分析

1. 采集 worker 依据账号开关把原文分发给对应分析器。
2. 分析器先做确定性清洗、转发识别、时间过滤和去重，再调用模型提取结构化结果。
3. 单条结果保存原帖、账号、标的/项目、发布时间、模型、fallback 原因和处理状态。
4. 汇总任务按窗口聚合，不为同一帖子反复调用模型；重复执行必须幂等。
5. 网络失败、超时、JSON 不合规和字段缺失进入可见失败队列，不转换成“没有相关内容”。

### 阶段四：控制台与性能验收

1. X Agent 页面提供账号一览、三个开关、最近采集状态和最近失败。
2. 市场情绪页面提供标的一览、情绪快照、窗口筛选和来源展开。
3. 项目推介页面提供项目一览、逻辑摘要、最近提及和来源展开。
4. 开关点击只执行短事务；连续点击合并为最后状态，worker 在配置窗口内批量重载。
5. 页面操作不得等待模型、不得执行全量重算、不得为每个账号单独启动线程。
6. 用历史回放和压力测试验证：重复采集、批量切换、模型失败、多个模块同时启用和大批量来源展示。

## 明确不做

- 不接入 X 快讯信源账号体系，不改变任何现有信源启停、写作名、AI 信源标记或发布权限。
- 市场情绪和项目推介不自动发快讯，也不创建普通快讯任务。
- 不建立账号画像、永久账号分类或模型自动覆盖人工开关的机制。
- 不以精确市值接口作为首版前置条件；先使用中心化交易所可交易性和内容语境近似判断。
- 不在本计划中重写热点自动快讯既有任务书。

## 验收原则

- 新模块不读取或改变任何 X 快讯信源配置。
- 同一帖子最多采集一次，可被多个已打开模块独立消费。
- 任意开关点击不会同步等待模型或触发无限任务。
- 每条结果可回到原始账号、帖子和时间。
- 模型失败不会伪装成无结果；fallback 可见。
- 初始批量勾选可在网页逐账号纠错，纠错后不被自动流程覆盖。
