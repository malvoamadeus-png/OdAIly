# 新版留存与信息流需求基线

## 文档状态

本文记录 2026-11-04 与产品使用者讨论及评审后确认的目标、问题和生产观察，供后续设计与实施续接。信息流继续使用现有查询库和投影机制的方向已在本轮确认；其他实现细节仍需设计。本文件不授权代码、数据或生产变更。

最初讨论阶段没有修改代码或生产数据；随后用户授权本地代码实施，实施范围见文末。生产容量、错误数量是 2026-11-04 的只读快照，后续实施前应重新核实。

## 用户目标

- 产品主要由用户本人低频使用，日常关注当前新闻；根盘中的热业务数据希望最多保留约 3 天。到期数据中无长期价值的删除，有历史、审计或后续查询价值的归档到 `/data`。
- 不需要为日常运行保留多份全库备份。历史业务档案与可恢复备份是两种不同用途；确有必要保存的业务历史应按记录归档，不以重复整库副本替代。
- 存储位置变化不能让控制台或未来外部调用方看到两个互不相干的数据源。调用方应通过稳定接口获得一个逻辑数据集，存储拆分由服务端负责。
- 全量信息流应帮助人理解一条新闻的来源、门槛判断、重复关系以及 API 定义的内部处理结果，包括直发、挂后台和失败等状态；状态判断以本系统 API 为准。外部依赖错误仅当天提供具体原因，跨日只保留汇总次数。
- Odaily 快讯总览需要搜索至少一个月以前的内容，并考虑未来供其他系统交互；不能因为主库只保留三天而失去这类搜索能力。
- 最近一次体验反馈是页面和流程已经明显变快。后续实现不能让这一点回退。

## 当前容量与存储背景

2026-11-04 生产只读核查结果：根盘约 40 GiB，已用约 37 GiB，可用约 0.9 GiB；`/opt/OdAIly/data/database/odaily.sqlite` 主业务库约 11.6 GiB。`/data` 是同一台 Linux 云服务器上另一块已挂载的块设备，约 98 GiB，已用约 24 GiB，可用约 70 GiB；不是另一台服务器，也不是异机备份。

主业务 SQLite 当前承载采集、处理、审核、控制台和其他 worker 的业务事实。任务可以保存来源原文、原始 payload、处理阶段状态和结果。当前没有覆盖所有主业务记录的统一过期策略；已有明确短期周期的包括搜索热缓存和部分采集尝试，不能据此推断整个主库只保留短期数据。

生产已经存在多个不同用途的存储：主业务 SQLite 当前位于根盘；系统信息流、巡检和压缩证据位于 `/data/OdAIly/system-observability`；写作查重使用可重建的 searcher 热缓存。它们不是彼此相同的数据库副本，但当前存储边界不能直接代表用户需要理解或操作多个搜索入口。

### 留存设计约束

- 先定义每类业务记录的热留存、归档留存和删除条件，再实施 3 天策略；不能只按文件修改时间或数据库总大小清理。
- 未结束的任务、队列 job、重试、发布待处理状态和仍被审查/争议保护的记录不能因年龄达到 3 天而丢失恢复依据。恢复所需的业务状态、输入、幂等键和调度信息按业务需要保留；外部依赖的错误明细仍执行仅留当天的规则，不因任务未结束或审计保护而额外长期留存。
- 长期查重、来源追踪和跨系统关联如不需要全文，应优先评估长期保留稳定来源键、链接、标题指纹、发布 ID 等轻量索引；必要正文与完整证据按业务价值归档。
- 归档文件若需要全文搜索，应同时维护可查询索引，并通过同一服务接口搜索；仅把 SQLite 文件放到 `/data` 不会自动让现有接口查到它。
- SQLite 的清理、归档和物理缩库要遵循停写/在线备份/WAL 一致性与临时空间要求。删除历史行不等于数据库文件会立即变小。

### 当前推荐的数据位置方向

优先考虑把唯一的主业务 SQLite 整体迁到同一台服务器的 `/data`，保持原有主库读写方访问同一个权威库。控制台和调用方仍只访问服务接口，不感知文件在哪个挂载点。这能先解除根盘压力，并保持既有跨表查询和一个月以上的 Odaily 快讯搜索；它只是把数据库文件放到另一块本机磁盘，不创建第二份主业务逻辑数据，也不自动实现记录 3 天过期。

全量信息流继续读取现有独立观测查询库，由投影机制关联主业务库、HotTopic、Meme 等业务来源；查询库是面向信息流的读模型。主业务库迁移不改变这条查询路径，也不要求将各业务库合并。旧业务记录归档或删除前，必须确认必要状态和关联已投影，归档后的详情与证据引用仍可解析，并使查询索引和证据同步遵守留存策略。

如后续确需把旧业务行从主库移走，再按业务表设计 `/data` 上的归档及统一查询 API。由 API 在内部检索热数据与归档、合并排序和分页；不能让网页或外部调用方分别连接两个库。当前尚未决定是否需要这层冷热拆分。归档数据库、搜索索引与恢复备份是不同用途，不能互相混称。

## 全量信息流的日常浏览与搜索

### 日常浏览：按最后处理操作时间查看最新情况

全量信息流平时是一个可挂着查看的运行工作台，不要求用户先搜索。默认按最后一次实际处理操作的时间倒序展示新闻/事件，包括通过业务门槛的内容和因重复而停止处理的来源信息。搜索、查重、价值判断、写作等每次实际操作都会刷新同一主体的排序时间，旧信息重新处理后可以回到列表前部。只需维护最后处理操作时间，不为排序额外保存逐次操作历史；页面读取、心跳和投影同步不算业务处理操作。用户偶尔查看时，主要回答：

- 最近系统采集到了什么有价值的信息？来自 X、竞品还是其他渠道？
- 对应信息在本系统 API 中是处理中、重复、直发、挂后台还是失败？当前是否需要人工处理？无需额外核验官网是否实际发布。
- 是否有来源侧证据表明 X 未抓到、竞品内容后来有修改，或后续处理阶段失败？

默认列表以可辨认的新闻标题为主，附来源、采集时间、最后处理操作时间和 API 定义的当前处理/发布状态。完整正文不是列表必需信息；详情再提供原文或必要摘录、来源关联及按留存规则可用的处理时间线。股票行情、运行心跳和低层 worker 事件不能淹没新闻时间线。

因新闻价值不足或金额未达门槛而筛除的原始材料不进入默认新闻列表。因已报道或与既有内容重复而停止处理的来源信息必须展示标题、重复结论及命中对象；此规则不要求价值判断先于查重，先查重即停止的记录也要展示，未执行的价值判断显示为未评估。通过门槛后的阶段失败、挂后台和直发等结果作为同一主体的状态或详情事件，不把每次操作拆成独立新闻卡。

如果 X 内容完全没有被系统采集，也没有其他来源或业务记录提到它，系统没有该条内容的证据，不能在信息流里虚构一条记录或断言“X 未抓到”。可以展示已有的账号轮询/采集健康证据；只有能关联到具体内容或来源观察的记录时，才能说明某条信息未被采集。

### 搜索：回看近期已不在当天的内容

搜索是用户主动使用的另一种场景：某条信息不在当天列表中，但仍处于过去一小段时间内时，用户希望通过标题、关键词、来源或业务把它找回来。这里不是“搜索首页以外的信息”的泛化目标，也不代替按时间浏览最新动态。

精确回看时长尚未确定；详细设计需给出可选时间范围和默认范围，并保证这段时间内的新闻、来源、重复关系、内部处理结果及按留存规则保留的诊断信息可查。结果仍按稳定新闻/事件身份组织，不把采集尝试、审核尝试或每次状态变化拆成多条新闻。点击结果后再看来源材料、重复命中及已有阶段结果；外部错误跨日后不提供逐新闻失败详情、摘要或类别。

具体查询路径：默认时间线调用一个认证后的列表 API，以最后处理操作时间和稳定主体 ID 排序并使用游标分页；搜索框提交标题/关键词并可选来源、业务和时间范围，调用同一服务边界下的搜索 API。列表和搜索继续读取现有观测查询库，由服务端完成业务投影、来源关联和详情读取。主业务库整体迁到 `/data` 不改变信息流读取查询库的边界；若业务数据以后分热区和归档区，由服务端处理归档关联与读取，浏览器仍只面对一个逻辑数据集。

- “X 抓到还是竞品改过”：结果应有渠道、来源账号/站点、原文链接和来源更新时间；修改历史作为同一新闻的来源事件，不另造新闻主体。
- “为什么停止处理或挂后台”：详情展示内部阶段结果，如重复并链接命中对象、某阶段失败、挂后台或直发。当天的内部失败与外部依赖失败采用不同可读分类；外部错误跨日后仅保留日汇总，不再展示逐新闻错误原因或摘要，业务状态仍可查。
- 因新闻价值不足或金额未达门槛而筛除的原始项目不进入默认时间线或普通搜索结果；如确有运营诊断需要，可通过显式诊断入口查看。因重复而停止处理的来源信息仍进入列表和普通搜索结果。

### Odaily 快讯总览

- 需要支持至少一个月以前的搜索。
- 未来外部交互继续通过稳定 API 契约访问，不向外部调用方暴露 SQLite 文件路径、数据库拆分方式或任意 SQL。
- 查询、排序、分页、稳定 ID 和详情关联在热数据与归档数据之间保持一致。
- 是否只需要标题/元数据搜索，还是归档正文也要全文搜索，需在详细设计中确认；不得静默返回不完整结果。

具体查询路径：总览页面继续调用现有专用快讯运营 API，搜索条件和分页交给后端；后端从唯一主业务库查一个月以上的快讯。若未来归档到另一个 SQLite，由同一 API 把两边的结果按同一时间及稳定 ID 合并，外部交互接口也维持单一契约。只把数据库挪到 `/data` 时，仍是原主库上的一次查询，不需要双库扇出或改外部数据契约。

### 搜索者内部查重

流水线查重是独立于控制台历史搜索的功能。当前 searcher 数据是可重建的有界热缓存，包含短期任务、运行中的 candidate 和有期限的已发布参考。调整主库留存时，应单独确认查重窗口、来源 ID 去重账本和归档候选的需要；不能把 searcher 缓存误当作完整历史档案，也不能因主库清理而悄悄缩短已承诺的查重窗口。

## 全量信息流展示边界

### 顶层列表应展示

默认显示通过业务准入门槛、对编辑/运营有判断价值的新闻或事件，以及因重复而停止处理的来源信息。重复项不以已完成价值判断为展示前提；通过门槛后的失败、挂后台和直发结果也要可见。

- X 内容未通过初始质量/新闻价值判断，例如废话：默认不进入新闻列表。
- X、竞品及其他来源内容被判为重复：展示原始新闻标题，并说明命中的既有内容；先查重即停止的记录同样展示，未执行的价值判断显示为未评估。
- X 内容通过门槛但处理失败：展示新闻标题、当前业务状态和按留存规则可用的失败信息；本机问题保留可行动诊断，外部依赖仅当天展示具体错误，跨日不保留逐新闻错误摘要或类别。
- 已写完并挂后台的内容：展示新闻标题和 API 定义的挂后台状态。
- API 标记为直发或其他发布结果的内容：展示新闻标题及对应内部状态，不增加官网发布核验。
- Hyperliquid 等监控源未过金额/重要性门槛的动作：默认不展示；过门槛后形成待写稿件的动作，展示新闻/事件标题和后续处理进度。

### 详情时间线应展示

按各自留存规则保留的采集、去重、判断、写作、发布、发布后审查等技术事件可作为详情中的时间线和诊断证据，但不能各自成为顶层新闻卡片。不要求为刷新排序新增逐次操作历史；外部依赖错误的详情、摘要和逐新闻类别跨日清理，详情不据此承诺完整历史追因。底层数字 ID 可以作为详情中的辅助定位信息，不能替代主标题。

### 当前明确不符合预期的例子

- `x_capture 18848059 已直发X快讯`：只展示内部编号和采集/投递动作，看不出稿件是什么；顶层应展示稿件新闻标题，采集 ID 放到详情。
- `民主党已获得参议院51席，达到多数席位门槛` 配 `fact_audit 发布后审查 processing`：发布后事实审查是已有新闻的后续事件，不应单独冒充一条新新闻；应关联回原稿详情。
- `2117816400630947922` 配 `x_agent_analysis 内部研究处理中`：内部研究任务 ID 不是新闻标题；没有形成通过门槛的新闻/事件前，不进入新闻列表。

### 列表组织

- 默认按最后处理操作时间倒序，同一时间以稳定主体 ID 排序；新闻原始发生时间和采集时间作为辅助信息。搜索、查重、价值判断、写作、重试等实际处理操作均刷新排序时间，即使状态未变也算一次刷新。
- 股票行情、运行健康和底层处理诊断可以有独立视图或显式筛选，不混成默认新闻列表。
- 同一新闻下的状态变化归并在同一主体；按留存规则已有的来源更新、重复命中和失败证据按时间排列在详情中。

## 错误与健康信息的分类要求

“错误”需要区分产品预期结果、上游服务故障和本机系统故障，并展示可理解的原因；不得把无候选、过期筛选、采集空结果统称为系统宕机。

2026-11-04 生产只读核查快照：

- 最近 24 小时有 744 组故障/恢复聚合，受影响对象计数合计 1,548；这是按组累计的对象数，不是 1,548 个独立故障。约 660 个影响计数来自内容超过 freshness gate 后被筛除，属于过期内容处理，不等同系统故障。
- 巡检记录中有模型/embedding API 返回 `Access denied`、HTTP 503、403、500、429 和请求超时。累计影响对象数会跨错误组重复，不能直接当成唯一失败任务数；403 / Access denied 还需区分账号权限、额度、接口配置与供应商策略。
- 约 18 小时内，各 worker 日志中有 961 条 `database is locked`；多项日志明确记录采集轮次、审核轮次或心跳写入失败。它们由程序捕获后以 INFO 级别记录，不能因日志级别是 INFO 就算作成功。最近一次 API 重启之后仍观察到 41 条。这是本机 SQLite 并发写入争用信号，需要与上游 API 故障分开处理。
- 同一约 18 小时窗口的 X 抓取尝试约 69,000 次成功；约 1,900 次 404 分布在 57 个账号；约 1,560 次 `no target-author posts` 集中在 3 个账号；有少量 `database is locked`。这不等于整条 X 抓取服务全面失联；空结果当前被记为非成功，存在展示分类噪声。

### 错误日志留存偏好

- 自身问题需要作为工程问题持续记录和处理。当前明确登记：生产多个 worker 并发访问主 SQLite 时出现 `database is locked`，约 18 小时有 961 条相关日志，近期 API 重启后仍有 41 条。根因尚未确认；后续应追查持锁来源、导致失败的轮次和影响，并修正架构/事务使用问题。问题未解决前保留足够的本机诊断证据；解决后保留根因、修复和验证摘要，不无限积累重复原始日志。
- 外部依赖的逐次技术错误，例如 FxTwitter/X 搜索失败、来源正文获取失败、写作模型 API 超时或上游 5xx，具体错误仅保留发生当天，按北京时间自然日划分。跨日后清理逐次明细及其在业务记录、查询投影、证据和索引中的副本，只保留按日期、错误类别、上游/阶段统计的发生次数；不另存逐新闻错误摘要、精简日志或失败类别。
- 外部错误长期统计只用于了解“哪类错误出现几次”，不提供跨日的单条新闻错误追因。文章本身的内部业务状态（如未完成、失败、挂后台、直发）仍按业务需要保留，但不借业务状态留存恢复已清理的外部错误详情。任务恢复所需输入、幂等键和调度信息继续按业务需要保留。
- 预期筛除、空结果、重复不是故障日志。空结果应计为正常结果或单独业务统计，不计入系统错误；过期门槛筛除也不计为服务故障。

健康界面应分别展示预期筛除/空结果、重复、上游超时或 5xx、鉴权/权限/额度错误、本地 SQLite 写锁/磁盘错误、程序输出验证失败、最终内部处理/发布状态。当天供应商错误可展示具体原因，历史供应商错误只展示每日分类次数；对于本机问题给出受影响服务/阶段和失败次数。聚合数需明确时间窗口和计数口径，已有唯一对象数与尝试次数分开展示，避免将尝试数误读成独立故障数；不为跨日外部错误统计额外保留对象清单或关联。

## 验收条件

- 根盘主业务热数据满足约 3 天留存目标；过期处理不破坏未结束任务、查重、发布状态、来源关联或审计保护。
- `/data` 中需要长期保留的归档可由授权 API 搜索和打开；调用方只面对一个逻辑数据集和稳定 ID，不需要知道双库实现。
- 若先将唯一主业务 SQLite 整体迁到 `/data`，控制台与外部服务接口维持单一入口，Odaily 快讯总览的一月以上搜索无需双库合并。
- Odaily 快讯总览可搜索至少一个月以前的内容，分页和详情跨热数据/归档连续且无静默漏项。
- 全量信息流继续通过现有观测查询库和投影机制聚合各业务来源；主库迁移不改变查询边界，源记录归档或清理前已完成必要投影，保留的详情及证据引用可解析。
- 全量信息流打开后无需先搜索，默认按最后处理操作时间倒序浏览新闻和内部处理状态；搜索、查重、价值判断、写作、重试等操作会刷新同一主体，不新增新闻卡，也不要求额外记录操作历史。用户主动搜索用于回看尚在设定留存期内、但已不在当天列表中的信息。
- 全量信息流的近期回看时长在详细设计中明确，并在该窗口内能按标题/关键词、来源或业务检索，不把搜索描述成“找首页之外的信息”。
- 全量信息流默认列表展示通过业务门槛的新闻/事件及因重复停止处理的来源信息；先查重即停止、尚未价值判断的重复项同样展示。因新闻价值不足或金额未达门槛而筛除的项目不出现。
- 按各自留存规则保留的采集、审查、内部研究等事件只作为相应新闻的详情时间线，不作为顶层新闻条目；列表主标题不使用数据库 ID。
- 搜索和列表结果能够辨认来源渠道、来源更新时间、门槛结果或未评估、重复目标及 API 定义的内部处理/发布状态；不增加官网实际发布核验。失败详情遵守外部错误仅留当天的边界，跨日不承诺逐新闻外部失败追因。
- 上游 API 错误、本地 SQLite 写入争用、正常筛除和模型输出校验失败有不同分类；当天已有的错误条数和唯一受影响对象数分别呈现，跨日外部错误只保留分类次数。
- 本地可修问题（当前包括 SQLite 写锁争用）保留可行动诊断，形成根因/修复/验证记录；外部依赖具体错误只保留北京时间当天，跨日只保留每日错误类别、上游/阶段和次数汇总，不保留逐新闻错误摘要、精简日志或类别，也不在投影或证据中保留副本。
- 页面加载速度不回退；股票行情等高频数据不挤占新闻信息流的默认视图。

## 尚待设计确认

- 采取“整份主库迁到 `/data`，维持单库”还是“根盘三天热库 + `/data` 归档库”。前者搜索改动少但不控制数据库增长；后者符合热/冷留存目标但要求统一查询路由和归档索引。
- 各业务表具体保留期限、哪些正文/原文需要归档，以及审计、争议和发布后检查对记录的保护期限。
- 全量信息流的统一新闻/事件主体如何关联现有 task、来源文章、重复目标、发布记录和后置审查。
- 历史归档需要支持全文搜索到什么范围；归档中的来源、标题、时间、URL 和内部处理结论至少要可检索。外部依赖错误跨日后仅支持每日分类次数查询，不纳入逐新闻归档检索。
- `database is locked` 的持锁来源和失败影响需单独排查；本文件记录它是本机问题信号，不认定单一根因或具体修复方案。
- 旧备份/迁移快照是否按用户“不保留全库备份”的偏好清理；这与业务历史归档策略分开决定。
