# SQLite 并发治理候选方案与官方依据

日期：2026-11-18。状态：研究候选，未实施、未修改运行契约。

范围：本地代码 `0556fbf`、仓库既有研究与 SQLite、Python、PostgreSQL 官方资料，以及 `/tmp` 隔离临时数据库复现。本记录没有连接生产，也没有查询本地产品数据库。生产现场与此次完整调查结论由主调查记录补充；代码风险不能单独证明某次生产延迟的原因。

## 判断

OdAIly 需要先把数据库写入视为一种有预算、可归属、可排队的资源。当前已经按部分业务分库，但同一个文件内仍有多个业务、维护任务和控制台路径竞争写事务。增加抓取线程、数据库连接或等待时间，均不会增加单个 SQLite 文件的同时写入数。[S1][S2]

建议分两层推进：先统一短事务规则、测量口径与维护预算；再用真实峰值负载比较“每库单一写入所有者”和“热业务迁至本机 PostgreSQL”。不应在缺少事务服务时间与峰值写入量时直接认定 SQLite 已达到容量极限，也不应无限期用补索引与延长超时处理持续增长的需求。

## 已离线确证：无变化分支泄漏写事务，并能跨联网调用边界

主调查指出 `EventTracker.observe_topics` 的无变化分支可能留下隐式事务。本轮使用既有测试的 `_tracker`、`_seed_topic` 和 `FakeAI`，在 `/tmp` 临时库调用真实实现，不修改产品代码，不发模型或外部网络请求。[C7]

执行命令：`PYTHONPATH=backend .venv/bin/python /tmp/odaily_sqlite_observe_repro.py`。脚本只在 `/tmp` 保存，临时 SQLite 通过 `TemporaryDirectory` 自动清理。连续两次执行均复现；第二次输出如下：

```text
first observe_topics: assessed=1, tracked=1, in_transaction=false
second connection after first: writable=true, 0.26ms
second unchanged observe_topics: assessed=0, tracked=0, in_transaction=true
second connection after unchanged: SQLITE_BUSY, database is locked, 25.43ms
explicit commit of leaked transaction: second connection writable=true, 0.04ms
repeat unchanged, enter FakeAI.web_search_json: in_transaction=true
second connection during fake web-search: SQLITE_BUSY, 25.52ms
discovery method later commits: in_transaction=false
```

根因链已经验证：

1. `observe_topics` 最初的 `with self.db` 已结束。
2. 当既有判断与 snapshot hash 相同时，1167 行调用 `_save_topic_observation_result`。
3. 该 helper 在 1249 行执行 UPDATE，Python 隐式开启写事务；调用方未在这一分支使用事务上下文。
4. 全部热点都无变化时，1181 行提前返回，事务没有 commit/rollback。
5. 之后同一连接直到其他路径提交或回滚前，一直持有写事务。在真实 `discover_official_accounts` 路径进入 `ai.web_search_json` 的边界，复现仍能看到持锁；本次网络函数被 fake 替代，第二连接同步探测失败。

这是**实际代码路径的事务生命周期缺陷**，不只是“查询可能慢”。隔离复现未计量生产发生率、全部持锁时长或总延迟贡献；生产调用链之间若有其他提交，也会提前释放，因此不能据此声称每次联网都带锁。

它要求新增比“不要把网络调用写进 with”更强的约束：非事务所有者的 helper 不得隐式遗留 DML 事务；顶层操作在入口无事务时，所有正常返回、提前返回和异常退出也应恢复无事务状态；外部 HTTP/AI、sleep 和主循环等待前必须断言无活动写事务。此规则要先确定事务所有权，不能在所有 helper 末尾盲目 commit，以免拆坏调用者需要的原子事务。验收应覆盖无变化、空队列、跳过、失败与连续调用，并用第二连接验证写入可用，不能只检查首轮业务结果。

## 一手资料确认的机制

| 机制 | 官方依据 | 对项目的含义 |
| --- | --- | --- |
| WAL 允许读写并行，同库仍只有一个写者 | [S1] Concurrency | 单库内改为不同表、不同进程或不同连接，不能隔离写锁。 |
| `BEGIN IMMEDIATE` 开始时就尝试取得写事务 | [S2] | 在后续查询、排序、反序列化或 Python 循环期间也可能独占写入；只能用于已经准备好、范围有界的原子操作。 |
| 已过时的 WAL 读快照升级写事务可能返回 `SQLITE_BUSY_SNAPSHOT` | [S3] | 要结束旧事务、重读并重做条件判断；只重试失败的 UPDATE 无法使旧快照变新。 |
| busy handler 可能因死锁风险不被调用；timeout 是连接级忙处理器 | [S4][S5] | 不能把 30/60 秒理解为每次都等待这么久，更不能视为 FIFO 排队或公平性保证。官方接口没有提供业务优先级。 |
| 长读可能阻止 checkpoint 完成或 WAL 重置 | [S1] | 只读连接也要限制快照存活时间、及时消费或关闭游标。WAL 大小本身不能证明长读、更不能证明它正持有写锁。 |
| 默认自动 checkpoint 在 WAL 达到 1000 页后触发 | [S1] | 部分提交可能承担 checkpoint 的 I/O；应分开记录锁等待、事务持有、提交和 checkpoint。配置可覆盖默认值。 |
| 原生 Python 连接上下文不会在入口自动开启事务，出口也不会关闭连接 | [S6] | `with db:` 不等于可见的完整事务边界。必须结合运行 Python 版本、autocommit/isolation_level、第一条 DML 和连接子类判断。 |
| WAL 中跨多个 ATTACH 文件的事务，不保证整组跨库原子性 | [S1] | 分库后不能用 ATTACH 替代可靠跨库交付协议。 |
| PostgreSQL 具有行级锁；`SKIP LOCKED` 可用于多消费者队列 | [S7][S8] | 多个独立记录可以并发修改；同一行、约束、DDL、死锁与磁盘仍可能成为瓶颈。`SKIP LOCKED` 不能用于要求完整一致视图的一般查询。 |

`synchronous=FULL` 在本项目公共连接和投资线索连接中明确启用。WAL 文档说明 FULL 下每次事务提交同步 WAL；NORMAL 的耐久性不同。[S1] 因而不能把改成 NORMAL 当作无代价的性能修复，尤其不能让已对外发布的业务结果在故障后失去对应去重账本。

## 当前代码提供的具体证据

1. **短事务改造已有可借鉴实现。** 文本审查者 `claim_task` 先用只读连接筛候选与计算正文 hash，再在短写事务内重新检查来源快照和租约，最后原子领取。[C1] 这说明“事务外准备、事务内复核”可以保留正确性，但候选读本身仍需要查询计划和规模预算。
2. **Writer3 仍先取写事务再筛选。** `claim_task` 在 `BEGIN IMMEDIATE` 后关联参考稿、执行 `julianday` 条件与排序，最后才 UPSERT 领取。[C2] `LIMIT 1` 仅约束返回数，不保证扫描和排序只处理一条。需真实规模的 `EXPLAIN QUERY PLAN` 和耗时样本再判断索引及时间字段改造。
3. **HotTopic 账号清理仍在写事务内找候选。** `_discard_transient_account_material_batch` 先 `BEGIN IMMEDIATE`，再用 `lower(activity_account)` 和多表 `NOT EXISTS` 检查永久保护，然后删除多个关联表。[C3] 批量上限有价值，但未限制候选筛选成本。保护条件必须保留，并在最终短事务内重新验证。
4. **投资线索每小时维护无单批行数预算。** `_maintain` 把两组状态更新、带 `NOT EXISTS` 的事件/材料删除以及维护时间更新放在一个 `with self.db:` 中。[C4] 第一条 UPDATE 触发写事务后，后续清理共享同一持锁周期；数据增长会放大最坏耗时。适合拆成可恢复的小批次，但不能提前记“维护全部完成”。
5. **现有观测不足以还原完整持锁时间。** `ClosingSQLiteConnection._monitored_call` 在 execute 返回后检测 `in_transaction` 的变化并开始计时；首条 DML 在 execute 内的执行成本不计入随后 long_transaction 时长。慢语句还混合了等待锁与执行时间；原生连接及游标迭代等路径覆盖也不同。[C5] 因此“没有 long_transaction 日志”不足以排除长持锁。
6. **等待契约不统一。** 公共 `connect_sqlite` 把传入 timeout 又覆盖为固定 `busy_timeout=30000`；投资线索为 60000；其他连接自己初始化。[C5][C4] 需要整理连接角色和总截止时间，不能只改一处参数就认为统一了失败处理。
7. **进程内串行与数据库串行是两层资源。** HotTopic `_serialized` 使用 `self.lock` 保护长连接调用。[C3] 它不能协调其他进程对同文件的写入；分析等待时也须测量该 Python 锁，避免把进程内排队误记为 SQLite 等待。

11 月 11 日研究已列出多个库的争锁、慢查询与 I/O 放大风险，并明确现场快照不足以确定宕机唯一原因。[H1][H2] 本轮新需求应把零散修复提升为全库事务清单、统一治理规则和并发验收。

## 候选方案及边界

### A. 保留多进程直写，统一短事务和维护预算

适用于持锁尾部主要由少量扫描、清理与批处理放大的情况，也是其他方案的共同前置工作。

- 在写事务外完成候选扫描、模型/网络调用、hash、JSON 构建；事务内只作主键级复核、有限条件更新和必要关联写入。
- 每个写入操作声明最大记录数、最大工作时间、幂等键、租约或版本校验、失败后的回滚和重试单位。
- 清理按主键游标和小批次恢复。候选可过期，事务内要重新验证保护条件；被保护记录不能因一次扫过就永久漏掉。
- 对慢候选查询先检查查询计划、索引、表达式筛选、触发器和级联删除，不能靠 `LIMIT` 推断成本。
- 后台维护仅在预算内尝试取得写锁；竞争时延期，避免重复争抢。实时任务仍需要合理的截止时间和背压。

局限：SQLite 的内核争锁没有业务优先级接口；事务都很短但数量很大时，仍可能发生某一类写者长期排队。A 能减少无效占用，不能提供可控公平性或多写者容量。

### B. 每个热点库只允许一个写入所有者

所有写请求进入一个负责该文件的写入进程或 owner；抓取、模型推理、只读查询仍可并发。队列才能明确实现实时结果优先、按账号或业务公平、低优先级清理限额、队列长度上限与等待告警。

收益来自可观测且可控制的排队，并可合并允许合并的心跳或进度刷新。它没有提高 SQLite 的底层同时写入数，不应把所有原先的长事务原样放入队列，否则只是把不可见等待移到了队列内。

必须满足的契约：

- owner 对事务提交成功后才确认请求；请求有稳定幂等键，调用方断线重试不会重复发布、重复计费或重复领取。
- 内存队列不是持久队列。owner 或生产者崩溃时，请求必须能由原来源重放、生产者持久 outbox 或明确持久命令日志恢复；不能口头承诺“不丢”。
- 所有写路径都纳入所有权，包括控制台、迁移、投影触发器安装、清理、人工导入和维护；保留旁路直写就仍会争锁。
- 优先级必须配最低服务份额或老化机制，避免维护永不执行、磁盘最终填满；实时任务之间也要公平。
- owner 故障需要重启与排他启动机制；就绪状态应与服务 active 分开，队列恢复要验证。
- 队列入库若也要等待同一个争锁文件，不能据此声称解决了入口阻塞。选 RPC、来源 outbox 或其他持久化方式时，应测量该路径的新增成本与故障恢复。

适合先在 HotTopic 域隔离验证，不宜立即强制全部业务走一个全系统 owner。当前多个文件本可并行写，统一成全局单写者会丢失这种隔离。

### C. 按写入所有权和时效要求继续分库

当前架构已经把部分业务和观测查询库拆开。进一步分库应围绕稳定所有权，例如“X 采集材料/账号目录”和“投资线索分析结果”，而不是每张表一个库。

需要回答：账号取消监控何时生效、永久来源证据如何保护、材料版本如何传递、分析提交前如何复核资格、跨库失败重试、删除传播和积压上限。可采用来源库事务 outbox + 消费者幂等 inbox/水位，由变更版本控制重复和乱序。最终一致性窗口必须可见，不可假装跨库原子。

收益是不同文件能各自写入；风险是数据复制、协议复杂度和对账成本增加。多个库在同一磁盘上仍共享 I/O，分库不能消除磁盘拥堵。若拆出的库仍有多业务直写，原问题也会在新库重现。

### D. 把高并发状态库迁至本机 PostgreSQL

这是新架构候选，不是启用旧 Supabase、旧连接字符串或现有环境开关。当前 ADR 和加载器只允许 SQLite，采用本机 PostgreSQL 需新 ADR、仓储实现、迁移及切换演练。[C6]

适用于短事务化之后，独立行更新仍持续受单写者容量限制，或写入公平、跨表事务、查询并发与运维诊断需求使 owner/outbox 体系复杂度超过使用服务器数据库的成本。队列领取可评估 `FOR UPDATE SKIP LOCKED`，但需保持稳定排序、租约、重试和幂等；跳过锁定行本身不保证每个任务公平处理。[S7][S8]

PostgreSQL 仍需短事务、连接数量预算、事务/语句/锁超时、死锁重试、vacuum、磁盘与备份监控。[S7][S9] 同机 PostgreSQL 不会消除同机故障与共享磁盘问题；索引、全表清理或事务内网络调用也不会自动变快。迁移应优先一个有明确边界的热业务域，禁止为了迁移而无期限双写。

## 选型前应交付的测量和验收

### 观测要求

每库、服务、业务操作至少记录：到达时间、尝试取锁、取得写事务、提交/回滚结束、行数、重试次数、SQLite 扩展错误码和调用点。无法可靠测出首条隐式 DML 的取锁时刻时，应明确标为“等待和执行混合耗时”，不能作为精确持锁值。明确 Python 锁、应用队列、SQLite 等待、SQL 执行、提交与外部请求各自的耗时。

同时采集：待处理量、最老任务年龄、账号到期至开始采集的延迟、来源发布至采集发现的时间、发现至分析完成的时间，以及磁盘 I/O 延迟和 WAL 增长。不同来源的发布时刻可能天然很早，不能把全部内容年龄算成内部数据库延迟。

用“单位时间内实际持锁秒数之和”估计写入占用，但不能把多个等待者的等待时间也相加作为占用。可写入容量由峰值到达率、事务服务时间和尾部共同决定；不存在适用于所有机器的固定 QPS 门槛。

### 隔离验收场景

1. 按生产表规模、关键索引、触发器和结果分布构造脱敏或合成库，模拟多进程抓取回写、分析领取/完成、控制台操作、投影和保留清理同时发生；禁止在生产压测。
2. 比较基线、A、B、必要时 D 的同一负载：实时操作的 p95/p99、最老任务年龄、峰值后恢复速度、持续吞吐、错误与维护完成率。验收预算是业务目标，需基于当前基线提出，不能把本记录任意数字当作承诺。
3. 人为制造慢查询、磁盘变慢、长读、维护堆积、某账号大量数据；确认实时业务不会因维护失去服务份额，维护也能最终完成。
4. 在领取前后、提交前后、确认前后和对外副作用之后杀进程，验证租约恢复、幂等处理与不重复发布；跨库方案额外验证重复/乱序/漏交付与删除保护。
5. 如果 A 在目标峰值已有足够余量，先采用 A 并设容量告警；若等待尾部与不公平仍明显但总服务量可满足，优先比较 B；若短事务总服务量已持续逼近可用时间或跨域事务需求明显，进入 D 的正式验证。C 仅在业务边界清晰且交付协议可维护时采用。

## 附：版本核查

SQLite 官方 WAL 页目前说明 WAL-reset race 在 3.51.3 及以后修复，并有 3.44.6、3.50.7 回补；条件涉及多连接同时写或 checkpoint。[S1] 后续运维应核查生产 Python 实际链接的 `sqlite3.sqlite_version` 与发行版安全回补情况。这里没有检查生产版本，也没有证据表明本项目发生该 race；它是版本清单核查事项，不能作为锁延迟的解释。
