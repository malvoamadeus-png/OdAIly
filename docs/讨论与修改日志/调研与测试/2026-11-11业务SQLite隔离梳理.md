# 业务 SQLite 隔离梳理

## 范围

本次梳理以减少无关业务争抢同一数据库写锁为目标，检查实际数据和事务依赖，而不以代码包数量决定数据库数量。用户明确暂不处理 Hyperliquid 的历史成交压缩；本次不迁移、修改、清理或压缩 Hyperliquid 数据。2026-11-11 21:47 的生产只读核对显示金十和两个旧巨鲸服务已停、禁用自启；独立 Hyperliquid 新闻监测仍运行。下述路径是当前默认或生产实测路径，实际生效值仍应按环境配置核实。

## 商务快讯的本地隔离实现

`ODAILY_BUSINESS_NEWS_SQLITE_PATH` 是可选开关；未配置时 API 和 worker 均保持使用主库。配置后必须指向由迁移器完成并验证过的新库，否则启动失败，防止静默创建空收件箱。隔离库保存群配置、消息、最近消息、游标及事务 outbox，迁移前后消息 ID 不变，信息流沿用既有业务身份。事件触发器在新库发布前安装，避免 worker 比投影器先启动时遗漏短暂状态。

迁移工具要求两端停写；对正在处理/格式化/发布的消息、未投影的商务事件、未知字段和已有目标文件拒绝执行。工具按一致快照复制数据和自增序列，检查外键、完整性和 WAL checkpoint，不删除源库。若新库接收数据后需要回退，不能直接切回旧库，否则新数据会遗漏或重复投递。完整运行步骤见 `商务快讯追踪文档.md`。

生产在 21:47 只读核对到商务表字段与实现一致，商务消息无处理中的状态，来源 outbox 相对当时观测水位没有未投影的商务事件。该结果仅为当时快照，正式切换前必须重新检查；本次没有停商务 worker、迁移生产数据、切换环境或部署。商务消息数量不大，拆分主要减少相互等待及故障波及，不能保证解决其他业务的长事务或服务器 I/O 瓶颈。

本地隔离测试覆盖游标、消息与群配置一致、在主库写锁期间独立库可写、处理中新消息拒绝迁移、未投影事件拒绝迁移、未知字段或触发器拒绝迁移、自增序列保留、迁移前后信息流身份及先启动 worker 的状态事件。更广的相关测试 107 项通过；既有商务测试已按当前业务规则修正预期，验证无文字媒体消息不展示且接收游标仍前进，业务逻辑未改变。

## 后续顺序

1. 正式切换前，审核运维步骤，重新测量数据库与锁等待、验证备份和恢复，确认服务停写窗口及待处理消息；按文档复制、对账，再让 API 与 worker 同时使用新路径。代码部署和生产切换尚未执行。
2. 对主库剩余高写入业务量化各自的写入频率、写锁持续时间和等待时间；优先优化长事务。审查者、采集器和主流程若继续拆分，必须逐条验证原有任务、稿件版本、去重、审查保护与发布恢复。
3. 对用户后续提出的 Hyperliquid 方向，保留“明细可汇总、长期画像可增量更新”的设计空间。以后需先定义胜率按什么构成一次完整交易，以及跨时间窗口的开平仓、费用和已实现盈亏如何计算；仅按小时求和不一定足以重建这些指标。历史数据的压缩和删除另行处理，本次不实施。

## 22:09 后补充检查

- 生产在 22:02–22:04 仍记录事实审查、文本审查和竞品处理的 `database is locked`；不能据此判断同一写锁的持有者。
- 生产只读 `EXPLAIN QUERY PLAN` 显示，文本审查和 Writer3 的已发布稿件候选查询均扫描 `odaily_reference_items` 并使用临时排序；尽管存在 `idx_odaily_reference_published`，这些 `julianday(published_at)` 查询计划未使用该索引。计划不包含实际耗时，也不能单独证明它们造成事故；需要在安全环境以数据量、耗时及写锁时长验证，并保留历史时区兼容。文本审查的本地改动已将该读取移出写事务，但尚未部署。
- `backend/packages/common/sqlite_backup.py` 使用 `destination.read_bytes()` 计算哈希，会在内存中一次性构造整份数据库文件的字节对象；主库文件约 11 GiB，服务器总内存约 7.3 GiB。执行该备份路径可能造成严重内存压力，备份工具应改为分块计算并验证备份恢复。本项是代码风险，未确认事故期间执行过备份，不能据此归因宕机。
- 当前商务迁移方案不需要主动停掉所有 worker，但迁移器在复制与校验期间会持有主库写锁；即使只停商务 worker 和 API，其他依赖主库写入的业务也可能等待。生产规模下的持锁时间、上游消息积压恢复及影响范围尚未测量，不能承诺无影响或指定停机时间。
