# SQLite 抢锁系统调查与改进需求

日期：2026-11-18。状态：研究与候选需求，未实施。

## 结论

建议把下一轮工作立为一次“数据库并发治理”，按业务时效验收。继续逐处加索引、延长 timeout 或增加线程，不能保证解决反复出现的延迟。

本轮发现了两个比“SQLite 文件大”更具体的问题：

1. **真实代码存在隐式写事务泄漏。** 热点追踪对未变化话题复查后，函数返回仍持有写事务；随后可将写锁带入账号发现的外部调用边界。已在临时库复现，另一连接写入报 `SQLITE_BUSY`，显式提交后恢复。
2. **增量采集触发全量写刷新。** 热点聚合每批都会在写事务内遍历全部 seed/active 话题并逐条更新，即使本批只有一条新帖。生产当前有 4,346 个 seed、24 个 active；工作量随存量增长，而不只随新消息增长。

另有投资线索每小时全表清理、采集结果同步逐账号回写、后台维护和实时任务争用同一写入资源等问题。它们共同构成延迟的放大链，不能用一个锁超时参数解决。

推荐顺序：先修事务生命周期与全量工作，建立可恢复的采集回写和维护预算；再用同一套峰值负载验证 SQLite 是否有足够余量。余量足够但排队不公平时，比较每库集中写入；容量不足或跨库协议成本过高时，正式评估热业务迁至本机 PostgreSQL。各项都应有完成条件，避免长期逐处修补。

## 既有修复为什么没有完成治理

历史调查已经推进过商务库、MSX 采集状态隔离，审查/主任务领取优化，时间表达式索引，热点清理分批，以及短证据独立 SQLite 和普通成功过程材料一天留存。

本轮查阅的对话确认：此前七天保留规则已由用户改为一天。11 月 11 日笔记保留了当时历史口径，不能把其中“尚未部署”“一周保留”等描述当成今天状态。

11 月 16 日 `bf72490` 等修复确实缩短了部分清理事务；最新代码 `prune_transient_state` 已把候选读取移到写锁外，并按批处理。因此本轮不能再声称该函数仍把全部候选扫描放在显式写事务里。

但尚存四个缺口：

1. 事务边界靠调用者约定，缺少退出和外部调用边界的不变量检查，隐式事务可逃逸。
2. 聚合、维护和普通状态刷新缺少统一的计算/扫描预算，少量新增仍可能触发大量存量工作。
3. 多进程直写同文件，没有业务优先级和公平性保证；分了其他业务库，也没有隔离 X Agent 内部的写入。
4. 验收偏向服务 active、API 200、锁异常是否出现；缺少账号实际准时率、成功写入尾延迟和峰值后恢复速度。

历史方案和上线过程见 [业务 SQLite 隔离梳理](2026-11-11业务SQLite隔离梳理.md)、[既有锁争用自查](2026-11-11磁盘增长与SQLite锁争用自查.md)，最新状态还需结合对话、代码及生产验证理解。

## 确证问题一：未变化分支把写事务带出函数

路径：`event_tracking.py:1167` 的 snapshot 未变化分支调用 `_save_topic_observation_result`；后者在 `1249` 执行 UPDATE。外层此前的 `with self.db` 已结束。如果所有快照都没有新判断需求，函数在 `1181` 提前返回，不会提交这一轮 UPDATE 隐式开启的事务。

隔离实验调用真实 `observe_topics`、真实 discovery 路径，使用既有 `_tracker`、`_seed_topic`、FakeAI：

```text
第一次观察：assessed=1，in_transaction=false；另一连接可写。
第二次未变化复查：assessed=0，in_transaction=true。
另一连接写入：25ms 后 SQLITE_BUSY。
显式 commit：另一连接约 0.04ms 写入成功。
再次未变化复查，随后进入模拟 web_search 边界：仍 in_transaction=true。
该边界的另一连接写入：仍 SQLITE_BUSY。
discovery 后续自身事务提交后：in_transaction=false。
```

实际运行命令：`PYTHONPATH=backend .venv/bin/python /tmp/odaily_sqlite_observe_repro.py`。主调查再次运行得到相同结果。临时库自动销毁；完整机制和官方依据在 [候选方案资料](2026-11-18-SQLite并发治理候选方案与官方依据.md)。文末保存最小复现，避免依赖 `/tmp` 脚本长期存在。

生产 431 条从该 UPDATE 位置开始的长事务与此风险相符，但本轮没有在生产安装追踪器，不能精确计算其中多少跨过了实际模型调用、贡献了多少延迟。

**后续需求：** 明确顶层操作的事务所有权；入口没有事务的顶层操作，所有正常返回、提前返回和异常退出都不得遗留写事务。HTTP、AI、sleep 和主循环等待之前必须无遗留写事务。不能简单在每个 helper 后加 commit，因为部分 helper 需要参与调用者的原子事务。

## 确证问题二：一条新帖触发全量话题刷新

`topic_aggregator.py:1080` 取得写事务后，在 `1290` 调用 `_refresh_all_topics`。

`3008` 起的实现读取所有 seed/active 话题；对每个话题读取参与者、执行 `_assess_topic` 的关联查询与 Python 处理，然后执行 UPDATE。即使话题内容没变，也会走更新。

离线调用真实 `process_batch`，给 1 条新帖，模拟提取器返回 0 条 claim；只改变数据库已有 seed 数量，通过 SQLite trace 统计工作量：

| 既有 seed | 新帖 | SELECT 数 | UPDATE 数 | 处于事务内的 SELECT 数 |
| ---: | ---: | ---: | ---: | ---: |
| 10 | 1 | 29 | 10 | 25 |
| 100 | 1 | 209 | 100 | 205 |
| 1,000 | 1 | 2,009 | 1,000 | 2,005 |

这证明范围随存量增长。合成库热缓存的批次总耗时约 5.5/6.7/24.0ms，不能用来承诺生产加速倍数；生产包含真实 claim、证据、关联、缓存和磁盘成本。

**后续需求：** 将“本批受影响话题重算”与“按时间到期的话题生命周期刷新”分开。后者按到期索引和游标有界推进；保留 1h/6h/24h 参与窗口、seed 到期、永久话题保护、合并身份及稿件可见性的一致语义。简单只刷新 dirty 话题会遗漏没有新帖但窗口已过期的话题，不可直接这样替换。

## 其他需要纳入同一轮的路径

### 投资线索维护：删除前也可能长时间持锁

`investment_leads/service.py:1142` 每小时在一个事务内更新过期任务、删除事件、删除材料并更新维护水位。

生产 `_maintain:1171` 的材料 DELETE 每轮约 14–21 秒；只读 `EXPLAIN QUERY PLAN` 明确为 `SCAN investment_lead_materials`，关联来源查询使用已有索引。材料表当前只有主键与 `posted_at` 索引，没有匹配 `last_observed_at` 的筛选索引。即使没有可删记录，扫描仍有成本，不能把“删除了零条”理解成“没占写资源”。

候选设计：索引与有界候选读取结合；事务内按主键重新检查时间、来源保护、活动状态和版本，再有限删除；每个子步骤独立水位和“尚有工作”标识。外键级联和触发器的实际成本也要计入。不能提前更新全部维护完成时间。

### 采集回写：数据库等待会阻止消费已完成请求

`hottopic/service.py:1185–1206` 在采集协调循环里同步调用 `_store_poll`。网络线程有 128 个并不代表存在 128 个可并发持久化者；一个结果等待写入时，该协调路径无法及时消费其他已完成结果。

`_store_poll` 同一账号事务同时涉及账号状态、投资材料和其他分析 job；共享库里的聚合、追踪、分析完成、心跳、维护又会竞争它。异常会冒泡至 `collect_loop`，退出当前批次后再重试；已完成请求结果未进入独立的持久交接队列。高发帖账号在重抓前超出 API 返回窗口时存在丢失材料风险，本轮未证明已经发生。

候选设计：采集与提交分离，有界缓冲、可恢复交接、稳定批次/来源 ID，提交成功前不得推进成功游标；数据库 busy 应重试相同结果而非默认重新请求整批账号。内存队列只解决短期调度，不能承担崩溃不丢的承诺。若持久队列也写入同一被锁文件，入口阻塞仍可能存在。

### 主库和 Hyperliquid：保留独立治理，不扩大热点库的归因

- 主库 `pipeline_timing.py:291` 耗时看板读取多次 68–73 秒，按时间表达式筛选，生产计划使用来源前缀查找并建立临时排序。建议验证完整查询计划、时间字段/表达式索引、增量读模型及大 metadata 读取成本。WAL 下慢 SELECT 不自动等于独占写锁，但会使用 I/O、内存并可能延长读快照。
- `newsflash_metadata.py:287` 写投递元数据后，在同一事务中按标题查稿件并匹配身份。生产该类事务最长约 11 秒，应把候选匹配移到事务外并在提交时复核，防止影响刚发布后的状态落库和恢复。
- Writer3 仍有先 BEGIN IMMEDIATE 后筛候选的结构，但本轮日志未证明它是当前首要瓶颈，优先级低于确证热点。
- Hyperliquid 独立库 `save_global` 有约 15 秒事务，新命名进程 BEGIN 有约 14 秒慢样本。可审查全局 payload 和批量候选写入；本轮不要求压缩历史交易或改变统计口径。
- 观测库已独立，但源 outbox 的触发器和清理仍发生在源业务库；独立观测库并不等于观测路径完全不会影响业务。当前 2 秒忙时让出的方向应保留。

| 优先级 | 需求 | 必须交付的结果 |
| --- | --- | --- |
| P0 | 事务所有权和出口不变量 | 修复已复现路径；空队列、无变化、跳过、异常及连续调用测试；第二连接证明返回/外部调用时可写；禁止 helper 盲目 commit |
| P0 | 聚合增量化与按时到期刷新 | 新帖成本与受影响集合相关；时间窗口仍正确；大存量下无整库话题逐条更新的单次写事务 |
| P0 | 投资线索维护预算 | 有索引的候选读取、行数与时间双预算、事务内复核、可恢复水位、竞争时让出；保护已发布与关联证据 |
| P1 | 采集结果可恢复交接 | fetched/persisted 分开计时；提交前不记成功；busy/进程崩溃后可重放同份结果；有界队列和背压 |
| P1 | 统一测量和失败契约 | 各库、操作、角色的等待期限，扩展错误码及总重试截止时间明确；不会因重试使请求永久卡住 |

| P2 | 集中写入 / 分库 / 本机 PostgreSQL 对照 | 同负载比较吞吐、尾延迟、维护完成率、恢复正确性和实现运维成本，做一次正式选型 |

## 三条架构路线如何选择

| 路线 | 实际收益 | 主要成本与前提 | 本轮判断 |
| --- | --- | --- | --- |
| 继续 SQLite，短事务和有界工作 | 直接消除已经证明的无效占用；变更相对集中 | 所有写入口都要遵守规则；仍不能同时写同文件 | 必须先做，是其他方案的共同前置工作 |
| 每个热点库集中写入 | 应用能控制优先级、公平性、合并普通刷新和队列上限 | 需要可靠交接、提交后确认、幂等、owner 排他和恢复；所有旁路写入要收口 | 在热点域试验；不能把全系统多个库集中成一个全局写者 |
| 按业务边界进一步分库 | 采集、热点、投资结果可各自写，降低互相影响 | 账号资格、材料版本、来源保护、outbox/inbox、删除与回滚协议复杂 | 只拆边界清晰的域，不能按表机械拆分 |
| 热状态域迁本机 PostgreSQL | 独立行可并发修改，队列及跨表事务能力更完整 | 新 ADR、仓储与迁移、连接/超时预算、备份恢复、持续运维 | 应成为正式对照方案；不等于启用旧 Supabase，也不能修复所有应用问题 |

是否采用集中写入和是否分库是两个不同维度，可以组合，不必一次绑定。SQLite 的单写者容量没有统一 QPS 门槛；关键是实际持锁服务时间、峰值到达量和尾延迟。

**建议设一个明确决策点：** P0 完成并获得同负载结果后，如果 SQLite 在目标峰值仍不能满足时效，进入 PostgreSQL 热域试点；如果总容量足够而排队公平性差，进入每库集中写入试点。不要再以“这次没报锁错”延后选型。

## 验收应围绕交易信息时效

以下是建议起点，尚未成为已承诺 SLA；实施时先对照完整分布和业务优先级确认。

1. **硬正确性：** 顶层操作、外部调用和主循环等待前，无逃逸写事务；并发领取、过期租约、重复消息、来源取消和版本变更不造成重复发布或错误归属。
2. **数据库时效：** 常规实时写入的持锁目标 p99 < 100ms、最大值 < 500ms；数据库等待 p99 < 1 秒。超过预算的任务拆分或明确登记例外，不能把慢操作统一豁免。首条 DML、提交和 checkpoint 都需覆盖，不能只测 with 块中间。
3. **采集时效：** 对未处于来源失败退避的账号，以当前成功后 600 秒到期规则为基线，建议到期至开始采集 p95 < 60 秒、p99 < 120 秒；到期至持久化完成 p99 < 180 秒。账号首次失败和退避仍另行可见，不能通过排除失败账号美化整体覆盖。
4. **持续负载：** 在与生产相近数据规模、索引、关联分布及触发器的合成库中，同时运行采集提交、分析、控制台、投影和维护；覆盖当前峰值以及一个明确增长场景，建议先取 2 倍峰值。连续正常运行与周期性维护都满足预算，峰值结束后最老任务年龄能下降。
5. **恢复：** 在结果抓取后、持久化前、事务提交后确认前、外部发布后杀进程，验证不漏交接、不重复发布、租约最终可恢复。数据库 busy 的重试不重复耗用外部服务。
6. **维护与空间：** 清理积压能最终排空，普通成功过程证据继续按已确认的一天规则；故障、待处理、重要稿件/审核/来源证据不随之删除。实时达标不能以停止维护、持续吃满磁盘为代价。

不能仅从 752 条慢日志计算这些 p99：目前没有低于门槛的全部样本与分母。

## 测量方案：避免把所有等待都叫“锁”

至少区分：采集任务到期 → 实际开始请求 → 请求完成 → 进入提交队列 → 进程内锁获取 → 数据库写事务获取 → 提交完成 → 分析领取 → 分析完成。

数据库指标按规范化文件路径、服务、操作名和事务 ID 关联，不能只用 basename 作为永久身份。记录事务入口原状态、写锁等待、取得事务到提交、commit 耗时、修改行数、重试次数和错误码；数据写到 stderr/独立观测路径，避免为了记录锁等待又去抢同一把锁。

当前公共监控有三个限制：

- 首条 DML 返回后才开始记录事务年龄，遗漏该语句执行期间已经持锁的部分。
- `state_commit` 在 BEGIN 前开始计时、commit 前取值，包含获取写事务的等待，不含最终提交，不可直接称为写锁时长。
- 原生连接、游标迭代、进程异常退出等覆盖不完整；没有日志不代表没有占用。

同时测 Python RLock 和采集协调循环排队。数据库心跳本身会等写锁，因此“业务循环活着”“数据库可提交”“数据按时推进”应分开显示。

容量评估可用 `峰值每秒写入事务数 × 平均实际持锁秒数` 作为粗略占用估计，并关注服务时间长尾；不要把多个等待者的等待时间相加当成写锁占用。2,548 个账号每 600 秒至少约 4.25 个账号结果/秒，是量级参考；每账号多次写、其他模块写和重试仍要另计。0.10 秒请求节流给出约 255 秒的理想发起下界，也不等于全轮完成保证。

## 不建议作为根治手段的动作

- 增加抓取线程、数据库连接、busy_timeout 或无限重试：可能减少可见异常，也可能增加等待、内存与恢复成本，不增加同文件并发写入能力。
- 仅把库放到另一目录/磁盘：可能改善空间与 I/O，不改变该文件单写者机制。
- 仅把热点表拆成几个文件：没有交接和所有权协议，可能丢失原子性并把问题复制到新库。
- 把长事务整体搬进一个写入队列：只是将等待位置移动，队头阻塞仍在。
- 直接改 `synchronous=NORMAL`、生产 VACUUM 或强制 checkpoint：涉及耐久性、维护 I/O 和空间，本轮无证据支持把这些当作锁问题的即时解法。

## 对此前 IRDM 样例的证据修正

既有调查确认原帖北京时间 03:00:45、目录账号 09:37:11 入库、随后约 38 秒完成分析，说明模型队列不是这条样例的主要等待位置。

但这份材料是转发，转发发生时间不可用。原帖时间到首次采集相差 6 小时 36 分钟，**不能全部解释为内部排队或锁等待**；该帖何时出现在目录账号可采集时间线，仍缺直接证据。锁日志、到期延迟和采集提交时间需要单独测量。本轮不沿用“这六个多小时均由数据库锁造成”的强归因。

## 最小复现存档

在仓库根目录执行下面的隔离实验。只使用既有测试夹具、临时目录和模拟模型，不启动产品服务。它仅确证“未变化分支退出后持锁”，跨模拟 web-search 边界的扩展结果见上文。

```bash
PYTHONPATH=backend .venv/bin/python - <<'PY'
import sqlite3
from pathlib import Path
from tempfile import TemporaryDirectory
from test_event_tracking import _tracker, _seed_topic

with TemporaryDirectory(prefix='odaily-lock-repro-') as directory:
    path = Path(directory)
    tracker, db, clock, _ = _tracker(path)
    probe = sqlite3.connect(path / 'hottopic.sqlite', timeout=0.025)
    try:
        _seed_topic(db, clock)
        tracker.observe_topics(['topic:giwa'])
        assert not db.in_transaction
        tracker.observe_topics(['topic:giwa'])
        assert db.in_transaction
        try:
            probe.execute('BEGIN IMMEDIATE')
        except sqlite3.OperationalError as error:
            assert error.sqlite_errorname == 'SQLITE_BUSY'
            print('REPRODUCED: unchanged observation returned with a write lock')
        else:
            raise AssertionError('Expected the current implementation to retain its write lock')
        db.commit()
        probe.execute('BEGIN IMMEDIATE')
        probe.rollback()
        print('CONTROL: explicit commit restored another writer')
    finally:
        probe.close()
        db.rollback()
        tracker.close()
        db.close()
PY
```
