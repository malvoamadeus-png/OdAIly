# GPT 联网搜索与 Bitget 官方 X 账号验证

## 调研时间

2026-09-27

## 结论摘要

1. **GPT 具备联网搜索能力，但能力不等于默认开启。**
   - OpenAI API 的 Responses API 提供托管的 `web_search` 工具。请求需要把工具放入 `tools`，返回中会包含搜索调用和 URL 引用。
   - ChatGPT 产品是否能搜索，取决于当前产品界面、账号和可用功能；只有在会话中实际启用 Search/搜索能力时，回答才应被当作实时检索结果。普通模型回答不能默认视为联网搜索。
   - 项目使用的 OpenAI-compatible 中转或 LiteLLM 不一定透传 Responses API 的 `web_search`。必须检查实际请求是否产生 web search call 和 citations，不能只看模型返回了一个像搜索结果的文本。

2. **GPT 可以回答“应该关注哪个官方 X 账号”，但应把它当作候选发现和自动核验的输入，不应把纯文本回答直接当作账号启用指令。**
   - 对 Bitget 热钱包异常转账事件，首选核验目标是 Bitget 的机构主账号：[@Bitget](https://x.com/Bitget)。
   - [@GracyBitget](https://x.com/GracyBitget) 只能作为涉事者本人公开账号的候选；只有官网/认证资料和事件关系同时通过自动核验时才可补充，不能替代机构官方主账号。
   - 模型必须同时返回账号主页、支持该判断的事件帖子或官网链接、账号身份依据和检索时间。只返回 `@Bitget` 字符串不算通过。

3. **本项目网关上的实时 GPT Web Search 已完成一次成功实测，但还不能据此跳过账号核验。**
   - GIWA 案例请求返回 HTTP 200，原始响应包含 6 个 `web_search_call`、10 个 URL 引用，且返回了可分层使用的 X 账号。
   - 这证明当前配置的 OpenAI-compatible 路由能够透传 `web_search`；但仍需把账号身份、事件关系和引用来源保存并做确定性核验。
   - 本次请求的搜索上下文很大，输入 token 明显高于手写 Prompt；正式任务需要限制搜索轮次、输出字段和搜索上下文，避免每个热点发现都产生高额 token 消耗。

## Bitget 案例

项目现有测试样本包含本次事件的两条事实：部分热钱包发生异常转账，初步涉及约 3.516 亿美元；Bitget 风险保护基金超过 4.64 亿美元，并由约 5500 枚 BTC 构成、分布在三个钱包。测试样本中的 X 帖文 ID 解码时间为 `2026-09-25 01:07:39 UTC`，符合本次“最近两天”案例的时间范围。

可追溯的样本链接：

- [EmberCN 事件帖 2103290298638159941](https://x.com/EmberCN/status/2103290298638159941)
- [EmberCN 事件帖 2103290298638159942](https://x.com/EmberCN/status/2103290298638159942)
- [Bitget 官方机构账号候选](https://x.com/Bitget)

这里要区分“最早报道或整理事件的账号”和“应当持续关注的官方账号”。`@EmberCN` 是事件信息来源样本，不是 Bitget 官方账号；如果目标是获取交易所后续公告、赔付、调查或资产追回进展，机构主账号应优先于二手转述账号。

## GIWA 实测结果

实测事件：GIWA“主网”被确认是假链，相关假桥被指转走超过 766 ETH。

请求使用 `gpt-5.6-luna` 和 Responses API `web_search`，返回 HTTP 200，状态为 `completed`。模型给出的关注顺序如下：

1. `@GIWA_by_Upbit`：GIWA 官方项目账号，优先关注官方事实边界、RPC、桥和合约说明；
2. `@Official_Upbit`：Upbit 官方母品牌账号，观察是否升级为品牌、用户资产或合规回应；
3. `@DYORSWAPDEX`：仅在能证明其为涉事项目方的官方账号时，才可关注调查、受害者登记和赔偿安排；
4. `@lookonchain`：链上资金追踪账号，不是官方账号，自动规则拒绝；
5. `@OdailyChina`、`@chaincatcher_`：媒体交叉验证账号，自动规则拒绝；
6. `@GIWACat`：生态社区账号，自动规则拒绝。

模型还明确指出：`766 ETH` 这一精确数字没有被本次找到的可靠一手来源独立确认，不能直接当作最终损失规模。这说明它不仅能找账号，也能对账号类型和证据强度做初步分层，但这仍是候选发现结果，不是自动启用授权。

### Token usage

本次单次请求 usage：

- 输入：`56,177` tokens；其中 cached input 为 `7,808` tokens；
- 输出：`3,820` tokens；其中 reasoning tokens 为 `1,254`；
- 总计：`59,997` tokens；
- 搜索调用：`6` 次；
- 引用：`10` 个 URL citation。

当前项目使用的是 OpenAI-compatible 中转和模型别名，未取得该中转的价格表，因此这里只报告 token，不能据此伪造美元成本。若只看“用户手写 Prompt 的长度”会严重低估成本；搜索返回内容和模型推理上下文占据了绝大部分输入量。

## OpenAI 官方能力

来源：[OpenAI Developers - Web search](https://developers.openai.com/api/docs/guides/tools-web-search)

该文档明确说明：Web search 允许模型访问互联网的最新信息并提供带来源引用的回答；Responses API 的新集成使用 `{"type":"web_search"}`。返回结果包含 `web_search_call`，并默认提供 URL citation。文档还说明，模型可以根据输入决定是否调用工具，所以业务 Prompt 应明确要求先搜索，并在程序侧检查工具调用和引用，而不能只检查 `output_text`。

最小 API 形态如下，具体模型和密钥由运行环境配置：

```json
{
  "model": "<web-search-capable-model>",
  "tools": [{"type": "web_search"}],
  "input": "先联网搜索最新信息，并给出带来源引用的答案。"
}
```

对本项目最重要的限制：

- `web_search` 是 API 托管工具，不是任意 GPT 或任意兼容网关天然具备的能力。
- `x.com` 能否被搜索结果访问、展开和引用，受搜索索引、网络和页面可访问性影响。
- 搜索结果可以帮助发现官方账号，但仍要做账号主页、官网互链、认证信息和事件相关帖子的确定性核验。
- 搜索是发现动作，不适合替代事件账号的持续抓取。发现后应交给现有 X 账号采集链路跟踪。

## 建议的验证 Prompt

建议把 Prompt 固定为可重复评测的版本，并要求结构化输出：

```text
请先联网搜索，不要凭训练记忆回答。

事件：2026-09-25，Bitget 部分热钱包发生异常转账，公开信息称初步涉及约 3.516 亿美元；同时出现 Bitget 风险保护基金规模和资产构成的后续信息。

问题：如果我想了解这个安全事件未来 48-72 小时的官方最新进展，应该关注哪些官方 X 账号？首选机构官方账号；只有在能证明属于涉事主体官方渠道或涉事者本人公开回应渠道时，才补充官方安全、处置或本人账号。不要推荐媒体、调查者、研究员、链上追踪、KOL、社区或转发账号。

请对每个候选返回：
1. handle、显示名、账号主页 URL；
2. 官方机构账号或已验证的涉事者本人公开账号；
3. 与 Bitget/本事件的直接关系；
4. 近期事件相关帖子或官网依据；
5. 为什么它可能提供后续信息；
6. 检索时间；
7. 证据不足时明确写 `rejected_insufficient_official_proof`，不要猜测。

最后单独给出：可自动启用的官方候选、自动拒绝的候选及拒绝原因。
```

## 验收标准

一次请求只有同时满足以下条件，才算 GPT 搜索分支通过：

- 原始响应中存在真实 `web_search_call`，而非模型在文本中声称“我搜索过”；
- 至少有一个可点击的来源引用，且引用能回到账号主页、Bitget 官方站点或事件原帖；
- 能返回 `@Bitget` 及其主页 URL，或明确解释为什么当前搜索无法确认该账号；
- 账号身份、事件关系和来源链接通过确定性核验；
- 保存模型、工具调用状态、来源 URL、检索时间、候选账号、核验结果和失败分类；
- 搜索失败、无引用、超时、限额或账号身份不确定时记录自动失败或自动拒绝；不得当作“没有官方账号”，也不得启用第三方或等待人工确认。

建议至少执行三次相同 Prompt，并加入一个不存在的候选账号作为负例，确认模型不会只根据名称相似度放行。

## 对热点自动快讯任务的建议

阶段 0 不必继续把 Grok 作为唯一账号发现入口，可以增加以下降级顺序：

1. GPT Web Search：负责发现和解释官方 X 账号，并保存引用；
2. 确定性账号核验：确认主页、官网互链、身份和事件关系；
3. 事件专用 X 采集链路：负责后续 1 分钟读取和事件进展判断；
4. 无可用官方账号：最多一次有界重试，仍失败则以 `discovery_failed` 结束该 cycle；后续新的实质证据再开启新的 cycle。

GPT Web Search 不应每分钟重复搜索，也不应把完整搜索结果直接送入普通快讯发布链路。它只负责一次性发现官方候选；账号启用后，后续内容仍由事件专用 X 采集和实质进展判断模块处理。
