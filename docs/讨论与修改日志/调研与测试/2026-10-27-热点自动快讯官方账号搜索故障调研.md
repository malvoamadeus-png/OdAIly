# 热点自动快讯官方账号搜索故障调研

调研日期：2026-10-27

## 结论

生产 GPT Responses 路由当前具备 Web Search 能力。使用生产服务当前配置的 `gpt-6-luna` 路由进行对照请求时：不带 `include` 的请求返回已完成的 `web_search_call`，但没有来源列表或 URL citation annotation；同一路由补上 `include: ["web_search_call.action.sources"]` 后，返回已完成搜索、12 条搜索来源和 1 条 `url_citation` annotation。LiteLLM 代理当前能够接收该参数并保留来源和 annotation。

热点自动快讯连续失败的直接原因是发现请求没有显式要求返回搜索来源，代码随后又把模型回答中的 URL 当作无效证据，只接受 Responses 引用/来源字段。多数失败样本中模型实际生成了候选账号和证据 URL，但 Responses 没有返回可供程序核验的来源字段，于是这些候选被拒绝；最近一次失败的模型则返回空账号列表，同样因没有来源字段失败。这不是本地解析字段改名，也没有证据表明搜索能力已经消失；问题是程序依赖不稳定的默认引用输出，没有请求稳定的完整来源列表。

最近一次成功发现账号为北京时间 10 月 24 日 13:04。10 月 25 日至 27 日共 9 次发现全部失败：10 月 25 日 3 次、10 月 26 日 5 次、10 月 27 日 1 次。事件追踪系统会将发现失败的 cycle 结束，不会自动重开，因此这些事件不会因路由恢复而自行开始轮询。

## 生产证据

本次生产核查通过 `odaily-official`、Linux 用户 `root`、目录 `/opt/OdAIly` 完成。SQLite 使用只读 URI 打开；未修改数据库、服务配置或服务状态。

### 故障影响范围

`odaily-hottopic.service` 在核查时为 active，`NRestarts=0`，最近启动时间是 10 月 24 日 16:35（北京时间）。HotTopic 每日完成的话题判断数为 10 月 24 日 212、10 月 25 日 139、10 月 26 日 333、10 月 27 日截至核查时 33；共享 inbox 同期分别新增 11,858、12,975、1,222 条帖子。失败期间仍创建 8 个事件（10 月 25 日 2 个、26 日 5 个、27 日 1 个），但都没有成功绑定账号。

因此问题没有让 HotTopic 采集或“是否追踪”判断整体停止；它卡在追踪事件创建后的官方账号发现边界。已知影响是这些事件未进入官方账号一分钟轮询，故后续官方帖不能被收集和分类为实质进展，也不会由这条链路自动生成快讯。

### 生产路由对照请求

使用相同生产 endpoint、API 凭据、`gpt-6-luna` 和 Web Search 工具执行两个只读请求，没有写入业务 SQLite：

| 请求 | HTTP / 搜索状态 | Sources | Citation annotation |
| --- | --- | ---: | ---: |
| 未提供 `include`，要求 JSON 结果 | HTTP 200；2 个 `web_search_call` 均为 `completed` | 0（action 有 query，但 `sources` 为空） | 0 |
| 提供 `include: ["web_search_call.action.sources"]` | HTTP 200；1 个 `web_search_call` 为 `completed` | 12 条，均来自 `platform.openai.com` | 1 条 `url_citation` |

这组对照与历史失败形状相同，说明当前生产路由能执行搜索并返回来源；响应源字段在请求 `include` 后可正常获得。LiteLLM 日志对应请求均为 `/v1/responses` HTTP 200。两次请求的用量分别为 14,382 和 12,983 tokens；响应没有费用字段。后续诊断不应重复发大输入模型请求，除非验证修复或不同路由确有必要。

## 故障发生时的代码与配置路径

- [event_tracking.py](../../../backend/packages/hottopic/event_tracking.py) 的 `OpenAIEventTrackingAI._request()` 构造 Responses 请求时只传 `model`、`input` 与 `tools: [{"type":"web_search"}]`，没有 `include`。
- 同文件 `_response_citations()` 只从 Responses 的 URL citation annotation、`web_search_result` 或 `web_search_call` 的 `sources` 中提取 URL；普通 JSON 文本里的 `official_evidence_urls` 被有意排除，这是正确的证据边界。
- 故障发生时，`_discover_cycle()` 要求 `tool_calls` 与 `citations` 同时非空，然后才调用当时的官方账号身份过滤器匹配候选证据 URL。失败时 cycle 和 event 被结束为 `discovery_failed`。
- 当前服务单元设置 `HOTTOPIC_MODEL=gpt-6-luna` 和 `HOTTOPIC_FALLBACK_MODEL=gpt-6-luna`。事件追踪器把它们作为 Web Search 主模型与重试模型的默认值；发现循环通过 `dict.fromkeys` 去重相同模型名。因此本次 9 条失败均只有 `attempts=1`，不会对相同模型发第二次请求。
- 生产 LiteLLM 为 `1.97.0`，映射 `gpt-6-luna` 到 `openai/gpt-6-luna`，上游连接信息来自服务器环境变量。`odaily-litellm.service` 自 10 月 23 日 19:59（北京时间）运行，`NRestarts=0`。配置仓库提交 `aca6c1b` 于 10 月 23 日 19:56 将 GPT 路由由 `gpt-5.6-luna` 切到 `gpt-6-luna`；之后 10 月 24 日仍有一次成功发现，故模型切换与故障开始时间接近，但不能据此断定切换单独造成故障。更准确的解释是，切换可能改变模型生成 JSON 引用 annotation 的行为，暴露了请求端未显式取回 sources 的脆弱点。

## API 契约与归因

OpenAI 官方 [Web Search 指南](https://developers.openai.com/api/docs/guides/tools-web-search)区分：

- `message.content[].annotations` 中的 `url_citation` 是模型回答引用的 URL，默认可能出现，但并非每个回答都必须引用来源。
- 完整检索来源列表位于 `web_search_call.action.sources`。要返回完整列表，请求必须加入 `include: ["web_search_call.action.sources"]`；它可能比最终回答引用的 URL 更多。

因此，过去代码仅检查默认 annotation，不足以保证 JSON 答案总会携带可核验 URL。无 `include` 时，空 `action.sources` 是预期的，单看它不能断言未搜索。失败样本没有 annotation，说明回答没有暴露被引用 URL；不表示工具不可用。带 `include` 的生产对照已经直接证实来源可由当前路由取回。

LiteLLM 官方 [Responses API 文档](https://docs.litellm.ai/docs/response_api)说明 `/v1/responses` 可走原生 passthrough，也可桥接到 Chat Completions；路由 URL 本身不足以证明底层采用哪一种模式。此处无需推测底层实现来判断当前能力，因为带 `include` 的生产请求已穿过实际 LiteLLM 服务并收到完整 sources 与 annotation。若以后更换路由或升级 LiteLLM，应继续用带 `include` 的实际响应做验收。

## 产品调整与实现

用户明确了实际需求：账号搜索只要找到候选 handle 就加入追踪，不需要官方身份或证据核验；相关快讯在发布前由人工审核。代码已按此目标调整：

1. 账号候选发现 Prompt 改为输出 handle、可选显示名和理由；程序只校验 handle 格式、去重并纳入追踪。引用、profile URL、官方关系和账号类别不再作为准入条件，Responses 工具调用和 citations 仍只作审计。
2. 事件帖子进展判断和写作规则明确账号身份与帖子主张未经核验，写稿按账号归属，不把候选账号标成官方主体。
3. `event_tracking` 发布分支改走通用 `ready_review` 人工审核路径，使用 `isPublish=false` 挂后台，编辑审核后再决定发布。
4. 对最近 72 小时内由旧身份核验 Prompt 失败的事件，在新版本首次启动时最多自动重新搜索一次；更早或已经忽略的事件不自动重开。
