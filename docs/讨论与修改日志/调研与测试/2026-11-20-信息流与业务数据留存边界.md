## 重要实现差异与风险

1. 六小时清理不是当前运行条件的全部：巡检样本、pin、问题卡、近期子项和事件可保护主体，部分停止记录至少保留 24 小时。物理证据按独立引用和保护机制处理。见 `backend/packages/system_observability/postgres_store.py:1032` 和 `控制台-全量信息流.md:37`、`:90`、`:98`。现有巡检抽样保留 14 天 pin、轻决定索引 30 天；是否继续保留这些是用户所提新业务规则的设计决定。
2. PostgreSQL `maintenance-cleanup` 实际不等同 SQLite 实现。工厂在 PostgreSQL 模式选 `PostgresMaintenanceRepository`（`backend/packages/maintenance/sqlite_repository.py:48-54`）。其默认 dry-run，但显式执行后 `backend/packages/maintenance/repository.py:55-66,177-213` 会按默认七天条件清空多种流水线输出及审核字段；SQLite 对应字段为零操作（`sqlite_repository.py:24-30`）。`完整程序架构.md:313` 声称通用维护不再清空这些字段，与 PostgreSQL 实现不一致；必须修正契约和实现或单独逐项核对，不能直接运行。
3. `system_information` 内容寻址证据可能被业务字段、观测事件、pin、审查或升级使用。删文件不能仅根据文件年龄或某个信息流主体消失而进行；先验证跨 schema 引用、并发读写和未完成任务，再做有界回收。
4. 故障应区分正常业务结束和系统故障。`same_event_no_new_facts` 是业务查重结果，不自动代表故障；外部依赖短暂失败和连续失败也不同。可讨论的设计是按来源、阶段、错误类别聚合最近窗口的次数、首次/最近发生时间、连续次数和有限摘要，恢复后保留短期，用它识别持续故障，而不是保留每轮检查详情；具体阈值与保留期需用户确定、结合现有告警去重与故障恢复状态设计。

- 竞品首发与事件究竟需要永久保存完整正文，还是保留标题、URL、来源、时间、事件映射和所需摘录；当前用户要求内容和链接，不应先删除正文。

## 用户最新确认：五天复盘和审核拒绝案例

- 判断、查重、写作、发布等过程详情保留至任务结束后 5 天；未结束任务继续保留。保留业务运行、来源和去重所需的数据。
- 文本审核者的人工拒绝也进入 AI 文本自我升级队列，由第三方 AI 判断审核者与写作者的争议；既有 AI 稿案例继续支持。应将审核稿、审核意见、人工拒绝和判断所需证据作为独立快照保存至用户明确要求删除，避免普通审核记录清理后丢失。仅适用于文本审核者及自我升级模块，不能扩散到其他流程。
- 非 AI 稿件被审核者指出问题、人工没有处理的普通记录，可以按期限自动清理。
- 用户明确撤销前一轮关于新增通用“待处理/已处理”生命周期的建议；不要引入这套状态，也不要按解决与否自动删除自我升级证据。现有 PostgreSQL 独立 `ai_text_self_upgrade_items` 可作为副本基础，但需要核实功能缺口。

## 清空信息流历史、从新时刻开始：初步边界

2026-11-20 用户提出是否可不留旧信息流历史，简化一次性清理；这是方案讨论，不代表已批准直接删除线上数据。用户确认过去业务过程复盘需保留 5 天，AI 文本升级证据保留至人工要求删除。

- 生产只读核查 PostgreSQL 正在运行，`system_observability` 约 11 GB，`main` 约 1333 MB。信息流的主体、事件、来源身份及证据索引是 PostgreSQL 表，不是可单独删掉的 SQLite 文件；gzip 证据目录单独在文件系统上。
- `system_observability` schema 同时保存 `ai_text_self_upgrade_*`、`system_review_*`、small_evidence、信息流及共享证据索引，不能整 schema 清空；生产案例表包含文本审核 19、事实审核 71 条（该时刻计数）。外键跨 schema 查询为空不能证明不存在应用层引用；`main.x_processing_attempts/events.response_ref` 可引用共享证据。PG 清理 `_evidence_references` 未检查这些主库引用，不能作为全局无引用证明。
- 普通重启不会自动回填已投影历史：`PostgresSourceStateProjector.run_once` 只处理 `projected_at IS NULL` 的源 outbox。清空主体会级联事件和身份映射，但不会自动删除证据，也不会重建已确认的近六小时记录。生产快照存在 19 条待投影和约 103755 条已投影 outbox；数量实时变动，不能用此快照做删除名单。未确认的旧事件仍可重新投影，不能直接用最大 event_id 作并发安全时间栅栏。
- 同时需要处理主流程：锁定任务结束后 5 天复盘所需字段、能访问的入口及旧清理规则；保留业务运行、去重、活动审核与副作用幂等。信息流现有 API 强制六小时，保留源记录并不自动形成五天复盘页面。
- 可研究从明确切换点起重新投影，使用小而可验证的表/引用范围与并发屏障，分开处理文件和业务历史，再修改长期写入与清理逻辑；实际删除范围、对未来新增记录的写入策略、持续故障汇总、文件回收、必要服务窗口与磁盘回收方式仍须验证。不做备份是用户已表达的偏好；不应先执行删除再补设计。

## 清空并从现在重建的真实边界（本地代码核查）

**不允许把整个 `system_observability` schema 当成可丢弃的查询副本。** 它除了 `system_information_*` 外，还包含 `ai_text_self_upgrade_*`（长期升级案例及人工决定）、`system_review_*`（问题卡、分析、人工决策、渠道连续失败状态）、`small_evidence`（压缩内容）和 schema migration 账本。来源见 `backend/packages/ai_text_self_upgrade/postgres_repository.py:12`、`backend/packages/system_observability/postgres_reviews.py:35`、`postgres_evidence.py:24`，数据库中其他关联还须现场由系统目录查询。

`system_information_items` 的 events 和 source_identity 存在 `ON DELETE CASCADE` 外键（`postgres_store.py:44-52`）；删除主体会丢相应详情与身份关联，包括当前六小时内记录及巡检对象。`system_information_evidence`、`small_evidence`、pin、巡检分析、decision samples 和文件不是级联副本。共享证据还可能从 `main.x_processing_attempts` / `main.x_processing_attempt_events.response_ref` 引用（来源定义 `backend/packages/x_processing/repository.py:2424-2474`）。SQLite 来源写入会持有证据 pin（`sqlite_repository.py:583-598`）；PG 当前记录模型响应使用库内 gzip（`repository.py:1383`），但迁移遗留 response_ref 仍需查证。`system_review_analysis_attempts.raw_response_ref` 与 pin 也是引用（`postgres_reviews.py:51`、`postgres_store.py:54-68`）。当前 PG `_evidence_references` 和 small evidence 的 `delete_if_unreferenced` 检查观测/巡检表，不包含 main 的 response_ref（`postgres_store.py:884-894`；`postgres_evidence.py:133-167`）；不能把其结果当成全域引用闭包。

投影器从 `main.odaily_source_state_outbox` 领取 `projected_at IS NULL` 并在同一事务完成投影及确认（`postgres_schema.py:18-30,157-180`；`postgres_projector.py:120-170`）。正常初始化只是 schema 迁移和初始 state，不回灌已确认的所有历史（`postgres_store.py:175-195`）；因此清空主体再重启会丢现有六小时详情，但未确认旧事件仍会被处理，投影会读取相应业务当前行（`postgres_projector.py:225-245`），可能再次产生旧主体。`event_id` 在提交前分配，项目代码专门说明提交顺序可能不同，不能以扫描时最大 ID 直接视为无遗漏的切换边界（`postgres_projector.py:125-129`）。重置 `projected_at` / outbox 或标记未处理事件会影响投影可靠性，需针对在途事务定义栅栏并验证。

安全实施路线仅为待设计：① 确认用户是否接受从切换时刻开始丢失已有六小时可视历史；界面当前六小时，与想要 3–5 天业务复盘并非同一能力。② 分类保护升级案例、未完成审核/队列、巡检异常状态、业务事实与五天复盘字段，建立所有证据写入者和引用者清单。③ 离线或测试库构造跨引用、共享证据、在途事务、旧未投影事件的代表性回归，明确切换边界；确保业务和保留样本内容/引用完整、历史不会意外复活、新事件不丢。④ 如果需要清理查询副本，用独立短批、后台限速和已验证的协调方案，不能以 schema DROP、无差别 TRUNCATE、目录递归删除代替。⑤ 先验证业务源与引用，再逐步清可证实无引用的证据并控制增长；清理前后检查磁盘、inode、PostgreSQL 空间复用和生产服务影响。此路径不是已验证的生产命令，也不意味着现有实现保证五天复盘。
