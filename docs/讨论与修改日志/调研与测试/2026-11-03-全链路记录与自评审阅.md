# 全链路记录与系统自评审阅

> 执行口径：最终决定为数据全部留在官方服务器并扩容。请先读[执行方案](../2026-11-03-控制台与系统自评改造执行方案.md)；本笔记只提供代码证据，历史留存/抽样/先后顺序建议以执行方案为准。

日期：2026-11-03。范围：本地当前源代码及第一方设计文档；不连接生产、不启动服务、不读取本地产品数据库或敏感配置。本记录供系统方案讨论，不代表生产数据完整性验收。涉及用户引用聊天的案例由主审阅者另外核实。

## 核心判断

当前不是“后端普遍没留记录”，而是 **记录散在不同业务模块、很多只保留最后状态、缺统一的因果与版本对应关系**。因此已有样本往往能追查，跨渠道查询、历史故障还原和主动发现系统性矛盾仍然困难。

应建设一份跨模块的业务过程账本和查询索引，复用已有证据；不要重写各模块状态机，也不要把每次行情轮询的全部原始数据复制进大日志表。全信息流的“全”应包含所有已接入业务及其有意义的处理结果，同时把无新信息的轮询汇总成覆盖/健康记录。

## 故障解释已经存在，下一步应从推断升级为证据

统一分类器已经能够识别欠费、限流、鉴权、数据库锁、网络、发布接口和解析错误，并给操作建议：`backend/packages/common/failure_diagnostics.py:77`、`:128`。监督者与控制台已有共用口径，见 `docs/OdAIly代码与整体设计/监督者.md:56`—`:71`。

但主要输入仍是 last_error 文本，而且优先顺序/关键词可能只给宽泛归因。下一版应在外部依赖适配层记录安全的结构化证据：服务商、模型、调用阶段、HTTP 状态、供应商错误码、请求 ID、超时阶段、耗时、是否可重试、剩余次数。缺失时展示“原因未确认”，不要让 AI 把“超时”解释成“上游欠费”。保存脱敏错误摘要和必要响应片段，禁止保存鉴权请求头。

区分四种结果：业务正常停止（重复/排除/过期/不达门槛）、技术失败、依赖降级、结果未知（例如接口超时但接收方可能已完成）。它们的人工动作和重试风险不同。

## 建议的统一记录契约

一份来源材料可以被多个业务消费、多条材料可以归为一个事件、一个事件也可以产生多稿。不要把所有对象压成一行 task。采用“材料—业务处理—输出”关联，并保留现有模块 ID：来源材料 ID、业务 run ID、关联事件 ID、输出稿件版本/官方 ID。

每个有意义的环节只记：何时开始/结束、输入证据引用、该次规则/代码/Prompt 版本、做了什么决定及可验证理由、输出/下一步、错误及重试安排。大原文保存一次，其余使用不可变快照引用或 hash；hash 必须配可取得的快照，否则只知道不同而无法解释不同。成功的普通轮询保留聚合计数、水位与延迟；发生变化、规则命中和失败才保留个案。

优先补四处：

1. **调用证据在解析之前保存**：失败输出不再随异常丢失；重试各有记录，成功不会抹去历史。
2. **有效指令可重建**：模板版本 + 附加规则版本 + 特色配置 + 最终渲染 Prompt/hash + 代码 revision；允许相同静态 Prompt 内容按 hash 去重。
3. **输出逐版对应**：模型原始稿→规范化/格式化/数据组装稿→提交文本→接收方 ID/回执→镜像版本→审核版本。先展示版本差异，再归因；自动稿和人工稿不强行假设同一来源链。
4. **采集覆盖可计量**：启用源清单/频率、应执行与实执行、成功获取的新材料数、处理水位、最新成功、完整性、进入业务和正常停止数。某源无新新闻、抓取失败、抓取成功但解析为零、信息进队列后卡住，应显示不同结论。

保留策略不能沿用各模块短期详情清理，直接承诺“全部历史可查”。建议先保存轻量业务摘要/索引作为长期账本，详细原文与调用证据分级限期；审核标记/人工处理案例、发布稿和关键回执单独保留。历史已清理的数据显示“详情已按策略清理”，从未来时间点开始保证，不伪造回填。

统一列表是查询读模型，不成为新生产调度器。各模块通过可靠增量记录/可恢复 outbox 或有水位的投影接入；不要在同一页面请求中临时扫多个库、解析所有大 JSON 再分页。来源模块暂不可读时，展示最后索引时间和受影响范围。

## AI 自评应分三层

### 1. 覆盖与运行完整性：确定性检查先行

回答“按已配置覆盖，今天该看的有没有看、该处理的有没有结论”。监督者已经有心跳/积压/卡住/失败窗口，但当前枚举有限：`backend/packages/pipeline_supervisor/repository.py:30`—`:52`。Gate/股票有各自告警，不能据此断言完全没被监控；需要建立跨模块能力清单和统一覆盖页。采集成功不等于覆盖成功，worker 活着也不等于新材料已消费。

先用规则校验：采集窗口缺口、分支数量不守恒、任务无终态、发布成功却缺官方关联、同稿版本不匹配、应挂后台却直发、模板要求和实际路由冲突。规则可检查的事实不依赖 AI 猜测。

### 2. 设计与产出一致性：异步 AI 复核

按来源/分支/模板/版本分层抽样，加上确定性异常和人工反馈的全量案例。AI 读取规则契约、当时有效 Prompt、原始材料、各版稿件和真实审核证据，输出可核对的“期望—实际—证据—影响—归因置信度—建议修复位置”。复核先对齐版本，然后区分原始信息、模型写稿、程序组装、人工修改、镜像采集、审核误报。

按同一规则/版本/根因聚类，避免把几十篇同因问题变成几十条人工工单。发现模板与附加规则冲突时输出系统问题卡，并附几个样本、受影响范围和离线回归用例。以交易误导和名誉损害优先排序。

保持异步：不增加每稿同步 AI 校验，不自动改 Prompt/发布资格/成稿。可确定的约束由本地校验保证，复杂偏差进入每日或按批复核。人工审阅确认后再进入开发、回归和部署流程。

### 3. 信源与产品改进：延续现有 AI 审阅

当前 AI 审阅只对“竞品先发后 Odaily AI 发”和“至少两家竞品发、Odaily 未发”的事件寻找原始 X 账号/网站，界面只展示“优先考虑”；未直接衡量全系统设计一致性。边界见 `docs/OdAIly代码与整体设计/控制台-AI审阅.md:5`、`:13`—`:21`；证据与人工决定 schema 见 `backend/packages/ai_review.py:56`。

因此可以在统一“系统审阅”入口下并列“运行覆盖 / 产出一致性 / 信源改进”，复用反馈与证据展示，但不把现有信源审阅 Prompt 直接扩成万能审计员。

## 建议交付顺序与验收

1. **覆盖地图与记录缺口表**：列出每个入口、分支、正常结束、失败结束、输出、已有证据和保留策略；作为交互流程与全信息流共同的数据字典。验收：现有业务没有“其他未知流程”，不应发稿的业务有正确成功定义。
2. **最小过程账本与版本对应**：先接主流水线、Meme、Hyper、Gate/股票，补失败尝试/有效 Prompt/逐版稿件/回执；保持旧状态机运行。验收：选一条成功、一条正常丢弃、一条失败重试、一条结果未知，能说明每一步及证据；历史缺口诚实呈现。
3. **统一信息流查询与按需详情**：数据库级关键词、来源/业务/分支/状态/时间/投递方式筛选；摘要分页查询，详情独立读取。验收：能找当前页之外的关键词；能按直发/挂后台/失败原因筛出全部适用业务；请求耗时分层可测。
4. **系统自评试运行**：先确定性覆盖检查和小样本异步复核；人工确认后才扩大。验收：已知的规则冲突、数据组装错误、镜像与定稿不一致可被区别识别；证据不足保持未确认；不降低生产速度。

### 先沿用短期工作集，再决定哪些值得留下

已核对现有实现：

- HotTopic 的临时材料、未成热点话题及短期审计保留 48 小时，运行事件 5 天；成热点后证据按永久档案保护。inbox 清理还会避开仍有待处理任务的内容。依据：`backend/packages/hottopic/service.py:41`、`:1910`；`backend/packages/hottopic/topic_aggregator.py:726`。
- 投资线索材料、扫描事件默认 30 天；没有线索引用才清理，关联任务随材料外键级联删除，故“历史为什么判无候选”也会失去。已有线索引用的材料与修订另受保护。依据：`backend/packages/investment_leads/service.py:32`、`:1220`；`backend/packages/investment_leads/schema.py:41`、`:64`、`:108`、`:123`。
- 投资线索原帖 payload 会带最多四条 related_materials，线索修订另存 source_materials_json，存在重复材料存储路径；是否占主要磁盘空间尚未测量，不能只按字段认定节省比例。依据：`backend/packages/investment_leads/service.py:201`—`:260`；`backend/packages/investment_leads/schema.py:108`—`:121`。
- 市场情绪、项目推介的任务保存模型、尝试次数和最后错误，但 `result=None` 直接记为 ignored；当前任务记录不能完整区分“无相关内容”和各类排除理由。依据：`backend/packages/hottopic/service.py:104`—`:119`、`:1382`—`:1437`。

建议按下表管理，不延长全量无产出原文留存：

| 留什么 | 最小内容 | 建议清理方式（均待测量后确定） |
| --- | --- | --- |
| 运行统计 | 每来源/模块每小时的应采、实际成功、失败/降级、新增、处理中、各正常结束原因、重试和预算暂停数量；最近成功时间/内容水位 | 长期留汇总，不复制每轮全部响应；需要历史账号资格时留订阅变更事件 |
| 无产出决定轻索引 | tweet/material ID、账号、原帖 URL、发帖/采集时间、模块、结果码、至多一句短理由、内容 hash、规则版本；已有结构化实体 ID 可复用 | 可先以 30 天为候选窗口，再按真实增量/磁盘预算调整；旧记录压为小时计数。不保存正文、完整模型响应、提示词和 related_materials |
| 处理和重试 | 业务 ID、阶段、每次起止、结果码、依赖服务/错误码、尝试次数、下一步；失败响应只留脱敏小片段 | 按天/字节封顶，超过上限归并同类错误；已发稿/人工确认的问题保留摘要引用 |
| 真正产出及其依据 | 热点正文、实际线索、草稿/定稿/提交稿的不同版本、官方回执、用到的原始证据 | 在现有资料上补关联；同一文本 hash 只存一份，不为统一信息流再复制原文。保留多久由业务价值和预算确定，不承诺无限保留 |
| 少量负例样本 | 按模块/规则版本/排除理由分层抽样的必要文字及原链接，包含截断标记和原始判定 | 固定总量与字节双上限，建议起步全系统每日最多 100 条、每条文字最多 2 KB、滚动 14 天、样本正文总额最多 10 MB；这些只是起始配置，不是磁盘实测。截断后不足判断的记不可判定，不补猜 |
| 已确认问题案例 | 一份最小复现材料、对应规则组件、各版稿/结论、人工决定 | 从抽样区提升为长期回归案例；限制每类代表案例数量，保留问题数量和关联 ID，避免重复归档几百篇同因错误 |

样本正文预算的上界算术是 `100 × 2 KB × 14 ≈ 2.8 MB`，**不包含 SQLite 行、索引、任务和审阅结果开销**；全库应另设预算与剩余空间预警。轻索引虽小也会随帖子数增长，不能只规定“单条小”便默认永久保留。先统计真实新增字节、各表大小、清理速度和 WAL 峰值，再确定配额；所有清理受未完成任务/必要证据引用保护，不能为释放空间破坏尚在运行的任务。

每个模块给信息流返回“可查时间范围、索引更新时间、详情是否已清理”，避免把清理后搜不到解释成系统从未看到。

### Prompt 与材料如何不重复保存

- Prompt 模板、附加核心规则、特色配置和输出 Schema 各按内容 hash 存一份；规则代码关联 Git revision，活动模板关联既有版本表。单次运行只记这些组件的 ID/hash、组合顺序、匹配到的少量标题主体、模型及参数。组件变了才增加一份，不把完整提示词写进每次调用。
- 材料按 `material ID + content hash` 存一次；任务、模块和线索修订只记引用/必要摘录。引用、转发、回复用关系表指向材料，避免每次把四条相关正文再嵌一遍。该去重是拟议迁移，不是当前事实。
- 需要复现的已产出或异常案例，保留确切材料版本及不可变规则组件。无产出且已清理的正文不求全量精确复现；轻索引只证明当时看到过、怎么判的，**不证明判得正确**。hash 不能恢复原文。
- 轻理由来自业务模型的短结论/结构化结果或确定性规则，不保存模型思考过程，也不为每条普通丢弃再增加 AI 解释调用。

### 六项能实际运行的巡检：看哪些数据→找什么→给什么

以下示例为说明输出格式的假设案例，不是本轮发现的生产问题。第一项以确定性查询为主，其他项异步、有单轮/每日上限；不增加发稿关键路径的同步 AI 调用。

#### 1. 覆盖断点与处理遗漏

- **看哪些现有数据**：启用账号/站点/模块订阅、last_success、各消费任务状态/尝试/预算、HotTopic inbox、热点自动快讯 outbox、本地 job 与模块运行状态。投资线索已有按阶段积压和预算数据，依据 `backend/packages/investment_leads/schema.py:7`、`:41`、`:134`；共享采集与分模块建任务见 `backend/packages/hottopic/service.py:1138`—`:1196`。
- **新增最少记录**：账号订阅变更；每次采集窗口的最早/最新返回时间、返回数量、是否打满上限/缺页、已消费水位；按小时汇总流入与各结束结果。不保留全部返回原文。
- **找什么**：启用但无成功采集、成功采集却无相应消费、长期预算暂停、分发已提交而下游没接收、结果未知未跟进；将“无新帖”“拉取截断风险”“技术失败”分开。
- **给什么**：覆盖缺口卡：`投资线索：3 个启用账号已有新材料，但扫描水位落后 2 小时；48 项待扫描，43 项因预算暂停。建议先调整预算/处理速率。` 卡片附区间、受影响账号/任务链接和证据计数；无需 AI 猜根因。
- **不能判断**：接口成功不证明平台返回了全部帖子；未命中不证明现实没有新闻。暂停是配置选择还是不合理需人工判断。

#### 2. 竞品已报道、本系统为何没产出

- **看哪些现有数据**：现有 AI 审阅两类竞品事件、来源文章及原链接；Odaily 发布镜像、原始信源配置、主任务/热点/自动快讯关联。当前 AI 审阅只推荐信源，可在同事件上增加“处理去向”研究，保持原有推荐功能独立。依据 `docs/OdAIly代码与整体设计/控制台-AI审阅.md:13`—`:21`。
- **新增最少记录**：上述无产出轻索引；账号当时是否启用。仅对具体候选事件保存一次调查结果、取证 URL/时刻/覆盖边界，不保存整批时间线。
- **找什么**：逐层区分“未配置→该采未采→已采未处理→明确排除→只成热点/线索但本来不应发快讯→写作或投递失败→已发但事件关联未识别”。优先精确原帖 ID；同主体/同日/相近语义只召回候选，AI 核对后才关联。
- **给什么**：`两家竞品报道某协议安全事故。原帖来自已启用账号；轻索引表明 09:03 已采，热点模块因“同类旧事件”排除。原文现仍可取得，复核发现这是新的损失披露，建议复核去重规则 vN。` 若证据不足则写：`已采并排除，但旧原文已清理、回取失败，不能确认是否误丢弃。`
- **不能判断**：竞品发过不等于值得发，也不证明我们错；必须按交易/名誉影响审阅。原链接不存在时，账号时间线是有界补充证据，不可伪装成完整历史采集；详见下节。

#### 3. 无产出抽样：哪些排除理由经常错

- **看哪些现有数据**：投资扫描分类、subject/action/summary/reason/Prompt 版本，热点 decision_audit，市场情绪/项目推介的任务结果；优先用尚在工作集的材料。依据 `backend/packages/investment_leads/schema.py:64`—`:80`；`backend/packages/hottopic/topic_aggregator.py:485`—`:496`。
- **新增最少记录**：统一短 reason_code、规则版本；市场情绪/推介将 ignored 的无相关内容与账号关闭分开；按固定上限留小样本及抽样方法。没有理由时不要由第二个 AI 倒推当时模型怎么想。
- **找什么**：不完整/欠费/限流被记成无候选；个人琐事被当重大驱动；应候选却被当静态介绍；模块本来无关却反复命中。先做状态约束检查，再让 AI 在每层样本上独立判断，比较旧判断与规则。
- **给什么**：`本周投资线索 no_candidate 抽查 40 条：发现 3 条疑似把“已宣布签署合同”判为一般介绍，集中于规则 v4；2 条截断，无法判断。附 3 例和原判定。` 标明样本数、抽样层与不确定性，形成一张根因卡。
- **不能判断**：100 条样本无法证明全部排除正确；只抽失败/边界样本不能估计全局误丢比例。样本不足完整语境时不据此要求改规则。

#### 4. 生效规则是否互相冲突

- **看哪些现有数据**：所有活动模板版本、代码追加核心规则/链上规则、特色模式、结构化输出要求、发布路由配置与确定性校验。主写作实际拼接路径见 `backend/packages/x_processing/worker.py:1880`、`:1911`；主流程只保存模板版本，见 `backend/packages/x_processing/sqlite_repository.py:433`。
- **新增最少记录**：按变更生成一次“有效指令组件清单”和 hash；运行记录引用清单。只扫描新增/变化组合，不每天把所有生产原文输入一遍。
- **找什么**：同一字段出现必须/允许的矛盾、模板与追加规则冲突、业务强制挂后台与发布设置冲突、固定格式有要求但无程序校验。AI 给逐字冲突证据，确定性测试验证能否同时满足。
- **给什么**：`链上快讯开头：模板要求“据{发言人}监测”，附加规则允许“发文称”。这两条对同类输入冲突；影响组合 H，建议统一规则并补本地校验。` 附两个规则出处和适用分支。
- **不能判断**：扫描未发现冲突不代表模型会遵守；AI 发现的冲突也需核对适用条件，不能只凭两个措辞不同判冲突。不自动改活动 Prompt。

#### 5. 成稿、提交、镜像和审核意见到底哪里不同

- **看哪些现有数据**：模型原始稿、结构化草稿、定稿、发布响应、镜像和文本/事实审查快照、人工接受/拒绝反馈；事实审查已有 content_hash 与 runs，文本审查已有稿件 hash。
- **新增最少记录**：各不同文本版本的 hash 与内容引用、转换步骤标识、提交稿版本和远端快讯 ID、审核引用的确切稿件版本。相同版本不重复存正文；完整回执中的无关字段可舍弃。
- **找什么**：先判断是否同稿，再归因“模型原稿就错/规范化或数据组装改错/提交正确而镜像变了/人工改稿/审核指控无同文依据”。高风险实体、金额、状态变化优先，纯润色不入问题池。
- **给什么**：`漏字只存在于镜像 B，AI 定稿/提交稿 A 完整；审核实际针对 B。当前不能归责编写者，建议核对镜像或人工变更。` 或 `数字在数据组装步骤由 A 变为 B，与原证据不符，疑似程序变换错误。`
- **不能判断**：没有官方修改事件时，“镜像不同”无法区分人工修改与采集错误；接口成功回执也未必能证明接收方正文逐字一致。此时明确列待取证，不把责任强行归给模型或审核者。

#### 6. 热点总结和投资推导有没有越过证据

- **看哪些现有数据**：真正展示的热点 brief_revisions、其 source_claim_ids 与 support/context/unrelated 复核；投资线索 revisions、source_claims/source_materials、条件和标的传导关系。热点永久证据/brief hash 已有，见 `backend/packages/hottopic/topic_aggregator.py:475`、`:479`、`:520`；投资来源与修订见 `backend/packages/investment_leads/schema.py:108`—`:130`。
- **新增最少记录**：审阅选择的版本及证据引用、规则组合 hash、问题原句、对应原文摘录和“事实主张/系统推导”边界；对当前已有证据不再复制另一份完整包。
- **找什么**：热点混入竞争资产或 unrelated claim、同事件重复数值被写成矛盾；投资线索把系统推导说成原作者结论、虚构关键前提、遗漏批准条件、引述归错账号。题材映射允许合理推导，不能机械要求所有经济关系都由原帖逐字写出。
- **给什么**：`线索 L 将“拟采用、待监管批准”写成“已经采用”，且原文没有批准结果。应恢复条件；2 篇同版本线索有相同模式，建议检查推导 Prompt vN。` 附原句和证据，不给买卖建议。
- **不能判断**：这不独立验证消息真假，也不能证明投资判断会赚钱；只有证据与产出一致性。没有完整引用语境时不能把推导本身当成造假。

六类结果合入同一“待人工审阅问题卡”，包含：问题/正常解释、影响范围、确切证据、确定或待确认、建议改哪里、接受/驳回/暂缓。按规则版本和根因去重；只有重大新问题或需人工动作才提醒，不把正常巡检刷屏。人工决定进入后续样例和回归案例，但不自动修改规则或线上发稿。

### 不留全部丢弃原文后，漏闻如何查到哪一步

建议采用 **“竞品事件触发回查 + 轻决定索引 + 极少量分层样本”** 的组合。

1. 竞品回查把调查限于已出现的重要事件，先用竞品明确原链接查 tweet ID→采集/模块决定轻索引。存在精确记录，能证明系统见过及当时去向；没有记录仍需先检查索引保留区间与采集窗口，不能直接说没采到。
2. 轻索引不存原文，照样能查“哪一账号、何时、哪个模块、按哪版规则做了什么”；已有扫描摘要/实体可协助召回，但它们也是旧模型输出，不替代原文证据，更不能把语义召回候选直接当同一事件。
3. 尚在 48 小时/30 天工作集则直接复用材料；已清理时，仅对命中的具体原帖尝试取回原文。拿不到确切原帖，才对竞品链接明确指向的少量账号读取一轮有界时间线；设置每日调查事件数、账号数、请求数上限，复用现有 pacer 和 429 冷却，不做全账号历史回扫。
4. **当前代码能力限制**：`backend/packages/hottopic/capture.py:471`—`:503` 一次读取 profile/statuses、count 最大 100，只做本地 cutoff 过滤，没有跨页历史抓取。因此高频账号过了数天就可能覆盖不到旧事件；旧帖删除、账号保护、接口截断、引用父帖缺失均会失败。基于时间线无法找到只应写“此次有界取证未找到”，不能写“源账号没有发过/系统没有丢过”。按单帖取回如需新接口，须单独实现验证，不能视作现成能力。
5. 小样本在原文过期前做判断，能发现某版规则反复误排，不必逐条回取全部历史；它适合发现模式，不能给每条已删负例补出原因。对没有外部报道、又没抽中样本的漏闻，本方案可能始终不知道。要更接近全量漏闻审计，就必须增加原文留存/样本率/第三方历史取证成本，无法免费同时得到容量低和全量语义可追溯。

第一版可先做第 1、4、5 项巡检，因为已有输入较充分；同时开始写轻索引和小样本，为第 2、3 项积累证据，再上线第 6 项输出抽查。实际容量配额、负例取证预算和自动提醒阈值在只读测量后确定；本轮不修改留存代码、不清理生产数据、不启用任何新巡检。
